# 文書の指示

文書の役割分担は、[開発方針](../../docs/development-policy.md)「開発の流れ」「設計フェーズの進め方」が定めています。本書は、文書を書く・直すときの判断を挙げます。

## 文書の種類と、手の入れ方

| 文書 | 寿命と役割 | 手の入れ方 |
|---|---|---|
| 開発方針、仮説、企画書、ユースケース記述 | 長寿命。プロジェクト全体を対象に、一度だけ作る上位の文書 | 開発者が求めたときにだけ、改訂する。企画書とユースケース記述には、技術要素を書かない。IDは、振り直さず、欠番を許す |
| 仕様(`docs/specs/<スライス>.md`) | 機能スライスごとに、1つ | 後続のスライスが、前のスライスの仕様を変える場合は、開発者に確かめる |
| ADR(`docs/adr/`) | 長寿命。判断と理由を、時系列で残す | active の間は、直してよい。frozen は、編集しない |
| 詳細設計(`docs/design/<スライス>.md`) | 使い捨て。実装の完了後に、削除する | 実装の中で、異なる形が要る場合は、詳細設計を直してから、実装する |
| アーキテクチャ概要(`docs/architecture.md`) | 長寿命。1枚だけ持つ、現在の姿 | 実装と一致させ続ける。理由と経緯は、書かない(ADRが受け持つ)。パッケージ、ポート、経路、実行環境を変えたら、同じ変更の中で直し、「最終更新」と「現在の範囲」を改める |
| 観察記録(`docs/observations.md`) | 長寿命。時系列に、追記する | 項目と書き方は、`CLAUDE.md`「観察記録」と ADR-008 に従う |
| 検査の記録(`docs/dependency-check-log.md`) | `make check-deps` が、自動で追記する | 手で書き換えない |
| 仮実装の箇所の一覧(`docs/temporary-implementations.md`) | MVPの完了まで | コードの `仮実装(WS-Pn)` のコメントと、一致させる |
| 手順書(`README.md`) | 長寿命。人が行う手順 | 手順、道具、設定(環境変数)を変えたら、同じ変更の中で直す。実際に行って確かめた手順だけを書き、端末に依る事情には、確かめた日を添える |

「なぜ」はADR、「これから、どう実装するか」は詳細設計、「今、どうなっているか」はアーキテクチャ概要、「どう動かすか」は手順書が受け持ちます。同じ内容を、複数の文書に書きません。他の文書が定めたことは、文書の名前と節、またはIDで、参照します。

## 仕様

[ウォーキングスケルトンの仕様](../../docs/specs/walking-skeleton.md)を、手本にします。

- 振る舞いを、技術要素に依存しない形で定める。技術要素は、選定せず、決定が要る事項と、選定の条件を挙げる(「技術要素の決定」)。画面の構成と操作の手段は、設計で定める。
- 構成は、次の通りとする。前提と、IDの表。目的と完了の姿。本書で判断した事項(理由とともに)。機能仕様。非機能要件の適用(適用する水準と、受け入れ基準の対応)。OWASP Top 10 の該当の確認。受け入れ基準。動作検証。技術要素の決定。マイルストーンの完了条件との対応。後続に送る事項。
- 対象とするフローは、ユースケース記述のID(UC-09 E1 など)で示す。対象にしないフローと、送り先を、明示する。
- 非機能要件は、企画書「水準を最初に適用する時点」に従い、そのスライスの機能に関わる水準を、受け入れ基準に落とす。上限値や有効期限などの具体的な値は、仕様で定める。
- OWASP Top 10 の該当の確認(SEC-4)は、スライスごとに行う。版は、フェーズ1の間、OWASP Top 10:2025 を使う。前のスライスが「見送り」として送った項目を、確かめる。
- 受け入れ基準は、IDを付け、参照(ユースケースのフロー、水準のID)と、確認方法(自動テスト、動作検証、検査、設計の確認など)を添える。誰が、何をすると、何が起きるかを、確かめられる形で書く。
- 前のスライスの仕様と、企画書が、そのスライスに送った事項(「後続に送る事項」「仕様以降で決める事項」)を、拾う。
- 新たに判断した事項と、後続に送る事項は、表にして残す。

## ADR

- 1つのADRには、1つの判断だけを書く。番号は、ADR-001 からの連番で、次は、既存の最後の番号の続きとする。ファイルの名前は、`ADR-NNN-<英語の短い名前>.md` とする。
- 冒頭に、ステータス、作成日、対象を書く。節は、Context / Decision / 検討した代替案 / Consequences とする。
  - Context: 判断が要る理由、選定の条件、関連する受け入れ基準と水準のID。
  - Decision: 決めたこと。技術要素の選定では、「選定の条件の確認」の表を置き、共通の条件(後続フェーズの妨げにならない、ライセンスがMITライセンスでの公開と両立する、PRV-3、費用)を確かめる。
  - 検討した代替案: 表にする。代替案の利点も書いたうえで、採らなかった理由を書く。
  - Consequences: 判断の帰結。不利な帰結と、携行コストも書く。
- ステータスは、active(作成時から、実装の完了まで)と、frozen(実装の完了後)の2つである。superseded は、設けない。
- frozen のADRは、編集しない。過去の判断を、打ち消す・修正する・補う場合は、新しいADRに書き、元のADRを参照する。
- ADRを起こすのは、アーキテクチャ上重要な判断である(技術要素の選定、層の構成や規則の変更、境界の握り方など)。新たな判断を伴わないスライスでは、ADRを起こさず、詳細設計だけでよい。
- 複数サーバー構成への移行を妨げないこと(PERF-3)は、技術選定のADRで確かめる。機能の実現に、外部のサービスが要る場合は、送信する内容を、ADRに記録する(PRV-3)。

## 詳細設計

- 仕様とADRを、実装できる形に具体化する。採用の理由は、ADRに従い、繰り返さない。
- 仕様とADRが設計に送った事項と、具体化する中で判断した事項を、冒頭に、番号(DD-nn)を付けて、理由とともに挙げる。アーキテクチャ上の判断に当たるものは、ADRにする。
- 層ごとに、置くもの(型、関数、ポート、入力・出力のデータ構造)を示す。受け入れ基準と、テストの対応を示す。
- 実装の順序を示す。各手順は、`make check` のうち、その時点で実行できるものが通る状態で、終える(ウォーキングスケルトンでは、内側の層から、順に進めた)。
- 完了時に行うことを挙げる。削除した後は、リポジトリの履歴で参照する。

## 文体と用語

既存の文書(ADR、仕様)の文を、手本にします。

- 本文は、です・ます体で書く。表の中と、箇条書きは、常体(〜する、〜である)で書いてよい。
- 平易な日本語の言葉を使い、同じものを、同じ言葉で呼ぶ。新しい用語は、定義してから使う。ユースケース記述「用語」と、次の表に従う。

| 使う言葉 | 指すもの |
|---|---|
| 利用者 | アプリを使う人(「ユーザー」は、固定ユーザー、削除済みユーザーなど、定めた語にだけ使う) |
| 端末 | アプリを開いているブラウザのタブ1つ |
| 識別名、表示名、連絡先 | ユースケース記述「用語」の通り |
| 認証に用いる秘密、ログイン状態を示す資格 | 上位の文書と仕様では、方式に依らない、この呼び方を使う |
| 保管先 | メッセージなどを永続化する先(選定の後は、PostgreSQL) |
| 通信の形式 | サーバーとクライアントの間の、要求、応答、配信の形式(`api/openapi.yaml`) |
| 配信 | 保管が確定した情報を、アプリを開いている端末へ、操作なしに届けること |
| 拒否 | システムが、操作を受け付けないこと。完了できなかったこと(エラー)と、区別する |
| 詰め替え | 層の境界で、型を、別の型に移し替えること |
| 置き場所 | パッケージ、ディレクトリ |
| ポート、境界要素 | ADR-005 の用語の通り |
| 依存規則、飛ばし禁止 | 仮説「仮説の本体」の通り(飛ばし禁止は、strict layering) |
| 水準 | 企画書の、非機能要件の目標水準(SEC-1 など) |
| スライス | 仕様から動作検証までを通す、機能の単位 |
| 仮実装、正式実装 | 仕様が、仮実装と定めたものと、その置き換え |
| 自動テスト、検査、動作検証 | テスティングフレームワークで実行するテスト。機械的な検査(lint、依存規則、秘密の検出など)。開発者がブラウザで行う確認 |
| 設置環境、検証環境 | 雛形を構築して動かしている、1つの環境。開発者が、検証のために使う環境 |
| 雛形の利用者 | 雛形を基に、自らのサービスを開発する開発者 |

- 判断には、理由を添える。採らなかった案と、その理由も残す。
- 事実と、解釈・推測を、分けて書く。確かめたことには、手段(と、端末に依る場合は、日付)を添える。確かめていないことは、確かめていないと書く。
- 日付は、`2026-11-21` の形で書く。「今日」「先日」などは、使わない。
- 他の文書や、コードへの参照は、相対パスのリンクか、IDで書く。
