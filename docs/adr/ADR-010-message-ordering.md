# ADR-010 メッセージの順序と、履歴と配信の境目の扱い

- ステータス: active
- 作成日: 2026-11-19
- 対象: ウォーキングスケルトン([仕様](../specs/walking-skeleton.md)「メッセージ」「会話の履歴を読む」「後続に送る事項」)

## Context

仕様は、メッセージの順序と、履歴と配信の境目について、次を定めています。

- 順序は、会話の中で、システムがメッセージを保管した順である。メッセージは、会話のすべての参加者に、履歴としても、リアルタイムの配信としても、同じ順序で見える。2人がほぼ同時に送信した場合も、同じ順序である(WS-07)。
- 送信の日時は、システムがメッセージを保管した日時であり、クライアントの時計には依らない。
- 会話を開くのと前後して保管されたメッセージは、履歴と配信のどちらで届いても、欠けることなく、1通だけ、順序の通りに示される(WS-22)。どちらで届けるかと、重複を除く手段は、設計で定める。

端末にメッセージが届く経路は、3つあります。送信の完了の応答(HTTP)、履歴(HTTP)、配信(WebSocket)です([ADR-002](ADR-002-realtime-communication.md))。経路が分かれているため、端末に届く順は、保管した順と一致するとは限りません。また、会話を開くのと前後して保管されたメッセージは、履歴と配信の両方に現れることも、手段を講じなければ、どちらにも現れないこともあります。

保管先は PostgreSQL です([ADR-004](ADR-004-data-store.md))。

## Decision

### 順序の与え方

- サーバーは、各メッセージに、会話ごとの連番を付ける。連番は、会話の最初のメッセージを1とし、欠番を作らない。メッセージの順序は、この連番とする。
- 連番は、メッセージを保管するトランザクションの中で、会話の単位で直列にして付ける(会話の行を、ロックする)。これにより、連番の順は、トランザクションが確定した順と一致する。保管が取り消された場合は、連番の割り当ても取り消され、欠番は生じない([ADR-012](ADR-012-transaction-boundary.md))。
- 送信の日時は、連番を付けるのと同じ時点(会話の行のロックを得た後)の、保管先の時計の値とする。PostgreSQL の `clock_timestamp()` を使う。`now()` は、トランザクションを開始した時刻を返すため、使わない。ロックを待つ間に、後から始まったトランザクションが、先に連番を得ると、日時が、連番と前後するためである。
- 表示の並びには、連番だけを用い、送信の日時を用いない。
- 完了の応答、履歴、配信のどの経路でも、メッセージに、会話を判別できる情報と、連番を含める。

### 端末での統合

- クライアントは、開いている会話のメッセージを、連番をキーとして保持する。3つの経路のどれから届いたメッセージも、同じ連番のものが既にあれば、加えない。表示は、連番の順とする。届いた順には、依らない。
- クライアントは、次の順で、会話を開く。
  1. WebSocket の接続を確立する。サーバーは、その接続を配信の宛先として登録した後に、受信を開始できたことを、その接続で端末に知らせる。
  2. クライアントは、その知らせを受けた後に、履歴を取得する。
  3. クライアントは、履歴の取得を始めてから、応答を得るまでの間に届いた配信を、捨てずに保持し、履歴と統合する。
- 接続は、利用者がアプリを開いている間、保たれる(ADR-002)。別の会話を開くときは、手順2から行う。

### 欠けないことと、重複しないことの根拠

あるメッセージの保管が確定した時点を、履歴の読み取りの時点と比べます。サーバーは、履歴の読み取りを、接続の登録より後に行います(手順1、2)。サーバーは、配信を、保管が確定した後に、その時点で登録されている接続に対して行います。

| 保管が確定した時点 | 届く経路 |
|---|---|
| 履歴の読み取りより前 | 履歴に含まれる。接続の登録より後であれば、配信でも届く |
| 履歴の読み取りより後 | 接続は既に登録されているため、配信で届く |

どちらの場合も、少なくとも1つの経路で届きます。両方で届いた場合は、連番によって、1通になります。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| 送信の日時で、順序を決める | 追加の項目が要らない。同じ時刻のメッセージの順序が、定まらない。時刻を付けた順と、保管が確定した順は、一致するとは限らない |
| 保管先の全体で1つの連番を、順序とする | 会話の単位のロックが要らない。値は、確定の前に割り当てられるため、後の値のメッセージが、先に確定することがある。履歴を読み取った後に、より小さい値のメッセージが現れうる。フェーズ1の、指定した位置からの取得(PERF-2、UC-13)で、取りこぼしの原因になる |
| サーバーが付ける識別子(順序を持たないもの)で、重複だけを除く | 重複は除ける。順序のために、別の項目が要る。連番は、重複の排除と、順序の両方に使える |
| 履歴を取得してから、接続を確立する | 手順が、直感に合う。履歴の読み取りから、接続の登録までの間に保管されたメッセージが、どちらの経路でも届かない |
| 履歴も、WebSocket で届ける | 1つの経路の上で、履歴と配信の順序を、サーバーが決められる。操作を HTTP に揃える判断(ADR-002)に反する |
| 重複を、サーバーの側で防ぐ(端末ごとに、どこまで届けたかを保持する) | クライアントが単純になる。サーバーが、端末ごとの状態を持つことになり、複数サーバー構成への移行(PERF-3)を難しくする |

## Consequences

- 同じ会話への送信は、会話の単位で、直列に保管される。想定規模では、支障がない。異なる会話への送信は、互いに待たない。
- 会話が成立していない場合、最初のメッセージの保管と同じトランザクションで、会話を成立させる。2人がほぼ同時に最初のメッセージを送った場合、会話の一意性の制約(ADR-004)によって、会話は1つになり、2通は、同じ会話の連番1と2になる(WS-05)。
- 統合の振る舞いは、クライアントの application([ADR-005](ADR-005-layer-structure.md))に置き、届く順を変えたテストで確かめる(WS-22。[ADR-006](ADR-006-automated-testing.md))。
- 受信を開始できたことの知らせは、WebSocket で届けるメッセージの1つとして、通信の形式に定義する([ADR-003](ADR-003-api-contract-definition.md))。
- 送信に使われた端末は、同じメッセージを、完了の応答と配信の両方で受け取る。連番によって、1通になる。送信中の表示との突き合わせは、[ADR-011](ADR-011-sender-device-delivery.md) で定める。
- 根拠は、配信が端末に届くことを前提とする。配信が届かなかった場合、そのメッセージは、会話を開き直したときに、履歴として読める(仕様「リアルタイムの配信」)。
- 欠番のない連番は、フェーズ1の、分割しての取得(PERF-2)の位置の指定と、再接続の後の取得(UC-13)に使える。本スライスでは、これらの仕組みを作らない。
- 送信の日時が、連番の順と前後することは、上の決め方により、保管先の時計が戻らない限り、ない。表示の並びには用いないため、前後しても、順序は変わらない。
