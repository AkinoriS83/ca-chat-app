# ADR-011 送信に使われた端末への配信の扱い

- ステータス: frozen
- 作成日: 2026-11-19
- 対象: ウォーキングスケルトン([仕様](../specs/walking-skeleton.md)「リアルタイムの配信」「後続に送る事項」)

## Context

仕様は、当初、配信の宛先から、送信に使われた端末を除くと定め、除く手段を設計に送っていました。理由は、次の通りでした。その端末には、完了の応答によってメッセージを示す。同じメッセージを2つの経路で届けると、その端末で、重複を除く仕組みが要る。

設計で、次の2点が分かりました。

- 送信は HTTP で、配信は WebSocket で行う([ADR-002](ADR-002-realtime-communication.md))。サーバーは、送信の要求だけからは、それが、どの接続と同じ端末から来たのかを、知ることができない。除くには、接続ごとに識別子を発行して端末に伝え、送信の要求に添えさせ、ユースケースの入力と配信のポートを通して、接続を保持する側まで運ぶ仕組みが要る。
- クライアントは、履歴と配信の境目のために、連番によって重複を除く仕組みを、既に持つ([ADR-010](ADR-010-message-ordering.md))。仕様が除く理由としたものは、成り立たなくなった。

このため、仕様を改め、送信に使われた端末も、配信の宛先に含めることにしました(仕様「リアルタイムの配信」、WS-37)。本ADRは、その端末に2つの経路で届くメッセージの扱いを、決定します。「端末」の単位は、[ADR-013](ADR-013-temporary-login-identity.md) に従います。

残る課題は、1つです。送信に使われた端末には、同じメッセージが、完了の応答と配信の両方で届きます。届く順は、定まりません。送信中のメッセージは、まだ連番を持たないため、配信が先に届くと、クライアントは、連番だけでは、それが自分の送信中のメッセージなのか、同じ利用者の別の端末が送ったメッセージなのかを、見分けられません。見分けられないと、送信中の表示と、配信で届いたメッセージが、応答が届くまで、2通として並びます。

## Decision

- サーバーは、送信に使われた端末を、配信の宛先から除かない。宛先は、会話の参加者がアプリを開いている端末の、すべてとする。サーバーは、送信の要求と、WebSocket の接続を、対応付けない。
- 配信するメッセージに、送信の識別子([ADR-009](ADR-009-send-identifier.md))を含める。履歴には、含めない。
- クライアントは、送信中のメッセージと、送信できなかったメッセージを、送信の識別子をキーとして保持する。完了の応答と、配信のうち、先に届いた方によって、同じ送信の識別子のメッセージを、完了したメッセージ(連番を持つ)に置き換える。後から届いた方は、連番によって、加えない(ADR-010)。
- 保持している送信の識別子と一致しない配信は、通常の配信として扱う。
- 送り直しによって、保管済みのメッセージについて完了を示す場合は、配信しない(ADR-009)。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| 接続の識別子によって、送信に使われた端末を、宛先から除く(改める前の仕様の通り) | クライアントは、配信との突き合わせが要らない。サーバーが、接続ごとに、推測できない識別子を発行し、受信を開始できたことの知らせ、送信の要求、ユースケースの入力、配信のポート、複数サーバー構成での中継の内容にまで、通すことになる。除く理由であった重複の排除は、連番で既に足りている |
| 除かずに配信し、連番だけで重複を除く(配信に、送信の識別子を含めない) | 配信の内容が増えない。配信が完了の応答より先に届くと、送信中の表示と、届いたメッセージが、応答が届くまで、2通として並ぶ。配信は、応答とほぼ同時に行われるため、まれな場合ではなく、送信のたびに起こりうる |
| 送信者自身の端末への配信にだけ、送信の識別子を含める | 識別子が、会話の相手に伝わらない。宛先によって、配信の内容を変えることになる。一致は、送信者ごとに判定するため、相手が識別子を知っても、得られるものがない(ADR-009) |
| 完了の応答を返した後に配信し、届く順を、サーバーの側で保つ | クライアントは、配信が先に届く場合を、扱わなくてよい。応答と配信は、別の接続を通るため、送った順に届くとは限らない。応答を書き出すのは、ユースケースから戻った後の adapter であり、usecase が、配信をその後に置くこともできない |
| 送信を、WebSocket の上で行う | 応答と配信の順を、サーバーが決められる。操作を HTTP に揃える判断(ADR-002)に反する |

## Consequences

- サーバーは、接続の識別子を持たない。ユースケースの入力と、配信のポートに、除く接続を渡す項目が要らない。複数サーバー構成で、サーバーの間で中継する内容は、メッセージだけになる(PERF-3)。
- 送信に使われた端末へ、送信のたびに、1通を余分に届ける。想定規模では、支障がない。
- 完了の応答が届かなかった場合も、配信が届けば、その端末は、メッセージを、完了したものとして示す。配信も届かなかった場合は、送り直すか、会話を開き直すまで、送信できなかったメッセージとして示される(仕様 WS-D2)。
- 送信から10秒が過ぎ、送信できなかったと示した後に、応答または配信が届いた場合も、同じ置き換えを行う。
- 送信の識別子は、会話の相手の端末にも伝わる(ADR-009 の Consequences)。
- 置き換えの振る舞いは、クライアントの application([ADR-005](ADR-005-layer-structure.md))に置き、応答と配信の届く順を変えたテストで確かめる(WS-37。[ADR-006](ADR-006-automated-testing.md))。
- 「配信されない」ことを確かめるサーバーのテストが、1つ減る(改める前の WS-37)。
