# ADR-008 観察記録の項目と記録タイミング

- ステータス: active
- 作成日: 2026-11-19
- 対象: プロジェクト全体(ウォーキングスケルトンの設計フェーズで定める。開発方針「設計フェーズの進め方」)

## Context

本プロジェクトは、[仮説](../hypothesis.md)を実践し、振り返り・観察記録を残します。仮説の採否は判定しません。記録は、仮説を支持する所見と、支持しない所見の両方を残します(仮説「位置づけ」)。

仮説と企画書は、記録について、次を定めています。

- 妨げになった箇所・助けになった箇所は、後から遡って復元できないため、開発中に、発生の都度記録する(仮説「チェックポイント」、企画書「各マイルストーンに共通の完了条件」5)。
- 機能スライスの完了時に、記録の有無を確認する(企画書「リスク」11)。
- チェックポイントで、次を記録する(仮説「チェックポイント」、企画書「マイルストーンごとの完了条件」)。
  - MVP完了時: 妨げ・助けの振り返り。一度も変更・参照されなかった境界要素の数。パススルーなユースケースメソッドの数。
  - フェーズ2(グループチャット追加)時: 変更したファイルの数、レイヤー横断の漏れの有無、構造自体の変更の要否。
  - 雛形の到達後にブロックを追加する場合: レイヤーごとの変更したファイルの数、既存の機能のコードを変更した箇所、構造自体の変更の要否。
- 記録する項目と記録タイミングは、ウォーキングスケルトンの設計フェーズで、ADRとして定める(開発方針「設計フェーズの進め方」)。

仮説は、チェックポイントで数えるものの数え方を、定めていません。数え方が決まっていないと、数える時点の判断で結果が変わります。境界要素を最初に置くのは、ウォーキングスケルトンであるため、数え方も、ここで定めます。

層の構成と、境界要素、ポートの定義は、[ADR-005](ADR-005-layer-structure.md) に従います。

## Decision

### 記録の置き場所

観察記録は、`docs/observations.md` の1つの文書に、時系列で追記します。最初の記録の時点で作成します。文書は、次の3つの部分からなります。

| 部分 | 記録タイミング | 内容 |
|---|---|---|
| 都度の記録 | 発生の都度 | 妨げになった箇所・助けになった箇所 |
| スライスの記録 | 機能スライスの完了時 | 都度の記録の有無の確認。スライスの範囲 |
| チェックポイントの記録 | 仮説が定めるチェックポイント | 計数と、振り返りの所見 |

### 都度の記録

設計、実装、テスト、動作検証のどの工程でも、下の「記録する出来事」に当たることが起きた時点で、記録します。開発者が気付いた場合も、AIが気付いた場合も、記録します。

| 項目 | 内容 |
|---|---|
| 番号 | OBS-001 からの連番。振り直さない |
| 日付 | 出来事が起きた日 |
| スライスと工程 | 例: ウォーキングスケルトン、実装 |
| 区分 | 妨げ / 助け / どちらとも言えない |
| 出来事 | 何をしようとして、何が起きたか。事実だけを書く |
| 関わる構造 | 関わった層、境界要素、規則(依存規則、飛ばし禁止、型参照の範囲) |
| 手がかり | コミット、ファイル、検査の出力など、後から確かめられるもの |
| 所見 | 構造が、その出来事にどう働いたかの解釈。比較対象がないため、構造がなかった場合との差は推測であることを、明示する |
| 気付いた者 | 開発者 / AI |

記録する出来事は、次の通りです。迷う場合は、記録します。

- 依存規則と飛ばし禁止の検査が、違反を検出した(開発者またはAIが、近道を取ろうとした)。
- 1つの変更が、構造のために、複数の層やファイルに及んだ(項目を1つ加えるために、詰め替えを何箇所も変えた、など)。
- 変更が、1つの層の中に閉じた。層の境界で、実装を差し替えられた(テストでの差し替えを含む)。
- 境界要素を、加えた、変えた、削った。その理由。
- 置き場所や、規則の解釈に迷った。規則の例外を設けた、または、設けたくなった。
- AIに読ませる範囲や、指示の範囲を、層の単位で絞れた、または、絞れなかった。
- 仮実装(仕様 WS-P1〜WS-P4)を、正式実装に置き換えた。変更が及んだ層と、ファイルの数を、併せて記録する。

### スライスの記録

機能スライスの完了時(動作検証の後)に、次を記録します。

| 項目 | 内容 |
|---|---|
| スライス | スライスの名前 |
| 範囲 | そのスライスの、最初のコミットと、最後のコミット |
| 都度の記録の確認 | そのスライスの間の、都度の記録の番号。1件もない場合は、振り返って、該当する出来事がなかったことを確かめたうえで、「該当なし」と書く |
| 検査の結果 | 依存規則と飛ばし禁止の検査の、違反の件数(完了条件は、0件) |
| 検査の記録との突き合わせ | 検査の記録(「取り漏らしを防ぐ手段」)にある違反が、都度の記録に対応していること。対応する記録がない違反は、この時点で、都度の記録に加える |

スライスの範囲を記録するのは、チェックポイントの計数(変更したファイルの数など)を、後から、リポジトリの履歴で求められるようにするためです。スライスごとの計数は、行いません。

### チェックポイントの記録

仮説が定めるチェックポイントで、次を記録します。数える対象から、生成したコード([ADR-003](ADR-003-api-contract-definition.md)、[ADR-004](ADR-004-data-store.md))と、テストのコードを除きます。サーバーとクライアントは、分けて数えます。

**MVP完了時**

| 計数 | 数え方 |
|---|---|
| 境界要素の数 | ポート(インターフェイス)と、層の境界を越えるためのデータ構造(ユースケースの入力・出力、拒否の種類の定義)を、型の宣言の単位で数える |
| 導入の後、一度も変更されなかった境界要素の数 | その宣言を導入したスライスの完了より後に、その宣言を変更したコミットがないもの。導入したスライスの中での変更は、数えない。チェックポイントの直前のスライスで導入したものは、変更の機会がないため、分けて示す |
| そのうち、抽象として使われなかったものの数 | ポートは、本番用の実装が1つだけのもの。このうち、テストで別の実装に差し替えられたものと、テストでも差し替えられなかったものを、分けて数える。データ構造は、詰め替えの元と、項目が1対1で対応し、変換を伴わないもの |
| パススルーなユースケースメソッドの数 | ユースケースのメソッドのうち、本体が、ポートの1回の呼び出しと、入力・出力の詰め替えだけからなるもの。検証、認可、分岐、複数のポートの呼び出しを含むものは、数えない |
| 検査が検出した違反の数 | 検査の記録(「取り漏らしを防ぐ手段」)にある違反の件数。同じ違反を、直すまでに繰り返し検出した場合は、1件と数える |

仮説の「一度も変更・参照されなかったもの(純粋な携行コスト)」は、上の2番目と3番目で表します。境界要素は、現に存在するユースケースが通過する箇所にだけ置くため(ADR-005)、どこからも参照されない境界要素は、原則として生じません。そこで、「参照されなかった」を、「置いたが、抽象としては働かなかった」と読み替えています。この読み替えは、本ADRの解釈です。仮説の文書にも、その旨を注記します。

数え方について、次の2点を補います。

- 「変更されなかった」を、スライスの完了より後で数えるのは、コミットの粒度によって結果が変わらないようにするためです。導入したスライスの中での変更は、作りながらの手直しであり、携行コストを表しません。スライスの完了は、スライスの記録の「範囲」で定まります。
- ポートの差し替えを、テストと本番用で分けて数えるのは、ポートが、application のテストで、テスト用の実装に差し替えられるためです([ADR-006](ADR-006-automated-testing.md))。分けずに数えると、「抽象として使われなかった」ポートは、ほぼ0件になり、携行コストを表しません。

計数に加えて、都度の記録を、妨げ・助けに分けて振り返り、所見を記録します。飛ばし禁止の携行コストが重いと判断した場合は、新しいADRで、規則を緩めることを検討します(仮説「チェックポイント」)。

**フェーズ2(グループチャットの完了時)**

| 項目 | 数え方 |
|---|---|
| 変更したファイルの数 | グループチャットのスライスの範囲で、変更したファイルを、層ごとに、新規と既存に分けて数える |
| レイヤー横断の漏れ | 機能の追加のために、依存規則・飛ばし禁止の例外を設けた箇所と、層の役割に合わない場所に実装した箇所。有無と、箇所を記録する |
| 構造自体の変更 | ADR-005 の層の構成、規則、型参照の範囲を、新しいADRで変更したかどうか |

**雛形の到達後にブロックを追加する場合**

フェーズ2と同じ項目に加えて、既存の機能のコードを変更した箇所を、機能と層ごとに記録します。ブロックを後から追加しうることを知っていたことが、既存の設計に影響した可能性も、所見に併記します(仮説「チェックポイント」)。

### 取り漏らしを防ぐ手段

- AIに作業を依頼するときの常設の指示に、都度の記録の規則(記録する出来事と項目)を含める。指示の置き場所は、詳細設計で定める。
- 依存規則と飛ばし禁止の検査の手順([ADR-007](ADR-007-local-development-environment.md))は、違反を検出したとき、日時と、検査の出力を、リポジトリが追跡する記録用のファイル(検査の記録)に追記する。AIは、検査の失敗を、作業の中で直してしまうことがあり、自己申告だけでは、違反の件数が残らないためである。規則に違反する見本に対する検査(ADR-005「検査の手段」)は、記録の対象から除く。ファイルの置き場所は、詳細設計で定める。
- スライスの記録の「都度の記録の確認」を、スライスの完了の条件とする(企画書「各マイルストーンに共通の完了条件」5)。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| 観察のたびに、ADRを起こす | 仮説は、ADRへの記録も認めている。ADRは、設計の判断を、1つずつ記録する文書であり、出来事の記録を混ぜると、判断を時系列で追いにくくなる。開発方針も、観察記録を、別の長寿命の文書としている |
| 仮説の文書に、追記する | 仮説は、これも認めている。仮説の本文と、長くなる記録を、1つの文書にすると、仮説の改訂と記録の追記が混ざる |
| スライスごとに、計数も行う | 推移が分かる。計数は、スライスの範囲を記録しておけば、後から、リポジトリの履歴で求められる。後から復元できないのは、出来事の記録だけであり、スライスごとの作業を、そこに絞る |
| 作業の時間や、AIの使用量を、計測する | 総コストの手がかりになる。比較対象がない1件の事例では、値の大小を解釈できない。計測の手間に、見合わない |
| 「変更・参照されなかった」を、文字通り、どこからも参照されないものとして数える | 仮説の文言に、最も近い。ADR-005 の方針では、ほぼ0件になり、携行コストを表さない |

## Consequences

- 都度の記録は、開発の流れを止める手間になる。項目を、後から確かめる手がかりと、事実と解釈の区別に絞っている。
- 「抽象として使われなかった」と「パススルー」の判定には、数える者の判断が入る。判定に迷ったものは、理由とともに、チェックポイントの記録に残す。
- 数え方を変える場合は、新しいADRで定める。変える前の数え方による記録は、書き換えない。
- 本ADRは、実装を伴わない。最初のスライスの記録を行い、運用できることを確かめた時点で、frozen とする。
