# ADR-015 認証に用いる秘密を保管する形

- ステータス: frozen
- 作成日: 2026-11-27
- 対象: 登録とログイン([仕様](../specs/registration-and-login.md)「技術要素の決定」)

## Context

認証に用いる秘密は、パスワードです([ADR-014](ADR-014-authentication-method.md))。本ADRは、秘密を保管する形と、照合の手段を決定します。

選定の条件は、次の通りです(仕様「技術要素の決定」)。

- 保管データが漏えいしても、元の値を、現実的な計算量で復元できない。同じ秘密を持つ2人の利用者の、保管された値は、異なる(SEC-1、RL-34)。
- 上限の長さ(128文字)までの秘密の全体が、照合に働く(RL-12)。秘密は、UTF-8 では、最大で512バイトになる。
- 照合が、想定規模と、開発者の端末で、支障なく行える(PERF-1、RL-40)。
- すべての選定に共通する条件を満たす。

関連する受け入れ基準は、次の通りです。

- ログインの応答にかかる時間に、秘密の照合の計算を行うかどうかによる差を、作らない(RL-13)。
- 秘密を、文字を置き換えずに、入力された通りに扱う(RL-D3)。

## Decision

- 秘密は、Argon2id で計算した値として保管する。パラメータは、メモリ 19MiB(19,456KiB)、反復 2回、並列度 1 とする。OWASP が、最小の構成として挙げる値である。
- ソルトは、保管する値ごとに(登録のたびに。秘密を変えるときも、作り直す)、16バイトを、暗号に使える乱数の生成の手段で作る。出力は、32バイトとする。
- 保管する値は、方式、版、パラメータ、ソルト、出力を、1つの文字列にまとめた形(PHC の文字列の形式)とする。照合は、保管した値が持つパラメータで計算し、出力を、所要時間が内容に依らない比較で比べる。
- 計算には、Go の準標準のライブラリ(golang.org/x/crypto の argon2)を使う。版は、導入の時点で最新のものを、固定する(WS-32)。文字列の形式への変換は、自前で書く。
- 計算に渡すのは、入力された秘密の、UTF-8 のバイト列そのものとする。切り詰めず、正規化せず、事前に別の要約にも通さない。
- 計算は、ポートの背後に置く。domain と application は、外部のライブラリを import できないためである([ADR-005](ADR-005-layer-structure.md))。
- 同時に行う計算の数に、上限を設ける。1回の計算が、19MiB のメモリを使うためである。値は、詳細設計で定める。
- 連絡先が登録されていない場合など、照合する相手がないログインでも、同じパラメータの計算を、1回行う(RL-13)。上限によって、照合を行わずに拒否する場合(仕様「ログインする」)は、除く。
- 出典: OWASP Password Storage Cheat Sheet「Argon2id」。OWASP ASVS 5.0.0 11.4.2(2026-11-27 に確かめた)。

### 選定の条件の確認

所要時間とメモリは、2026-11-27 に、開発者の端末(WSL2。メモリ 4GB、論理プロセッサ 16)で、Go 1.26.8 と golang.org/x/crypto v0.55.0 を使って測りました。同じ日の時点で最新の版(v0.59.0)でも、1回の計算が、同じ程度(約20ミリ秒)であることを確かめました。

| 条件 | 確認 |
|---|---|
| 現実的な計算量で、復元できない(RL-34) | Argon2id は、計算のたびに、定めた量のメモリを要する。秘密の候補を、大量に並列に試す費用が、メモリの量に比例して増える。パラメータは、OWASP が挙げる最小の構成である |
| 同じ秘密の、保管された値が異なる(RL-34) | ソルトを、保管する値ごとに、無作為に作る |
| 上限の長さまでの秘密の全体が、照合に働く(RL-12) | Argon2id は、入力の長さを、実用上、制限しない。512バイトの秘密の全体が、計算に入る |
| 照合が、開発者の端末で、支障なく行える(RL-40) | 1回の計算は、約25ミリ秒であった(15バイトの秘密で、20回の平均。512バイトの秘密でも、差はなかった) |
| 照合が、想定規模で、支障なく行える(PERF-1) | 照合は、ログインのときにだけ行う。操作のたびには、行わない(ADR-014)。同時に16件を計算すると、全体で約0.23秒、プロセスが確保したメモリは約330MiB であった。同時に50件では、約1.4秒、約975MiB であった。想定規模(同時に利用する人数が、数十人程度)で、ログインが同時に重なる数は小さいが、試行を重ねる要求でメモリが膨らまないように、同時に行う計算の数を限る。設置環境のノードでの所要時間は、確かめていない(設置環境を扱うスライスで確かめる) |
| 後続フェーズの妨げにならない | 秘密の変更と再設定(UC-07、UC-04)は、同じ計算と、同じポートを使える |
| 複数サーバー構成への移行を妨げない(PERF-3) | 計算は、状態を持たない。保管する値は、パラメータを含むため、どのサーバーでも照合できる |
| ライセンスが、MITライセンスでの公開と両立する | golang.org/x/crypto(BSD-3-Clause) |
| 個人データとメッセージを、外部のサービスへ送信しない(PRV-3) | 計算は、サーバーの中で行う |
| 検証にかける費用を、小さく抑えられる | 無償で使える |

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| bcrypt | 実績が多く、同じ準標準のライブラリにある。入力の上限が72バイトであり、512バイトまでの秘密の全体を、照合に働かせられない(RL-12)。事前に別の要約に通す形にすると、その扱いの誤り(途中で切れる値など)を、自前で防ぐことになる |
| scrypt | メモリを要する方式であり、条件を満たす。OWASP は、Argon2id を使えない場合の選択としている |
| PBKDF2(HMAC-SHA-256、60万回) | Go の標準ライブラリ(crypto/pbkdf2)にあり、依存物を加えずに済む。メモリを要さないため、大量に並列に試す費用が小さい。OWASP は、FIPS-140 への準拠が要る場合の選択としている。同じ端末で、1回の計算は、約115ミリ秒であった |
| Argon2id の、より重いパラメータ(メモリ 64MiB、反復 3回、並列度 4 など) | 復元の費用が上がる。同じ端末で、1回の計算は、約50ミリ秒であった。1回の計算が使うメモリが、3倍あまりになる。設置環境は、小さなノードを想定しており(企画書「可用性・運用」)、OWASP の最小の構成に留める。保管する値がパラメータを含むため、後から上げられる |
| 利用者に共通の秘密の値(ペッパー)を、計算に加える | 保管データだけが漏えいした場合に、復元を防げる。管理する秘密が1つ増え(SEC-6)、その値を失うと、すべての利用者がログインできなくなる。バックアップからの復元(OPS-5)にも、関わる |
| Argon2 を包むライブラリ(alexedwards/argon2id など)を使う | 文字列の形式への変換を、書かずに済む。変換は、短い処理であり、そのために依存物を加えない([ADR-001](ADR-001-language-and-libraries.md)) |
| パラメータを、設定で変えられるようにする | 運営者が、ノードに合わせて調整できる。現に、変える必要がない。誤った設定で、弱い値が保管されうる |

## Consequences

- 依存物が、1つ加わる(golang.org/x/crypto)。import できるのは、計算を行う adapter のパッケージだけとする。パッケージを加え、依存規則の設定と、アーキテクチャ概要を更新する(詳細設計)。
- 境界要素が、1つ増える(秘密を、保管する形に変え、照合するポート)。application のテストは、このポートを、テスト用の実装に差し替える。サーバーの振る舞いのテストは、実際の計算を通す([ADR-006](ADR-006-automated-testing.md))。
- 登録とログインは、1回につき、約25ミリ秒と、19MiB を要する。サーバーの振る舞いのテストは、利用者の登録とログインのたびに、この計算を行う。開発者の端末のメモリは 4GB であり、並行して実行するテストの数によっては、メモリが不足しうる。同時に行う計算の数の上限は、1つのプロセスの中でしか働かない。テストの所要時間とメモリは、実装の中で確かめる。
- 同時に行う計算の数の上限に達している間、ログインと登録の完了は、順番を待つ。試行を重ねる要求が、他の利用者のログインを遅らせうる。送信元ごとの上限(仕様「上限」)が、これを抑える。
- パラメータを変えた場合、変える前に保管した値は、その値が持つパラメータで、引き続き照合できる。ログインのときに、新しいパラメータで保管し直す仕組みは、作らない。
- 秘密は、要求の本文から、置き換えずに復号して、内側へ渡す。メッセージの本文と同じ扱いである(ADR-001 の Consequences)。「Unicode の文字列として正しい」の判定は、domain が行う。
