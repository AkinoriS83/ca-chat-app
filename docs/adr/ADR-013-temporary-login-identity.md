# ADR-013 仮のログインで、利用者を要求に添える形

- ステータス: active
- 作成日: 2026-11-20
- 対象: ウォーキングスケルトン([仕様](../specs/walking-skeleton.md)「利用者」、WS-P2)

## Context

本スライスのログインは、仮実装です(WS-P2)。利用者は、固定ユーザーから1人を選ぶだけで、ログインした状態になります。認証に用いる秘密は、持ちません。

サーバーは、HTTP の操作のたびに、また、WebSocket の接続を確立する要求の時点で、利用者を特定します([ADR-002](ADR-002-realtime-communication.md))。選ばれた固定ユーザーを、要求にどう添えるかは、次の3点を左右します。

- **第三者のサイトからの操作(WS-29)。** ブラウザが自動で要求に付ける手段(Cookie)を使うと、第三者のサイトのページから送らせた要求にも、利用者が付く。
- **固定ユーザーの選び直し(WS-41)。** 仕様は、選び直すと、その端末の、それまでの固定ユーザーとしてのリアルタイムの接続が終わると定めている。利用者を保持する単位と、接続を持つ単位が食い違うと、選び直した後も、前の利用者としての接続が残る。
- **「端末」の単位。** 仕様は、配信の宛先を「アプリを開いている端末」と定めている。

ブラウザの標準の WebSocket API は、接続を確立する要求に、任意のヘッダーを付けられません。添える手段は、Cookie、接続先のアドレス、サブプロトコルの欄に限られます。

## Decision

- 「端末」は、アプリを開いているブラウザのタブ1つとする。タブは、WebSocket の接続を1本持つ(ADR-002)。同じブラウザの2つのタブは、別の端末として扱う。
- 選ばれた固定ユーザーは、タブが保持する。Cookie など、タブの間で共有され、ブラウザが自動で要求に付ける手段は、使わない。
- クライアントは、HTTP の操作に、固定ユーザーの識別名を、専用の要求ヘッダーで添える。WebSocket の接続を確立する要求には、接続先のアドレスのクエリで添える。
- サーバーは、操作のたびに、また、接続を確立する要求の時点で、添えられた識別名が、固定ユーザーのものであることを確かめる。添えられていない要求と、固定ユーザーでない識別名を添えた要求は、拒否する(WS-16)。
- 固定ユーザーを選び直すとき、クライアントは、WebSocket の接続を閉じ、保持していた会話の内容を捨ててから、新しい固定ユーザーとして、接続を確立し直す。サーバーは、接続を確立した時点の利用者で、配信の宛先を判定するため、閉じた後の端末には、前の利用者の会話のメッセージは届かない(WS-41)。
- 識別名は、ユースケースを呼ぶ adapter が要求から取り出し、ユースケースの入力の「操作を行う利用者」として渡す。固定ユーザーであることは、usecase が、ポートを通して確かめる([ADR-005](ADR-005-layer-structure.md))。

ヘッダーとクエリの名前、タブを再読み込みした後も選択を保つかどうかは、詳細設計で定めます。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| Cookie で添える | クライアントが、何も添えなくてよい。WebSocket の接続を確立する要求にも、自動で付く。採らなかった理由は2つある。(1) Cookie は、同じブラウザのタブの間で共有される。あるタブで選び直すと、別のタブは、HTTP の操作は新しい利用者として行い、WebSocket の接続は前の利用者のまま保つ。これを防ぐには、ログインの状態と接続を対応付けて、サーバーの側から接続を閉じる仕組みが要る。これは、フェーズ1の認証で作るものである。(2) 第三者のサイトのページから送らせた要求にも付くため、WS-29 を、Origin の検証だけで保つことになる。GET には Origin が付かない場合があり(ADR-002)、規則が増える |
| HTTP の操作でも、クエリで添える | 添える手段が、1つに揃う。専用の要求ヘッダーは、第三者のサイトのページから付けようとすると、ブラウザが、事前の確認の要求を送る。サーバーは、他のオリジンに許可を返さないため(ADR-002)、操作の要求は送られない。クエリには、この性質がない |
| WebSocket では、サブプロトコルの欄で添える | 接続先のアドレスに、識別名が現れない。欄の本来の用途ではなく、サーバーが、選んだ値を応答で返す取り決めにも従うことになる。識別名は、秘密ではない |
| WebSocket の接続を確立した後、最初のメッセージで伝える | 接続先のアドレスに、識別名が現れない。接続を確立する要求の時点で利用者を特定する判断と、WebSocket の上で端末から操作を送らない判断(ADR-002)に反する |

## Consequences

- 第三者のサイトからの操作(WS-29)は、次の2つで防ぐ。HTTP の操作は、専用の要求ヘッダーが要るため、第三者のサイトのページからは、Origin が付かない形(画像の読み込みなど)では利用者を添えられず、付く形では Origin の検証で拒否される。WebSocket の接続を確立する要求は、ブラウザが必ず Origin を付けるため、Origin の検証で拒否される(ADR-002)。
- 選ばれた固定ユーザーと、WebSocket の接続は、どちらもタブの単位になり、食い違わない。動作検証は、仕様の通り、互いに状態を共有しない3つのブラウザで行う(WS-D6)。同じブラウザの3つのタブでも、同じ結果になる。
- 識別名は、接続先のアドレスに現れ、開発用のサーバーとサーバーのログに残りうる。固定ユーザーの識別名は、秘密ではない。フェーズ1で扱うログイン状態の資格は、秘密であり、アドレスに載せない(SEC-1)。
- 本ADRは、仮のログイン(WS-P2)とともに、フェーズ1の認証のADRで置き換える。その際、Cookie を採る場合は、次を定める。
  - ログイン状態が無効になったとき、そのログインによるすべての接続を、サーバーの側から閉じるための、ログイン状態と接続の対応付け(R-1、ADR-002)。
  - Origin が付かない GET の扱い(ADR-002)。
- 置き換えは、ユースケースを呼ぶ adapter と、固定ユーザーを確かめるポートの実装に閉じる。ユースケースの入力の「操作を行う利用者」は、変わらない。
