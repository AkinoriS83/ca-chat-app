# ADR-005 層の構成、依存規則と飛ばし禁止の検査、型参照の範囲

- ステータス: active
- 作成日: 2026-11-19
- 対象: ウォーキングスケルトン([仕様](../specs/walking-skeleton.md)「技術要素の決定」)

## Context

本プロジェクトは、Clean Architecture の構造(層の分割、依存規則、呼び出し経路の飛ばし禁止)を、開発の初期から採用します([仮説](../hypothesis.md)「仮説の本体」)。仮説は、次の2点を、仕様・設計フェーズの判断としています。

- 層の具体的な構成。
- 型参照の範囲(内側の型を、どこまで外側に見せるか)。飛ばし禁止は、呼び出し経路についての規則であり、型参照は、別の判断とされている。

選定の条件は、次の通りです(仕様「技術要素の決定」)。

- 仮説「仮説の本体」の構造を満たす。
- 境界要素は、現に存在するユースケースが通過する境界にのみ置く(仮説「適用範囲の限定」)。

関連する完了条件と受け入れ基準は、次の通りです。

- 依存規則と飛ばし禁止への違反が、機械的な検査で0件である(企画書「各マイルストーンに共通の完了条件」3)。
- 接続中の端末と、配信の宛先を保持する状態が、内側の層が定義するインターフェイスの背後に置かれている(PERF-3、WS-35)。

サーバーは Go、クライアントは TypeScript です([ADR-001](ADR-001-language-and-libraries.md))。Go の import は、パッケージの単位です。あるパッケージを import すると、その型を参照することも、その関数を呼ぶこともできます。import の検査では、型の参照と呼び出しを区別できません。この性質が、型参照の範囲の決め方を制約します。

本ADRでは、次の用語を使います。

| 用語 | 意味 |
|---|---|
| ポート | 内側の層が定義し、外側の層が実装するインターフェイス |
| 境界要素 | ポートと、層の境界を越えるためのデータ構造 |

## Decision

### サーバーの層

| 層 | 書籍での呼び名 | 置き場所 | 置くもの |
|---|---|---|---|
| domain | Enterprise Business Rules(Entities) | `server/internal/domain` | 利用者、会話、メッセージと、その規則(本文の規則〈WS-D3〉、参加関係の判定など) |
| application | Application Business Rules(Use Cases) | `server/internal/application/usecase`、`server/internal/application/port` | ユースケースと、その入力・出力のデータ構造(usecase)。ポート(port) |
| adapter | Interface Adapters | `server/internal/adapter/` の下の、外部の相手ごとのパッケージ | 外部の形式と、ユースケースの形式の間の変換。HTTP の操作を受けるもの、WebSocket の接続と配信を扱うもの、保管先へ問い合わせるもの |
| main | Frameworks and Drivers(Main) | `server/cmd/server` | 設定の読み込み、各層の組み立て、サーバーの起動 |

### サーバーの依存の規則

依存規則と飛ばし禁止は、パッケージごとの「import してよい先」として定めます。標準ライブラリは、下の表とは別に扱います。

| パッケージ | import してよい先 |
|---|---|
| domain | なし |
| application/port | domain |
| application/usecase | application/port、domain |
| adapter(ユースケースを呼ぶもの。HTTP の操作) | application/usecase |
| adapter(ポートを実装するもの。保管先) | application/port、domain |
| adapter(両方を行うもの。WebSocket) | application/usecase、application/port、domain |
| main | すべて |

- adapter のパッケージ同士は、import しない。
- domain と application は、外部のライブラリと、入出力を行う標準ライブラリのパッケージ(net/http、database/sql など)を、import しない。
- 各 adapter は、自分が受け持つ外部の相手のためのライブラリ(生成した通信の形式の型、WebSocket、保管先のドライバーなど)だけを、import する。
- 規則は、パッケージごとに、import してよい先を列挙する形で設定する。列挙にない import は、違反とする。パッケージを加えるときは、規則を加える。
- main は、組み立てだけを行う。adapter には、そのパッケージが import してよい層のものだけを渡す(HTTP の操作を受ける adapter には、ユースケースだけを渡す)。

この規則により、HTTP の操作を受ける adapter は、ポート、domain、他の adapter を import できません。仮説が例に挙げる「ハンドラーが、ユースケースを経由せずに、リポジトリに到達する」経路は、import の違反として検出されます。application を usecase と port の2つのパッケージに分けるのは、この検出のためです。

### 型参照の範囲

| 境界 | 越えるデータの型 |
|---|---|
| ユースケースを呼ぶ境界(adapter → usecase) | 入力と出力のどちらも、usecase が定義する、ユースケースごとの専用のデータ構造とする。domain の型を含めない。入力には、操作を行う利用者を含める |
| ポートの境界(usecase → port ← adapter) | domain の型を、そのまま使う。専用のデータ構造は置かない |
| システムの外との境界 | 通信の形式([ADR-003](ADR-003-api-contract-definition.md))と、保管先の表現([ADR-004](ADR-004-data-store.md))は、内側の型とは別の型とし、adapter の中で詰め替える |

- ユースケースを呼ぶ境界に専用のデータ構造を置くのは、ユースケースを呼ぶ adapter に、domain の import を許さないためである。許すと、domain の規則を adapter から直接呼ぶ経路(application の飛ばし)を、import の検査で検出できなくなる。
- ポートの境界に専用のデータ構造を置かないのは、すべての境界での詰め替えを避けるためである(仮説「仮説の本体」)。ポートを実装する adapter は、ポートが受け渡す domain の型を扱うため、domain を import する。
- ポートを実装する adapter が domain を使うのは、型の受け渡しと、保管先の表現からの組み立てに限る。domain の規則(検証、判定)は、adapter から呼ばない。この区別は、import の検査では検出できないため、規約とし、レビューで確かめる。
- ユースケースを呼ぶ側には、インターフェイスを置かない。adapter は、usecase の具体的な型を呼ぶ。依存の向きが、既に外側から内側であり、向きを逆にするためのインターフェイスが要らないためである。

### クライアントの層

クライアントにも、同じ考え方の層を置きます。クライアントは、送信の状態の遷移(完了、拒否、送信できなかった、送り直し)や、履歴と配信の統合といった振る舞いを持ち、これを画面の部品と通信から分けるためです。

| 層 | 置き場所 | 置くもの |
|---|---|---|
| application | `client/src/application`、`client/src/application/port` | クライアントの振る舞いと状態(会話の表示内容、送信の状態の遷移など)。ポート(サーバーとの通信、時間の経過など)。React と、ブラウザの入出力のAPIを使わない |
| adapter | `client/src/adapter` | ポートの実装。通信の形式(ADR-003)と、application の型の間の変換 |
| ui | `client/src/ui` | React の部品。application の状態を表示し、利用者の操作を application に伝える |
| main | `client/src/main.tsx` | 組み立てと、起動 |

| 置き場所 | import してよい先 |
|---|---|
| application(port を含む) | application の中だけ |
| adapter | application/port と、そこから参照される application の型 |
| ui | application(port を除く) |
| main | すべて |

- domain の層は、置かない。業務の規則は、サーバーが持つ。クライアントに置くものが現れた時点で、加える。
- ui と adapter は、互いに import しない。画面の部品が、application を経由せずに通信する経路は、import の違反として検出される。

### 検査の手段

- サーバーは、golangci-lint の depguard で検査する。パッケージごとの規則を、設定に宣言する。
- クライアントは、dependency-cruiser で検査する。application が、ブラウザの入出力のAPI(fetch、WebSocket など)を使わないことは、ESLint の規則で検査する。
- 規則に違反する見本に対して、検査が失敗することを確かめる手段を用意する。設定の誤りによって、検査が常に成功する状態を防ぐためである。
- 検査は、ローカルの開発環境で、1つの手順で実行できるようにする([ADR-007](ADR-007-local-development-environment.md))。
- 現在のパッケージと規則の一覧は、アーキテクチャ概要に記載し、設定と一致させる。

### 境界要素を置く範囲

ポートと、ユースケースの入力・出力のデータ構造は、本スライスのユースケース(メッセージを送る、会話の履歴を読む、リアルタイムの接続を受け付ける)が通過するものだけを置きます。後続のスライスのためのポートやデータ構造は、先行して作りません。

接続中の端末と、配信の宛先を保持する状態は、WebSocket を扱う adapter の中に置き、application/port が定義する配信のポートの背後とします(PERF-3、WS-35)。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| adapter を、ライブラリに依存しない層と、依存する層に分ける | 書籍の4つの層に、より厳密に対応する。採らなかったのは、HTTP は標準ライブラリで扱い、通信の形式と保管先の表現は、生成したコードが受け持つためである。層を分けると、その間に境界要素が増えるが、差し替えたいライブラリが現にない |
| application を、1つのパッケージにする | パッケージが減る。ポートが、ユースケースを呼ぶ adapter から見えるようになり、ユースケースを経由せずにポートを使う経路を、import の検査で検出できない |
| ユースケースの出力に、domain の型をそのまま返す | 出力の詰め替えが要らない。Go では、型の参照のための import と、呼び出しのための import を区別できないため、adapter から domain への飛ばしを、機械的に検出できなくなる。また、domain の型に加えた項目が、意図せず、通信の形式へ向かう経路に乗る |
| ポートの境界にも、専用のデータ構造を置く | 規則が一様になり、adapter は、どれも domain を import しなくなる。すべての境界で詰め替えが要るようになり、仮説が避けるとした形になる |
| ユースケースを呼ぶ側にも、インターフェイスを置く | 書籍の図(Input Boundary)に対応する。依存の向きを変えないインターフェイスであり、境界要素を、必要な箇所にだけ置く方針(仮説「適用範囲の限定」)に合わない |
| サーバーの検査に、別の道具(go-arch-lint など)を使う | 層と依存を、宣言的に書ける。depguard は、静的解析に使う golangci-lint に含まれ、道具が増えない |
| クライアントに、層を置かない | 仮説の層構造の例(ハンドラー、ユースケース、リポジトリ)は、サーバーのものである。クライアントにも、画面の部品から直接通信するという近道があり、テストで確かめる振る舞い(WS-17、WS-22、WS-40)がある。分けておく |
| クライアントの検査を、ESLint だけで行う | 道具が1つ減る。import の文字列に対する規則になり、相対パスの書き方によって、検出が漏れる。dependency-cruiser は、解決した後のファイルに対して規則を適用する |

## Consequences

- ユースケースの出力は、domain の型 → 出力のデータ構造 → 通信の形式と、2回詰め替えることになる。この携行コストは、観察記録の対象とする([ADR-008](ADR-008-observation-records.md))。
- ポートを呼ぶだけのユースケースが生じうる(リアルタイムの接続の受け付けなど)。数は、仮説のチェックポイントで数える(ADR-008)。
- Go のインターフェイスは、import なしに満たせる。adapter が自分でインターフェイスを定義し、main が別の adapter を渡せば、import を伴わずに、層を飛ばす経路を作れる。import の検査では検出できないため、main の組み立ての規則(「サーバーの依存の規則」)を、レビューで確かめる。
- 仮実装(WS-P1、WS-P2)は、正式実装への置き換えが外側の層に閉じるように、ポートの実装と adapter に置く。置き場所は、詳細設計で定める。
- 検査の道具のライセンスは、golangci-lint が GPL-3.0、dependency-cruiser が MIT である。どちらも、開発の時点で実行する道具であり、成果物に含まれない。
- フェーズ1以降で機能が増えたとき、層の中を機能ごとに分けるかどうかは、その時点で判断する。
