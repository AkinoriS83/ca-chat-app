# ADR-004 保管先

- ステータス: active
- 作成日: 2026-11-19
- 対象: ウォーキングスケルトン([仕様](../specs/walking-skeleton.md)「技術要素の決定」)

## Context

ウォーキングスケルトンは、メッセージを、仮実装ではなく、正式な保管先に保管します(仕様 WS-D1)。本ADRは、保管先と、サーバーから保管先へアクセスする手段を決定します。

選定の条件は、次の通りです(仕様「技術要素の決定」)。

- 完了を示したメッセージが失われない(OPS-2)。
- 分割しての取得(PERF-2)、バックアップと復元(OPS-5)、複数のサーバーからの共有(PERF-3)を妨げない。
- 保管先が出力するログに、メッセージの本文を記録しない構成にできる(PRV-4)。
- すべての選定に共通する条件を満たす。

機能仕様は、保管先に、次の性質も求めます。

- 同じ2人の間の1on1会話は、1つだけである。2人がほぼ同時に最初のメッセージを送っても、会話は1つである(WS-05)。
- 会話の成立と、最初のメッセージの保管は、どちらか一方だけが行われることがない。
- 同じ送信者の、同じ送信の識別子のメッセージは、同時に受けた場合も、1通だけ保管される(WS-18)。
- 会話の中のメッセージに、すべての参加者に共通の順序を与える(WS-07)。

## Decision

- 保管先は、PostgreSQL とする。版は、着手の時点でサポートされているメジャー版とし、ローカルの開発環境の定義で固定する([ADR-007](ADR-007-local-development-environment.md))。
- サーバーからのアクセスには、pgx を使う。問い合わせは、SQL で書き、sqlc で、型の付いた Go のコードを生成する。ORM は使わない。
- 保管先の構造の変更(マイグレーション)は、連番を付けた SQL のファイルとして、リポジトリで管理し、goose で適用する。
- 会話の一意性と、送信の識別子の一意性は、保管先の制約で保つ。会話の成立とメッセージの保管は、1つのトランザクションで行う。
- サーバーは、保管のトランザクションが確定した後に、完了の応答を返し、配信する(OPS-2、WS-31)。
- 保管先のログは、下記「ログに本文を記録しない構成」の通りに設定する。

### 選定の条件の確認

| 条件 | 確認 |
|---|---|
| 完了を示したメッセージが失われない(OPS-2) | PostgreSQL は、確定したトランザクションを、ログ先行書き込みによって、異常終了の後も保つ(既定の設定のままとする)。完了の応答は、確定の後に返す |
| 分割しての取得を妨げない(PERF-2) | 会話と順序による索引を使い、指定した位置から一定の件数だけを取得できる。本スライスでは、一括で取得する(WS-P4) |
| バックアップと復元を妨げない(OPS-5) | 標準の道具で、取得と復元ができる。手順は、フェーズ1で定める |
| 複数のサーバーからの共有を妨げない(PERF-3) | サーバーとは別のプロセスとして動き、複数のサーバーから接続できる。会話の一意性、送信の識別子の一意性、メッセージの順序は、保管先の制約とトランザクションで保つため、サーバーが複数になっても成り立つ |
| 保管先のログに、本文を記録しない構成にできる(PRV-4) | 下記「ログに本文を記録しない構成」 |
| ライセンスが、MITライセンスでの公開と両立する | PostgreSQL(PostgreSQL License)、pgx、sqlc、goose(MIT) |
| 個人データとメッセージを、外部のサービスへ送信しない(PRV-3) | 自らの環境の中で動かす。外部のサービスを使わない |
| 検証にかける費用を、小さく抑えられる | 無償で使え、開発者の端末の上で動く |

### ログに本文を記録しない構成

- 本文は、問い合わせの文に埋め込まず、常にパラメータとして渡す。sqlc が生成するコードは、この形に限られる。
- 問い合わせの文の記録(log_statement、log_min_duration_statement)は、無効(既定)のままとする。調査のために有効にする場合は、パラメータの値を記録しない設定(log_parameter_max_length = 0)を併せて行う。
- エラーの記録に、パラメータの値を含めない(log_parameter_max_length_on_error = 0。既定)。
- エラーの記録に、詳細(DETAIL)を含めない(log_error_verbosity = terse)。制約に違反したときの詳細には、その行の内容が含まれることがあるためである。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| SQLite | サーバーと同じプロセスで動き、設置が最も簡素である。保管先がサーバーのノードに閉じるため、複数のサーバーから共有できず、PERF-3 を妨げる |
| MySQL / MariaDB | 条件は満たせる。PostgreSQL を選んだのは、フェーズ2のメッセージ検索で使える機能と拡張の選択肢が多く、サーバーの間の通知の機能(ADR-002「複数サーバー構成への移行」の候補)を備えるためである |
| クラウドが提供するキーバリュー型の保管先(DynamoDB など) | 運用の手間は小さい。ローカルの開発環境で動かすには模擬の仕組みが要り、設置環境が特定のサービスに固定される。会話の成立とメッセージの保管の一体性、複数の一意性を、条件付きの書き込みで組み立てることになる |
| ドキュメント型の保管先(MongoDB など) | 条件は満たせる。本プロジェクトのデータは、利用者、会話、参加関係、メッセージの間の関係と制約が中心であり、関係型の保管先が合う |
| ORM(GORM、ent など)を使う | 問い合わせを書く量が減る。ORM が定める型が、エンティティの代わりになりやすく、保管先の表現と内側の型を分けにくい。実行される問い合わせも、見えにくくなる |
| pgx だけを使い、結果の詰め替えを手で書く | 道具が1つ減る。問い合わせと Go の型の対応を、手で保つことになる |
| マイグレーションに、他の道具(golang-migrate など)を使う | 同等の候補である。goose は、SQL のファイルをそのまま適用でき、足りる |

## Consequences

- サーバーのテストは、保管先の制約とトランザクションに依る振る舞い(WS-05、WS-07、WS-18)を確かめるため、実際の PostgreSQL を使う([ADR-006](ADR-006-automated-testing.md))。
- sqlc が生成する型は、保管先の表現(行)である。エンティティとは別の型として、保管先を扱う層の中で詰め替える([ADR-005](ADR-005-layer-structure.md))。生成したコードは、リポジトリに含め、生成し直した結果との一致を検査する([ADR-003](ADR-003-api-contract-definition.md) と同じ扱い)。
- 問い合わせの文は、ビルドの時点で固定され、本文は、パラメータとしてだけ渡る。本文が、問い合わせの一部として解釈されることはない(WS-28)。
- サーバーは、保管先が返したエラーの詳細を、アプリケーションのログに出力しない。詳細には、行の内容が含まれることがあるためである(WS-33)。
- PostgreSQL の文字列は、U+0000 を保管できない。仕様は、制御文字を含む本文を拒否するため(WS-D3)、正しい本文は、すべて保管できる。
- メッセージの順序の与え方は [ADR-010](ADR-010-message-ordering.md) で、送信の識別子の一致の判定は [ADR-009](ADR-009-send-identifier.md) で定める。
- AWS上での配置(保管先を、サーバーと同じノードで動かすか、管理されたサービスを使うか)と、保管データの保護(SEC-8)は、フェーズ1の仕様で定める。
