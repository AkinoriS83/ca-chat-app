# ADR-009 送信の識別子の形式と、一致の判定

- ステータス: frozen
- 作成日: 2026-11-19
- 対象: ウォーキングスケルトン([仕様](../specs/walking-skeleton.md) WS-D2、「後続に送る事項」)

## Context

仕様は、送り直しによる重複を、送信の識別子によって防ぐと定めています(WS-D2)。クライアントは、送信の操作ごとに識別子を作り、送り直しには、同じ識別子を使います。サーバーは、同じ送信者から、保管済みのメッセージと同じ識別子の送信を受けた場合、新しいメッセージを保管せず、完了を示します。

仕様は、識別子の形式を、設計で定めるとしています。本ADRは、形式と、一致を判定する手段を決定します。

仕様が定めている条件は、次の通りです。

- 一致は、送信者ごとに判定する。判定に、本文を用いない。判定に、期限を設けない。
- 識別子は、メッセージとともに保管する。
- 同じ識別子の送信を同時に受けた場合も、保管されるのは1通である(WS-18)。
- 形式が正しくない識別子を添えた送信は、拒否する(WS-13)。拒否の順序は、本文の検証の後である(仕様「メッセージを送る」の拒否の表)。
- 一致は、入力の検証と、相手・会話の確認の後に判定する。保管済みのメッセージが、指定した会話とは別の会話のものである場合は、拒否する(WS-39)。

保管先は PostgreSQL です([ADR-004](ADR-004-data-store.md))。クライアントは、ブラウザで動きます。

## Decision

- 送信の識別子は、UUID とする。通信の上では、36文字の文字列(16進数の8桁-4桁-4桁-4桁-12桁)で表す。
- クライアントは、ブラウザの標準のAPI(crypto.randomUUID)で、識別子を作る。
- サーバーは、上の文字列の形であることだけを検証する。16進数の大文字と小文字は、区別しない。UUID の版は、問わない。
- サーバーは、識別子を、メッセージとともに、保管先の UUID の型で保管する。一致は、値(128ビット)の一致で判定する。
- 保管先に、送信者と識別子の組の一意性の制約を置く。一致の判定は、この制約によって行う。保管を試み、制約に当たった場合は、そのトランザクションを取り消す。併せて行った、会話の成立と、連番の割り当て([ADR-010](ADR-010-message-ordering.md))も、取り消される。その後に、保管済みのメッセージを取得する(手順と、握る層は、[ADR-012](ADR-012-transaction-boundary.md))。
  - 保管済みのメッセージが、指定した会話のものである場合、新しいメッセージを保管せず、配信せず、保管済みのメッセージについて、完了を示す。
  - 別の会話のものである場合、入力が正しくないことを示して、拒否する。
- 形式の検証は、内側の層で、本文の検証の後に行う。通信の形式の上では、識別子は、制約のない文字列とする([ADR-003](ADR-003-api-contract-definition.md))。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| 時刻の順に並ぶ識別子(UUID の版7、ULID など) | 保管先の索引の効率がよい。想定規模では、差が現れない。ブラウザの標準のAPIでは作れず、クライアントに依存物が加わる。サーバーは版を問わないため、後から、クライアントの作り方だけを変えられる |
| 形式を定めない文字列(長さの上限だけを設ける) | クライアントの自由度が高い。長さと使える文字の規則を、独自に定めることになり、保管先でも、文字列として持つことになる |
| 端末ごとの連番 | 小さく、単純である。同じ利用者の別の端末や、開き直した後の同じ端末と、衝突する。衝突すると、別の送信が、送り直しとして扱われ、失われる |
| サーバーが、送信の前に識別子を発行する | サーバーが、形式と一意性を保証できる。送信のたびに、要求が1回増える。発行の要求にも、応答が届かない場合の扱いが要る |
| UUID の版を、乱数によるもの(版4)に限って受け付ける | 推測できない値に限れる。一致は、送信者ごとに判定するため(WS-D2)、他の利用者が識別子を推測しても、得られるものがない。限る理由がない |
| 一致を、保管の前の検索で判定する | 制約に当たった後の処理が要らない。同時に受けた2つの送信が、どちらも「保管済みでない」と判定し、2通を保管しうる(WS-18)。一意性の制約は、いずれにしても要る |

## Consequences

- 一意性は、保管先の制約で保つため、同時に受けた場合も、サーバーが複数になった場合も、成り立つ(WS-18、PERF-3)。
- 悪意のあるクライアントは、任意の識別子を送れる。影響は、その送信者自身のメッセージに限られる。応答として得られるのは、その送信者自身が保管したメッセージだけである(AC-2)。
- 送信の識別子は、配信するメッセージに含まれ、会話の相手の端末にも伝わる([ADR-011](ADR-011-sender-device-delivery.md))。一致は、送信者ごとに判定するため、相手が識別子を知っても、得られるものがない。
- 乱数による識別子が、同じ送信者の中で偶然に一致する確率は、無視できる。一致した場合、後の送信は、送り直しとして扱われる。
- クライアントは、送信できなかったメッセージとともに、その識別子を保ち、送り直しに使う。拒否の後の送信には、新しい識別子を作る(仕様「メッセージを送る」)。
- crypto.randomUUID は、保護された文脈でだけ使える。ローカルの開発環境(localhost)と、暗号化した経路(SEC-2。フェーズ1から)は、これに当たる([ADR-007](ADR-007-local-development-environment.md))。
- 判定に期限を設けないため、識別子と、その索引は、メッセージがある限り、保管し続ける。1通あたりの増加は、小さい。
