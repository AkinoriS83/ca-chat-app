# ADR-019 ログイン状態を確かめる層と、ユースケースに渡す形

- ステータス: frozen
- 作成日: 2026-11-27
- 対象: 登録とログイン([仕様](../specs/registration-and-login.md)「ログイン状態」、RL-15、RL-23)。[ADR-013](ADR-013-temporary-login-identity.md) の Consequences の見込みを、改める

## Context

[ADR-014](ADR-014-authentication-method.md) は、認証の方式を決定しました。操作には、ログイン状態を示す資格(Cookie)と、ログイン状態の識別子(専用の要求ヘッダー、または、クエリ)が添えられます。本ADRは、ログイン状態が有効であることを、どの層が確かめるかと、資格と識別子を、ユースケースに渡す形を決定します。この判断は、資格の形と添え方には依らないため、ADR-014 と分けて記録します。

これまでの定めは、次の通りです。

- ユースケースの入力には、操作を行う利用者を含める([ADR-005](ADR-005-layer-structure.md)「型参照の範囲」)。
- 仮のログインでは、ユースケースを呼ぶ adapter が、識別名を要求から取り出し、ユースケースの入力の「操作を行う利用者」として渡す。固定ユーザーであることは、usecase が、ポートを通して確かめる(ADR-013)。
- ADR-013 は、フェーズ1の認証への置き換えが、ユースケースを呼ぶ adapter と、ポートの実装に閉じ、この入力は変わらないと見込んでいた。

仕様が求めることは、次の通りです。

- ログイン状態の確認は、ほかの検証と認可より先に行う(仕様「ログイン状態」)。
- 拒否の応答は、理由を区別しない(RL-15)。
- ログイン状態の確認を完了できなかった操作は、受け付けない(RL-23)。
- 資格を、ログと、拒否とエラーの応答に含めない(SEC-1、RL-33)。

判断に関わる、層の規則は、次の通りです(ADR-005、[アーキテクチャ概要](../architecture.md))。

- ユースケースを呼ぶ adapter は、application/port と domain を import できない。標準ライブラリは、import できる。
- domain と application が import できる標準ライブラリは、入出力を行わないものとして、設定に列挙したものに限る。乱数(crypto/rand)と、要約の計算(crypto/sha256)は、列挙にない。
- adapter のパッケージ同士は、import しない。

仮のログインの識別名と異なり、資格は、秘密です。確かめる層と、渡す形によって、既存のユースケースの入力の変わり方、資格が通る範囲、境界要素の数が変わります。

## Decision

- ログイン状態が有効であることは、usecase が、操作のたびに、ポートを通して確かめる。adapter の中では、判定しない。ADR-005 と、ADR-013 が固定ユーザーの確認について定めた分担を、保つ。
- ユースケースを呼ぶ adapter は、資格と、ログイン状態の識別子を、要求から取り出し、ユースケースの入力の「操作を行う利用者」として、そのまま渡す。添えられていない要求も、同じく渡し、usecase が拒否する。
- 確認は、各ユースケースの最初の手順とし、ほかの検証と認可より先に行う。対象は、登録、ログイン、「現在のログイン状態を確かめる」を除く、すべてのユースケースである(ADR-014)。確認の手順を、usecase の中でまとめる形は、詳細設計で定める。
- 資格の生成は、ポートの背後に置く。application は、乱数の標準ライブラリを import できず、テストでは、資格の値を差し替えるためである。
- 資格の要約の計算も、ポートの背後に置く。資格を作るポートが受け持つか、ログイン状態を保持するポート([ADR-016](ADR-016-login-state-and-counter-stores.md))の実装の中の、実現の手段とするかは、詳細設計で定める。後者は、[ADR-012](ADR-012-transaction-boundary.md) が、行のロックと一意性の制約を、adapter の中の実現の手段としたことと、同じ考え方である。
- application は、資格を、次のほかには、使わない(詳細設計のレビュー〈2026-11-27〉で、改めた。それまでは、「確認のポートに渡すほかには、使わない。ユースケースの出力と、エラーに、資格を含めない」としていた)。
  - 要求に添えられた資格は、ログイン状態と、登録の申し込みを保持するポート(ADR-016)に渡す(確かめる、無効にする、使用済みにする)。ユースケースの出力には、含めない。
  - 新しく作った資格は、同じポートに渡して、保持させる。ログイン状態を示す資格は、ログインのユースケースの出力に含め、adapter が、Cookie にだけ載せる(ADR-014)。確認のための資格は、案内を送るポート([ADR-018](ADR-018-local-notice-delivery.md))に渡す。
  - どの資格も、拒否とエラー、出来事の記録に、含めない。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| ログイン状態の確認を、専用のユースケースにまとめ、adapter が先に呼んで、特定した利用者を、各ユースケースの入力に渡す | 既存のユースケースの入力が、変わらない(ADR-013 の見込みの通りになる)。各ユースケースは、渡された利用者を信じることになり、確認を経ない呼び出しを、拒否できない。確認が行われることが、adapter の呼び出しの順に依る |
| 上の形で、確認のユースケースが返す値を、usecase の外からは作れない型にし、各ユースケースの入力は、その型で受ける | 確認を経ない呼び出しを、型で防げる。入力が、認証の方式に依らなくなり、今回の後は変わらない。保管先への照会は、要求につき1回で済む。採らなかった理由は2つある。(1) Go では、外のパッケージからも、型のゼロ値は作れる。各ユースケースが、ゼロ値を拒否する検査を持つことになり、型だけでは防げない。(2) 確認と操作が、別の呼び出しになり、usecase が操作のたびに確かめる分担(ADR-005、ADR-013)を変える。確認から操作までの間に無効になったログイン状態を、操作の側では確かめない |
| ユースケースを呼ぶ adapter が、資格の要約を計算し、要約を入力に渡す | 資格そのものが、application に入らない。要約のためのポートの操作が、要らない。要約の計算が、HTTP の操作を受ける adapter、接続を受け付ける adapter、資格を作る adapter の3箇所に分かれる。adapter 同士は import できないため、共有できず、食い違いは、サーバーの振る舞いのテストでしか検出できない(ADR-005 の Consequences が挙げた、通信の形式への変換と、同じ形の携行コストである)。application は、ログと書式の標準ライブラリを import できず、資格が漏れる経路は、限られる |
| 要約の計算(crypto/sha256)を、application が import してよい先に加える | 入出力を行わない計算であり、ADR-005 の規則には反しない。要約のためのポートの操作が、要らない。設定の列挙を、広げることになる。資格の生成には、いずれにしてもポートが要り、ポートの数は減らない。要約を、保管先を扱う adapter の中の、実現の手段とすれば、列挙を変えずに、同じ効果が得られる |

## Consequences

- ユースケースの入力の「操作を行う利用者」が、変わる。仮のログインでは、識別名であった。本ADRでは、資格と、ログイン状態の識別子になる。既存の3つのユースケース(メッセージを送る、会話の履歴を読む、リアルタイムの接続を受け付ける)の入力と、利用者を確かめる手順が変わる。ADR-013 と、[仮実装の箇所の一覧](../temporary-implementations.md)の見込みとは、異なる。観察記録に残す(OBS-020、OBS-021)。
- 資格そのものが、ユースケースの入力として、application を通る。application は、ログと書式の標準ライブラリを import できないため、出力の経路は限られる。Decision が定めたほかの出力と、エラーに含めないことは、import の検査では検出できない。規約とし、レビューと、RL-33 の自動テストで確かめる。実装のときに、置き場所ごとの指示(`.claude/rules/server.md`)に加える。
- 確認の手順を持たないユースケースは、認証なしに、操作を受け付ける。これも、検査では検出できない。RL-15 の自動テストを、すべての操作に対して行う。
- ユースケースが増えるたびに、確認の手順が加わる。繰り返しが妨げになった場合は、代替案の2つ目を、新しいADRで見直す。
- 境界要素が増える見込みである(資格を作るポート。ログイン状態を保持するポートは、ADR-016)。application のテストは、これらを、テスト用の実装に差し替える。形は、詳細設計で定め、観察記録の計数の対象とする([ADR-008](ADR-008-observation-records.md))。
