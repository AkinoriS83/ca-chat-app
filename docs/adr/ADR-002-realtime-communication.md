# ADR-002 リアルタイムの通信方式

- ステータス: active
- 作成日: 2026-11-19
- 対象: ウォーキングスケルトン([仕様](../specs/walking-skeleton.md)「技術要素の決定」)

## Context

ウォーキングスケルトンは、保管したメッセージを、アプリを開いている参加者の端末へ、即時に届けます(仕様「リアルタイムの配信」)。本ADRは、そのための通信方式を決定します。あわせて、クライアントからの操作(送信、履歴の取得)を、どの経路で行うかを決定します。配信の経路と操作の経路を同じにするかどうかで、通信方式に求めるものが変わるためです。

選定の条件は、次の通りです(仕様「技術要素の決定」)。

- サーバーからブラウザへ、操作なしに届けられる。
- 接続ごとに利用者を特定し、宛先を絞れる(AC-6)。
- 第三者のサイトからの接続を拒否できる(WS-29)。
- 経路を暗号化できる(SEC-2)。
- 複数サーバー構成へ移行できる(PERF-3)。
- すべての選定に共通する条件を満たす。

サーバーは Go、クライアントはブラウザで動く TypeScript です([ADR-001](ADR-001-language-and-libraries.md))。

## Decision

- サーバーから端末への配信には、WebSocket を使う。端末は、利用者がアプリを開いている間、サーバーとの間に1本の接続を保つ。
- クライアントからの操作(メッセージの送信、履歴の取得など)は、HTTP の要求と応答で行う。本文は JSON とする。本スライスでは、WebSocket の上で、端末から操作を送らない。
- サーバーの WebSocket の実装には、coder/websocket を使う。クライアントは、ブラウザの標準の WebSocket API を使う。
- サーバーは、接続を確立する要求の時点で、利用者を特定する。特定できない要求は、接続を確立せずに拒否する(WS-16)。
- サーバーは、HTTP の操作と、WebSocket の接続を確立する要求の両方で、Origin ヘッダーを検証する。Origin があり、設定で与えたアプリのオリジンと一致しない要求を、拒否する。他のオリジンに対して、CORS の許可を返さない(WS-29)。
- Origin がない要求は、この検証では拒否しない。ブラウザは、同一オリジンの GET に、Origin を付けないためである。ブラウザは、WebSocket の接続を確立する要求と、GET と HEAD を除く要求には、Origin を付ける。Origin が付かない GET と HEAD は、第三者のサイトのページからも、画像の読み込みなどの形で送れる。この要求によって、第三者のサイトが利用者として操作できないことは、利用者を要求に添える形([ADR-013](ADR-013-temporary-login-identity.md))で保つ。
- 接続中の端末と、配信の宛先を保持する状態は、内側の層が定義するインターフェイスの背後に置く(PERF-3、WS-35。層の構成は [ADR-005](ADR-005-layer-structure.md))。
- 本スライスでは、接続が切れても、再接続しない(UC-13 は対象外)。受信を再開するには、利用者がアプリを開き直す。

通信の形式(HTTP の要求と応答、WebSocket で届けるメッセージ)の定義は、[ADR-003](ADR-003-api-contract-definition.md) で定めます。仮のログイン(WS-P2)で、利用者を要求に添える形と、「端末」の単位は、[ADR-013](ADR-013-temporary-login-identity.md) で定めます。

### 選定の条件の確認

| 条件 | 確認 |
|---|---|
| サーバーからブラウザへ、操作なしに届けられる | WebSocket は、確立した接続の上で、サーバーから任意の時点で送れる |
| 接続ごとに利用者を特定し、宛先を絞れる(AC-6) | 接続を確立する要求は、HTTP の要求である。その時点で利用者を特定し、接続に結び付ける。宛先は、配信のたびに、サーバーの側で判定する。フェーズ1では、要求に付くログイン状態の資格で特定する(方式は、認証のADRで定める)。ログイン状態が無効になった端末の接続は、サーバーの側から閉じられる(R-1、R-4) |
| 第三者のサイトからの接続を拒否できる(WS-29) | WebSocket の接続を確立する要求には、ブラウザの同一オリジンの制限が働かない。そのため、サーバーが Origin ヘッダーを検証して拒否する。ブラウザは、この要求に、必ず Origin を付ける。coder/websocket は、既定で、他のオリジンからの要求を拒否し、許可するオリジンを設定できる |
| 経路を暗号化できる(SEC-2) | WebSocket は、TLS の上で使える(wss)。HTTP の操作も同じである。暗号化の構成は、フェーズ1で定める |
| 複数サーバー構成へ移行できる(PERF-3) | 下記「複数サーバー構成への移行」 |
| ライセンスが、MITライセンスでの公開と両立する | coder/websocket(ISC) |
| 個人データとメッセージを、外部のサービスへ送信しない(PRV-3) | 端末とサーバーが、直接に通信する。外部の配信のサービスを使わない |

### 複数サーバー構成への移行

本スライスは、単一のサーバーで動かし、次の仕組みは作りません。移行を妨げないことだけを確認します。

- 接続は、それを受けたサーバーが保持する。複数サーバー構成では、あるサーバーが保管したメッセージを、他のサーバーが保持する接続へ届けるために、サーバーの間でメッセージを中継する仕組み(保管先の通知の機能や、別の中継の仕組み)が要る。この仕組みは、配信のインターフェイスの実装として加えられ、内側の層を変えない。
- 操作は HTTP で行い、サーバーは、操作の間に、端末ごとの状態を保持しない。操作の要求と、同じ端末の WebSocket の接続が、別のサーバーに届いてもよい。
- 接続を特定のサーバーに固定する仕組みは、要らない。負荷分散の装置は、WebSocket を中継できるものを選ぶ。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| すべての操作を、WebSocket の上で行う | 経路が1本になり、端末に届く順を、サーバーが決められる。採らなかったのは、要求と応答の対応付け、拒否の表し方、応答を待つ時間の扱いを、WebSocket の上に独自に定めることになるためである。HTTP は、これらを備えている。また、フェーズ1で加わる登録やログインは、接続を確立する前の操作であり、HTTP で行うことになる。操作の経路を2種類にせず、HTTP に揃える |
| 配信に Server-Sent Events を使う | サーバーからの片方向の配信に合い、ブラウザが再接続を標準で行う。採らなかった理由は2つある。(1) HTTP/1.1 では、ブラウザが、オリジンごとの同時の接続の数を制限する。同じブラウザで複数のタブを開くと、配信の接続が枠を占め、操作の要求まで滞る。暗号化しないローカルの開発環境では、HTTP/2 を使えず、この制限を避けられない。(2) フェーズ3の通話では、接続を確立するための情報を、端末とサーバーの間で、双方向に、短い間隔でやり取りする。そのための経路が、別に要る |
| ロングポーリング | 追加の取り決めなしに使えるが、届くたびに要求をやり直すため、順序と取りこぼしの扱いが複雑になる。WebSocket を使えないブラウザは、想定しない |
| 独自の取り決めを持つライブラリ(Socket.IO など) | 再接続や代替の経路を備えるが、取り決めがライブラリに固有で、サーバーとクライアントの両方が、そのライブラリに縛られる。必要な機能は、WebSocket の上に、小さく定められる |
| WebTransport | 暗号化した経路(HTTP/3)を前提とし、暗号化しないローカルの開発環境(WS-D6)で動かしにくい |
| gRPC | ブラウザから直接には呼べず、変換の仕組みが要る。ブラウザを第一想定とするクライアントでは、利点が小さい |
| クラウドが提供する配信のサービス | ローカルの開発環境で動かせない。設置環境が、特定のサービスに固定される。メッセージを、アプリの外のサービスに渡すことになる(PRV-3) |
| gorilla/websocket | 実績は多い。coder/websocket を選んだのは、Go の標準の context に沿って、接続の終了と時間切れを扱え、他のオリジンからの要求を既定で拒否するためである |

## Consequences

- 経路が、操作(HTTP)と配信(WebSocket)の2つになる。このため、次の2点を、別のADRで定める。
  - 履歴(HTTP)と配信(WebSocket)の境目で、メッセージが欠けず、重複しないようにする手段([ADR-010](ADR-010-message-ordering.md))。
  - 送信に使われた端末に、完了の応答(HTTP)と配信(WebSocket)の両方で届く、同じメッセージの扱い([ADR-011](ADR-011-sender-device-delivery.md))。
- 送信の成否は、HTTP の応答で判定する。仕様の「送信が、システムに届かない」(UC-09 E6、WS-17)は、送信の要求が、応答を得られずに失敗した場合に当たる。WebSocket の接続だけが切れた端末は、送信を完了できる(仕様「メッセージを送る」)。
- 動作検証の手順8では、サーバーを起動した後、ブラウザを開き直さずに送り直せる。ただし、WebSocket は再接続しないため、その端末は、開き直すまで、配信を受け取らない。送信はできるが受信はできない状態を利用者に示すことは、本スライスでは行わない(接続が切れたことの表示は、フェーズ1の仕様で定める)。
- WebSocket の上の取り決めは、サーバーから端末への通知に限られ、小さく保てる。フェーズ3で、端末からサーバーへの送信に WebSocket を使う場合は、その時点で、取り決めを広げる判断をする。
- サーバーは、端末ごとの書き込みに時間の上限を設け、応答しない端末が、他の端末への配信と、送信の完了の応答を妨げないようにする。配信が端末に届かなかった場合も、保管と完了の応答は取り消さない(仕様「リアルタイムの配信」)。上限の値は、詳細設計で定める。
- ローカルの開発環境で、ブラウザから見たオリジンを1つにする構成は、[ADR-007](ADR-007-local-development-environment.md) で定める。
