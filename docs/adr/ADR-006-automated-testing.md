# ADR-006 自動テストの手段

- ステータス: active
- 作成日: 2026-11-19
- 対象: ウォーキングスケルトン([仕様](../specs/walking-skeleton.md)「技術要素の決定」)

## Context

仕様は、受け入れ基準の確認方法の「自動テスト」を、テスティングフレームワークで実行する、ソースコードのレベルのテストと定めています(仕様「受け入れ基準」)。あわせて、次を定めています。

- サーバーの振る舞いに関する基準は、クライアントを介さずに、サーバーへ要求と接続を行って確かめる。
- 画面に関する基準は、クライアントのコードのテストで確かめる。
- ブラウザを自動で操作するテスト(E2Eテスト)は、自動化できる場合に導入する。導入するかどうかは、本ADRで判断する。

選定の条件は、次の通りです(仕様「技術要素の決定」)。

- 確認方法を「自動テスト」とした受け入れ基準を、確認できる。複数の利用者の接続にまたがる基準(WS-02、WS-25 など)と、クライアントのコードで確かめる基準(WS-17、WS-27、WS-40 など)を含む。
- E2Eテストを自動化できるかを確かめ、導入するかどうかを判断する。
- すべての選定に共通する条件を満たす。

サーバーは Go、クライアントは TypeScript と React です([ADR-001](ADR-001-language-and-libraries.md))。保管先は PostgreSQL です([ADR-004](ADR-004-data-store.md))。

## Decision

- サーバーのテストは、Go の標準のテストの仕組み(testing パッケージ)で書く。
- クライアントのテストは、Vitest で書く。画面の部品のテストには、jsdom と React Testing Library を使う。
- E2Eテストを導入する。Playwright を使う。
- 対象ごとの手段は、次の表の通りとする。

| 確かめる対象 | 手段 | 基準の例 |
|---|---|---|
| domain と application の規則 | Go のテスト。ポートは、テスト用の実装に差し替える | 本文の規則の境界の値(WS-09〜WS-11) |
| サーバーの振る舞い | サーバーを組み立てて起動し、実際の HTTP の要求と WebSocket の接続で確かめる。保管先は、実際の PostgreSQL とする。複数の利用者と端末は、複数の接続で表す | WS-01〜WS-07、WS-12〜WS-16、WS-18〜WS-21、WS-23〜WS-26、WS-28〜WS-30、WS-37(両方で届くこと)、WS-38、WS-39 |
| 保管に失敗した場合 | 保管のポートを、失敗する実装に差し替えて、サーバーを組み立てる | WS-31 |
| ログ | ログの出力先を差し替え、出力された内容を調べる | WS-33 |
| クライアントの振る舞い | application を、React なしでテストする。ポートは、テスト用の実装に差し替える。時間の経過は、テストから進める | WS-17(応答を得られない場合)、WS-22、WS-37(1通だけ示すこと)、WS-41 |
| 画面の表示 | 画面の部品を、jsdom の上で描画して確かめる | WS-21、WS-27、WS-40 |
| サーバーとクライアントをつないだ動作 | E2Eテスト(下記) | WS-01〜WS-03、WS-27、WS-41 |

- サーバーのテストが使う PostgreSQL は、ローカルの開発環境のもの([ADR-007](ADR-007-local-development-environment.md))とする。テストは、テストごとに独立したデータベースを作って使い、開発用のデータと、他のテストに影響しない。
- 検査(WS-32、WS-34)と、依存規則の検査は、自動テストとは別の手段で行う(ADR-007、[ADR-005](ADR-005-layer-structure.md))。

### E2Eテストの範囲

E2Eテストは自動化できます。Playwright は、1つのテストの中で、互いに状態を共有しない複数のブラウザの状態(コンテキスト)を開けます。これは、動作検証が求める「互いに状態を共有しないブラウザ」(WS-D6)に当たり、複数の利用者と端末にまたがる操作を、1つのテストで書けます。

導入する理由は、サーバーとクライアントがソースコードを共有せず、両者をつないだ状態でしか確かめられないことがあるためです(生成した型の使い方の誤り、実際のブラウザでの表示と実行)。

- E2Eテストで確かめるのは、動作検証の手順のうち、複数の端末にまたがる主要な経路(手順1〜5、手順9)とする。
- 受け入れ基準ごとの確認は、サーバーのテストとクライアントのテストを主とする。E2Eテストは、すべての基準を網羅しない。
- E2Eテストは、動作検証に代えない。動作検証は、仕様の通り、開発者がブラウザで行う。
- E2Eテストは、開発用とは別のデータベースと、そのデータベースにつないだサーバーとクライアントを、実行のたびに用意して使う。固定ユーザーは3人で、会話は3つしかない。手順1は、メッセージがないことを期待するため、開発用のデータや、前の実行のデータが残っていると、成り立たない。
- E2Eテストは、直列に実行し、テストごとに、データを空の状態に戻す。戻す手段は、詳細設計で定める。
- 使うブラウザは、本スライスでは1種類とする。対応するブラウザの範囲は、フェーズ1の仕様で定める(仕様「後続に送る事項」)。

### 選定の条件の確認

| 条件 | 確認 |
|---|---|
| 複数の利用者の接続にまたがる基準を、確認できる | サーバーのテストは、1つのテストの中で、複数の利用者の要求と、複数の WebSocket の接続を扱える。Go の並行処理により、同時の送信(WS-07、WS-18)も書ける |
| クライアントのコードで確かめる基準を、確認できる | Vitest は、時間の経過をテストから進められる(WS-17 の10秒)。React Testing Library は、描画された結果を、文字として確かめられる(WS-27) |
| ライセンスが、MITライセンスでの公開と両立する | Vitest、jsdom、React Testing Library(MIT)、Playwright(Apache-2.0)。いずれも、開発の時点で実行する道具である |
| 個人データとメッセージを、外部のサービスへ送信しない(PRV-3) | テストは、開発者の端末の上で完結する |
| 検証にかける費用を、小さく抑えられる | すべて無償で使え、開発者の端末の上で動く |

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| サーバーのテストに、比較や代替実装の生成のためのライブラリを加える | 記述は短くなる。標準の仕組みで足り、依存物を加えない。足りなくなった時点で、判断する |
| サーバーのテストで、保管先を、メモリの上の代替実装にする | 速く、PostgreSQL が要らない。会話の一意性、送信の識別子の一意性、メッセージの順序は、保管先の制約とトランザクションに依る(ADR-004)。代替実装では、これらを確かめられない。保管先を使わないテストは、domain と application のテストに限る |
| テストごとに、PostgreSQL のコンテナを起動する(testcontainers-go) | テストだけで完結し、事前の起動が要らない。採らなかったのは、依存物が大きく増えることと、ローカルの開発環境に、既に同じ版の PostgreSQL があるためである |
| テストの実行(Go のテスト、Vitest、Playwright)も、コンテナの中で行う | 端末に要るものが減り、ブラウザが要する OS のライブラリも、イメージで揃う。採らなかったのは、サーバーとクライアントを、端末の上で直接に動かす構成(ADR-007)と揃えるためである。E2Eテストは、サーバーとクライアントを起動するため、コンテナの中にも Go と Node.js の環境が要り、環境の定義が二重になる。コンテナで動かすのは、保管先だけとする |
| クライアントのテストに、Jest を使う | 実績は多い。Vitest は、Vite の設定をそのまま使え、TypeScript のための設定が要らない |
| E2Eテストを導入しない | 道具と、実行の時間が増えない。サーバーとクライアントの食い違いを、動作検証でしか検出できなくなる |
| E2Eテストに、Cypress を使う | 1つのテストの中で、複数の利用者を扱いにくい |
| 受け入れ基準を、すべて E2Eテストで確かめる | 利用者の操作に最も近い。実行が遅く、失敗の原因を絞りにくい。拒否の応答や、同時の送信は、ブラウザから起こしにくい |

## Consequences

- サーバーのテストの実行には、ローカルの開発環境の PostgreSQL が、起動している必要がある。PostgreSQL はコンテナで動くため(ADR-007)、Docker が動いていることも要る。
- E2Eテストの実行には、ローカルの開発環境の PostgreSQL が起動していることと、Playwright が取得するブラウザが要る。サーバーとクライアントは、E2Eテストの手順が、専用のデータベースにつないで起動する。開発用に起動しているサーバーとは、別の待ち受け先を使う。実行の手順は、ADR-007 の手順に含める。
- テスト用のポートの実装は、手で書く。ポートは、[ADR-005](ADR-005-layer-structure.md) により、本スライスのユースケースが通過するものに限られ、数は少ない。
- 「配信されない」こと(WS-06、WS-25)を確かめるテストは、届かないことを待って判定することになる。判定の方法は、詳細設計で定める。
- 変更のたびに、テストと検査を自動で実行する仕組み(CI)は、本ADRでは定めない。必要になった時点で、別のADRで判断する。
