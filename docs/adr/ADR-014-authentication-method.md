# ADR-014 認証の方式

- ステータス: active
- 作成日: 2026-11-27
- 対象: 登録とログイン([仕様](../specs/registration-and-login.md)「技術要素の決定」)。[ADR-013](ADR-013-temporary-login-identity.md) を置き換える

## Context

本スライスは、仮のログイン(WS-P2)を、正式実装に置き換えます。本ADRは、認証の方式(秘密の種類、ログイン状態を示す資格の形、操作とリアルタイムの接続への添え方)を決定します。ADR-013 は、仮のログインとともに、フェーズ1の認証のADRで置き換えると定めています。

選定の条件は、次の通りです(仕様「技術要素の決定」)。

- RL-14〜RL-21 を満たせる。
- ログイン状態が無効になったとき、そのログイン状態による接続を、サーバーの側から終えられる(RL-18、RL-19)。
- 資格を、接続先のアドレスに載せない(SEC-1、RL-33)。
- 第三者のサイトからの操作を防げる(RL-41 の WS-29。ADR-013 が挙げた、Origin が付かない要求の扱いを含む)。
- 複数サーバー構成への移行を妨げない(PERF-3)。
- すべての選定に共通する条件を満たす。

仕様が、既に定めていることは、次の通りです。本ADRは、これを前提とします。

- 秘密は、利用者が決めて入力する(RL-D3)。ログインは、連絡先と秘密で行う(RL-D2)。
- ログイン状態は、ブラウザの単位で保ち、同じブラウザのタブが共有する。再読み込みの後も、ブラウザを閉じて開き直した後も、保たれる(RL-D4、RL-21)。
- 有効期限は、ログインからの経過だけで定まり、操作によって延びない(RL-D4)。

ADR-013 は、Cookie を採る場合に定める事項として、次の2つを挙げています。

- ログイン状態が無効になったとき、そのログインによるすべての接続を、サーバーの側から閉じるための、ログイン状態と接続の対応付け。
- Origin が付かない GET の扱い([ADR-002](ADR-002-realtime-communication.md))。

判断に関わる、ブラウザの性質は、次の通りです。

- 標準の WebSocket API は、接続を確立する要求に、任意のヘッダーを付けられない(ADR-013)。Cookie は、付く。
- Cookie は、同じブラウザのタブが共有し、ブラウザが、要求に自動で付ける。SameSite 属性は、付ける範囲を、サイト(登録できるドメインの単位)で限る。オリジン(ポートを含む)の単位では、限らない。localhost の、別のポートのページは、同じサイトに当たる。
- 他のオリジンのページが、要求に、専用の要求ヘッダーを付けようとすると、ブラウザは、事前の確認の要求を送る。サーバーは、他のオリジンに許可を返さないため(ADR-002)、その要求は送られない(ADR-013)。

本ADRでは、次の用語を使います。

| 用語 | 意味 |
|---|---|
| ログイン状態の識別子 | ログイン状態ごとに、システムが割り当てる値。資格とは、別の値である。秘密ではなく、これだけでは、操作できない |

## Decision

### 秘密の種類

- 認証に用いる秘密は、パスワード(利用者が決めて入力する文字列)とする。条件は、仕様「入力の規則」の通りである。保管する形は、[ADR-015](ADR-015-secret-storage.md) で定める。

### ログイン状態を示す資格の形

- 資格は、それ自体は意味を持たない、無作為な値とする。256ビットを、暗号に使える乱数の生成の手段(標準ライブラリの crypto/rand)で作る(RL-35)。ログインのたびに、新しく作る。
- サーバーは、ログイン状態(利用者、有効期限、ログイン状態の識別子)を保持し、資格から引く。保持する先は、[ADR-016](ADR-016-login-state-and-counter-stores.md) で定める。
- サーバーは、資格そのものを保管しない。資格の要約(SHA-256)だけを保管し、要約で引く。
- 登録の、確認のための資格も、同じ形とする(256ビットの無作為な値。保管するのは、要約だけ)。

### 操作とリアルタイムの接続への添え方

資格は、Cookie で保ちます。属性は、次の通りです。

| 属性 | 値 | 理由 |
|---|---|---|
| HttpOnly | 付ける | ページのスクリプトから、資格を読めなくする |
| SameSite | Strict | 他のサイトのページからの要求に、資格を付けさせない。クライアントは、静的なファイルと、そこからの通信で動くため([ADR-001](ADR-001-language-and-libraries.md))、他のサイトから遷移してきた最初の要求に、資格が付かなくても、支障がない |
| 有効期限 | ログイン状態の有効期限まで | ブラウザを閉じて開き直した後も、保つ(RL-21) |
| Path | `/` | — |
| Domain | 付けない | 送る先を、アプリのホストに限る |
| Secure と、名前の `__Host-` 接頭辞 | ローカルの開発環境では、付けない | 経路を暗号化しないためである(RL-D1)。設置環境を扱うスライスで、付ける |

- HTTP の操作と、WebSocket の接続を確立する要求には、ブラウザが、Cookie を付ける。クライアントのコードは、資格に触れない。資格は、応答の本文にも、接続先のアドレスにも、載せない。
- ログインの応答は、ログイン状態の識別子を返す。端末(タブ)は、これをメモリに保持し、HTTP の操作に、専用の要求ヘッダーで添える。WebSocket の接続を確立する要求には、接続先のアドレスのクエリで添える。
- 再読み込みした端末と、開き直した端末は、メモリに識別子を持たない。「現在のログイン状態を確かめる」操作で、ログイン中の利用者と、ログイン状態の識別子を取得する。この操作は、GET とし、状態を変えず、識別子を要さない。
- サーバーは、登録、ログイン、「現在のログイン状態を確かめる」を除く、すべての操作と、接続を確立する要求で、次の2つを確かめる。どちらかを満たさない要求は、理由に依らず、同じ応答で拒否する(RL-15)。
  1. Cookie の資格に当たるログイン状態があり、有効期限を過ぎていない。
  2. 添えられた識別子が、そのログイン状態のものである。
- 「現在のログイン状態を確かめる」は、1 だけを確かめる。
- ログインの要求に付いた資格に当たるログイン状態があれば、サーバーは、それを無効にしてから、新しいログイン状態を与える(RL-14)。
- ログアウトでは、サーバーは、ログイン状態を無効にし、Cookie を消す応答を返す。

### 第三者のサイトからの操作(WS-29)

次の4つを重ねて、防ぎます。

| 手段 | 防ぐもの |
|---|---|
| SameSite=Strict | 他のサイトのページからの要求(Origin が付かない GET を含む)に、資格が付かない |
| Origin と Host の検証(ADR-002 のまま) | Origin が付く要求(GET と HEAD を除く操作、WebSocket の接続を確立する要求)のうち、アプリのオリジンからでないもの。同じサイトで、オリジンが異なるページ(localhost の別のポートなど)からのものを含む |
| ログイン状態の識別子を、専用の要求ヘッダーで要する | Origin が付かない GET のうち、同じサイトで、オリジンが異なるページからのもの(SameSite では、資格が付く)。他のオリジンのページは、識別子を読めず、専用の要求ヘッダーも付けられない |
| 状態を変える操作を、GET と HEAD に割り当てない | 上の3つを通った GET が、状態を変えること |

- ADR-013 が挙げた「Origin が付かない GET の扱い」は、1行目と3行目が受け持つ。
- 「現在のログイン状態を確かめる」は、識別子を要さないため、同じサイトで、オリジンが異なるページから、資格の付いた GET を送れる。この操作は、状態を変えず、上限の計数の対象でもない。応答は、CORS の許可を返さないため、そのページからは読めない。
- 第三者のサイトのページが、自分のホストの名前を、サーバーのアドレスに向け直した場合(DNS rebinding)、Cookie は、ホストの名前に結び付くため、資格が付かない。Host の検証(ADR-002)は、続ける。

### ログイン状態が無効になったときの、接続と端末

- サーバーは、接続を受け付けるときに、接続を、利用者に加えて、ログイン状態と対応付ける。対応付けは、配信の adapter が保持する状態に加え、ポートの背後に置く(RL-39)。
- ログイン状態を無効にしたとき(ログアウト、同じブラウザでのログインし直し)、サーバーは、そのログイン状態による接続を、すべて閉じる。閉じた接続は、配信の宛先から外れる(RL-18)。
- 有効期限は、接続を受け付けた時点で定まる(操作によって延びない。RL-D4)。サーバーは、期限に達した接続を、閉じる。
- サーバーは、これらの接続を、ログイン状態が無効になったことを示す、専用の終了コードで閉じる。
- クライアントは、この終了コードで接続が閉じられたときと、認証の拒否の応答を受けたときに、保持していた内容を捨て、ログインを求める画面に切り替える(RL-19)。
- 同じブラウザの別のタブで、別の利用者としてログインし直された端末(RL-20)は、次の通りになる。ログインし直しは、それまでのログイン状態を無効にする。接続を保っている端末は、上の終了コードで、操作なしに切り替わる。接続が切れている端末は、次の操作が、識別子の不一致によって拒否され、切り替わる。

### 層との関係

- 資格と、ログイン状態の識別子は、ユースケースを呼ぶ adapter が、要求から取り出し、ユースケースの入力の「操作を行う利用者」として渡す。
- ログイン状態が有効であることは、usecase が、操作のたびに、ポートを通して確かめる。adapter の中では、判定しない([ADR-005](ADR-005-layer-structure.md)。ADR-013 が、固定ユーザーの確認について定めた分担と同じである)。
- 資格の生成と、要約の計算は、ポートの背後に置く。domain と application は、乱数と暗号の標準ライブラリを import できないためである(ADR-005)。

Cookie、要求ヘッダー、クエリの名前、終了コードの値、期限に達した接続を閉じる仕組み、ポートの形は、詳細設計で定めます。

### 選定の条件の確認

| 条件 | 確認 |
|---|---|
| RL-14(ログインのたびの、新しい資格) | 資格は、ログインのたびに作る。ログインの前にブラウザが持っていた資格のログイン状態は、ログインの中で無効にする。ログイン状態は、資格ごとに独立しており、別のブラウザのものは、残る |
| RL-15(同じ応答での拒否) | 資格がない、正しくない、期限が切れた、ログアウトした、識別子が合わない、のどれも、「当たる有効なログイン状態がない」として、同じ拒否にする |
| RL-16(有効期限) | 期限は、ログイン状態とともに保持し、操作のたびに、サーバーが比べる。Cookie の有効期限には、頼らない |
| RL-17(ログアウト) | ログイン状態を、保管先から無効にする。同じブラウザのタブは、同じ資格を共有するため、すべてに及ぶ。他のブラウザの資格は、別のログイン状態である |
| RL-18、RL-19(接続を、サーバーの側から終える) | 「ログイン状態が無効になったときの、接続と端末」の通り。coder/websocket は、サーバーの側から、終了コードを指定して閉じられる |
| RL-20(別の利用者としてのログインし直し) | 同上。接続が切れている端末の操作は、識別子の確認で拒否する。サーバーへ直接送った要求で、確かめられる |
| RL-21(保たれること) | 資格は、有効期限を付けた Cookie として、ブラウザが保つ。ログイン状態は、保管先に置くため、サーバーを再起動しても残る(ADR-016) |
| 資格を、接続先のアドレスに載せない(SEC-1、RL-33) | 資格は、Cookie のヘッダーでだけ送られる。アドレスに載せるのは、秘密でない識別子だけである |
| 第三者のサイトからの操作を防げる(WS-29) | 「第三者のサイトからの操作」の通り |
| 複数サーバー構成への移行を妨げない(PERF-3) | ログイン状態は、保管先に置き、どのサーバーからも引ける。操作の間に、サーバーが保持する端末ごとの状態は、増えない。接続との対応付けは、配信の adapter の状態であり、他のサーバーが保持する接続を閉じるには、配信と同じく、サーバーの間の中継が要る(ADR-002)。中継は、ポートの実装として加えられる。本スライスでは、作らない |
| ライセンスが、MITライセンスでの公開と両立する | 依存物を加えない。標準ライブラリ(crypto/rand、crypto/sha256、net/http)と、既存の coder/websocket で足りる |
| 個人データとメッセージを、外部のサービスへ送信しない(PRV-3) | 外部の認証のサービスを使わない |
| 検証にかける費用を、小さく抑えられる | 費用は、生じない |

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| 資格を、端末(タブ)が保持し、要求ヘッダーで添える(ADR-013 の形を続ける) | ブラウザが自動で付けないため、第三者のサイトからの操作を、単純に防げる。採らなかった理由は3つある。(1) タブのメモリに置くと、再読み込みのたびにログインが要り、RL-D4 に合わない。(2) ブラウザの保存の仕組み(localStorage など)に置くと、ページのスクリプトから、資格を読める。(3) WebSocket の接続を確立する要求に、ヘッダーを付けられず、資格を、接続先のアドレスに載せるか(SEC-1 に反する)、別の受け渡しの取り決めを作ることになる |
| 資格を、自己完結型(利用者と期限を含め、署名した値。JWT など)にする | 操作のたびの、保管先への照会が要らない。ログアウトした資格を使えなくするには(RL-17)、無効にした資格をサーバーが保持して、照会することになり、利点が消える。鍵の管理も加わる(SEC-6) |
| SameSite を、Lax にする | 他のサイトから遷移してきた最初の要求にも、資格が付く。クライアントは、その要求に資格を要さないため、付ける理由がない |
| Origin が付かない要求を、Sec-Fetch-Site ヘッダーの検証で拒否する(Go の標準ライブラリの http.CrossOriginProtection を含む) | クライアントが、何も添えなくてよい。採らなかった理由は3つある。(1) このヘッダーを付けないブラウザでは、検証できない。対応するブラウザの範囲は、まだ定めていない(仕様「後続に送る事項」)。(2) http.CrossOriginProtection は、GET と HEAD を、検証せずに通す(Go 1.26.8 の文書で、2026-11-27 に確かめた)。(3) 別のタブでログインし直された端末(RL-20)には、働かず、別の手段が要る |
| 別のタブでのログインし直しを、タブの間の通知(BroadcastChannel など)で知らせる | 接続が切れている端末も、操作を待たずに切り替えられる。クライアントの中の取り決めであり、通知を処理する前の操作を、サーバーが拒否できない。サーバーのテストで、確かめられない |
| ログイン状態の識別子の代わりに、利用者の識別子を添える | 同じ利用者としてログインし直したとき、古い端末の操作が、そのまま通る。その端末の接続は、古いログイン状態とともに閉じられているため、操作だけが通り、配信が届かない端末になる |
| ログイン状態の確認を、専用のユースケースにまとめ、adapter が先に呼んで、特定した利用者を、各ユースケースの入力に渡す | 既存のユースケースの入力が、変わらない(ADR-013 の見込みの通りになる)。各ユースケースは、渡された利用者を信じることになり、確認を経ない呼び出しを、拒否できない。確認が行われることが、adapter の呼び出しの順に依る |
| セッション管理のライブラリ(alexedwards/scs など)を使う | 資格の生成、Cookie、有効期限の扱いを備える。HTTP のミドルウェアとして働くため、ログイン状態の確認が、adapter の中で完結する形になり、usecase がポートを通して確かめる分担に合わない。要る処理は、標準ライブラリで足りる(ADR-001) |
| 資格そのものを、保管する | 要約の計算が要らない。保管データを読めた者が、有効なログイン状態を、そのまま使える |
| パスワードを使わない方式(案内のリンクだけでログインする、パスキーなど) | 利用者が、秘密を覚えなくてよい。仕様とユースケース記述は、利用者が決めて入力する秘密を前提としている(RL-D3、UC-01 基本フロー 4、UC-07) |

## Consequences

- ユースケースの入力の「操作を行う利用者」が、変わる。ADR-013 は、置き換えが、ユースケースを呼ぶ adapter と、ポートの実装に閉じ、この入力は変わらないと見込んでいた。仮のログインでは、識別名であった。本ADRでは、資格と、ログイン状態の識別子になる。既存の3つのユースケース(メッセージを送る、会話の履歴を読む、リアルタイムの接続を受け付ける)の入力と、利用者を確かめる手順が変わる。観察記録に残す(OBS-020)。
- 境界要素が増える見込みである。ログイン状態を保持するポート(ADR-016)、資格を作るポート、ログイン状態による接続を閉じるポートが加わり、接続を登録するポートと、接続への書き込み口(閉じる理由の伝え方)が変わる。形は、詳細設計で定め、観察記録の計数の対象とする([ADR-008](ADR-008-observation-records.md))。
- 操作のたびに、保管先への照会が、1回増える。想定規模では、支障にならないと判断する(PERF-1)。
- ログアウトと、ログインし直しは、同じブラウザの、すべてのタブに及ぶ(RL-D4 の帰結と同じ)。同じ利用者としてログインし直した場合も、古いタブは、ログインを求める画面に切り替わる。
- 端末は、開いた直後に、「現在のログイン状態を確かめる」を呼ぶ。通信の形式に、この操作が加わる。
- ログイン状態の識別子は、接続先のアドレスに現れ、クライアントの開発用のサーバーと、サーバーのログに残りうる。識別子は、資格ではなく、仕様「記録」が記録しないと定めたものにも、当たらない。
- Cookie は、ポートを区別しない。開発者の端末では、localhost の別のポートで動くサーバーにも、資格が送られる。E2Eテスト用のサーバーも、これに当たるが、E2Eテストは、テストごとのブラウザの状態を使うため、開発用の資格は送られない([ADR-006](ADR-006-automated-testing.md))。
- 設置環境を扱うスライスで、次を行う。Cookie に、Secure と `__Host-` 接頭辞を付ける。サーバーの前に中継を置く場合に、Origin と Host の検証が成り立つ構成にする(ADR-002)。
- 確認のための資格を、案内に載せる形は、詳細設計で定める(仕様「後続に送る事項」)。アドレスに載せる場合は、サーバーへ送られない部分に載せる(RL-33)。
- 秘密の変更と再設定(UC-07、UC-04)が求める、利用者のすべてのログイン状態の無効化は、ログイン状態を利用者から引き、同じ手段で接続を閉じることで、行える。そのための操作は、先行して作らない。
- ADR-002 が、ADR-013 に委ねていた「Origin が付かない要求によって、第三者のサイトが利用者として操作できないこと」は、本ADRの「第三者のサイトからの操作」が引き継ぐ。
- 通信の形式の `securitySchemes.fixedUser` と、仮実装の箇所の一覧の WS-P2 の箇所は、本ADRの方式に置き換える(RL-42)。
