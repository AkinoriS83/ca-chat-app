# ADR-001 実装言語と主要なライブラリ

- ステータス: active
- 作成日: 2026-11-19
- 対象: ウォーキングスケルトン([仕様](../specs/walking-skeleton.md)「技術要素の決定」)

## Context

ウォーキングスケルトンの仕様は、技術要素を選定せず、選定の条件だけを定めています。本ADRは、そのうち「実装言語と主要なライブラリ(サーバー、クライアント)」を決定します。

選定の条件は、次の通りです(仕様「技術要素の決定」)。

- 依存規則と飛ばし禁止を、機械的に検査できる。
- フェーズ1〜3の機能(認証、ブラウザでの音声通話)と、AWS上での個人による運用を妨げない。
- すべての選定に共通する条件を満たす(後続フェーズで目標水準を満たす妨げにならない。依存物のライセンスが、MITライセンスでの公開と両立する。個人データとメッセージを、外部のサービスへ送信しない。検証にかける費用を、小さく抑えられる)。

クライアントは、ブラウザを第一想定とします(開発方針「開発の流れ」)。開発者は1名で、AIを使用して開発します(開発方針「開発体制」)。

## Decision

- サーバーは、Go で実装する。HTTP、JSON、ログには、標準ライブラリ(net/http、encoding/json、log/slog)を使う。外部のライブラリは、標準ライブラリで足りない箇所に限って加える(WebSocket は [ADR-002](ADR-002-realtime-communication.md)、通信の形式からのコード生成は [ADR-003](ADR-003-api-contract-definition.md)、保管先へのアクセスは [ADR-004](ADR-004-data-store.md))。
- クライアントは、TypeScript で実装する。画面の構築に React を、ビルドと開発用のサーバーに Vite を使う。ビルドと依存物の管理に、Node.js(LTS版)と npm を使う。
- クライアントは、ビルドした静的なファイルだけで動く構成とする。実行時に、外部(CDNなど)から、コード、スタイル、フォントを読み込まない。
- リポジトリは、サーバー(`server/`。Go のモジュール)と、クライアント(`client/`。npm のパッケージ)に分ける。両者は、ソースコードを共有しない。共有するのは、通信の形式の定義だけとする(ADR-003)。
- Go と Node.js の版、依存物の版は、リポジトリに記録して固定する(go.mod と go.sum、package.json と package-lock.json。WS-32)。

### 選定の条件の確認

| 条件 | 確認 |
|---|---|
| 依存規則と飛ばし禁止を、機械的に検査できる | Go は、import がパッケージの単位で、循環する import をコンパイラが拒否する。パッケージの間の import の許可と禁止を、静的解析で検査できる。TypeScript も、モジュールの間の import を、静的に検査できる。手段は [ADR-005](ADR-005-layer-structure.md) で定める |
| 認証(フェーズ1)を妨げない | 秘密を復元できない形にする処理、推測できない値の生成、メールの送信は、Go の標準ライブラリと準標準のライブラリ(golang.org/x/crypto)で扱える。方式は、フェーズ1のADRで定める |
| ブラウザでの音声通話(フェーズ3)を妨げない | ブラウザの側は、標準のAPI(WebRTC)を、TypeScript から使える。サーバーの側は、接続を確立するための情報のやり取りを、ADR-002 の通信で行える。中継が要る場合は、Go による実装(Pion)や、アプリとは別に動かす中継のサーバーを選べる。選定は、フェーズ3の仕様で行う |
| AWS上での個人による運用を妨げない | サーバーは、単一の実行ファイルになる。クライアントは、静的なファイルになる。小さな構成のノード1台で動かせる |
| 複数サーバー構成への移行を妨げない(PERF-3) | 言語とライブラリは、サーバーの中に保持する状態を強いない。状態の置き場所は、ADR-002、ADR-004、ADR-005 で確認する |
| ライセンスが、MITライセンスでの公開と両立する | Go(BSD-3-Clause)、TypeScript(Apache-2.0)、React、Vite、Node.js(MIT) |
| 個人データとメッセージを、外部のサービスへ送信しない(PRV-3) | 選定した言語とライブラリは、外部のサービスへ送信する仕組みを含まない。クライアントは、実行時に外部から何も読み込まない |
| 検証にかける費用を、小さく抑えられる | すべて無償で使え、開発者の端末の上で動く |

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| サーバーも TypeScript(Node.js)にする | 言語が1つで済み、通信の形式の型や、本文の規則(WS-D3)の実装を、サーバーとクライアントで共有できる。採らなかったのは、Go の次の点を選んだためである。(1) 長く保たれる多数の接続を、軽量な並行処理(goroutine)で素直に扱える。(2) 標準ライブラリが、HTTP、JSON、ログ、暗号を備え、依存物を少なく保てる(SEC-4 の A03、SEC-7 の対象が小さくなる)。(3) 単一の実行ファイルになり、設置と更新(OPS-1)が簡素になる。(4) パッケージが import の単位であり、層とパッケージを対応させて検査しやすい。言語が2つになることによる定義の二重化は、ADR-003 で避ける |
| サーバーを Kotlin / Java、C# にする | 層の検査の道具は揃っている。実行環境が重く、小さなノードでの運用と、開発時の起動の速さで、Go に劣る |
| サーバーを Rust にする | 実行時の性能と安全性は高い。想定規模(利用者数十人程度)では必要がなく、開発の速さで劣る |
| サーバーを Elixir(Phoenix)にする | リアルタイムの配信を、フレームワークが備える。フレームワークが構造を定めるため、仮説の層構造を自前で定めて検査する本プロジェクトの目的と、噛み合わない |
| Go の HTTP のフレームワーク(chi、Echo、Gin など)を使う | 要求の方法とパスによる振り分けは、標準ライブラリで足りる。足りる機能のために、依存物を加えない |
| クライアントを Vue、Svelte にする | いずれも条件を満たす。React を選んだのは、参照できる情報が最も多く、開発者とAIの双方が扱いやすいためである |
| クライアントを、サーバーで画面を組み立てる構成(Next.js など)にする | 画面を組み立てるサーバーが加わり、運用する対象が増える。本プロジェクトの画面は、ログイン後に使うものであり、サーバーで組み立てる利点が小さい |
| 依存物の管理に pnpm を使う | クライアントのパッケージは1つであり、Node.js に付属する npm で足りる |

## Consequences

- 言語が2つになる。検査、テスト、依存物の脆弱性の検査(SEC-7。フェーズ1の完了時)の道具を、それぞれに用意する。
- 通信の形式を、2つの言語で持つことになる。食い違いを防ぐ手段は、ADR-003 で定める。
- 本文の規則(WS-D3)は、サーバーの実装が正となる。クライアントが送信の前に検証する場合、同じ規則を TypeScript でも実装することになる。文字の数え方(コードポイント)と空白文字の範囲(White_Space 特性)は、言語の標準の機能が指す範囲が Go と JavaScript で異なる箇所があるため、同じ見本で両方をテストする。
- Go の encoding/json は、正しくない UTF-8 と、対にならないサロゲートのエスケープを、エラーにせず、U+FFFD に置き換えて受け付ける。「文字列として正しい」(WS-D3)の検証は、JSON を復号した後の文字列ではできないため、復号の前の段階で行う。手段は、詳細設計で定める。
- クライアントが実行時に外部からコードを読み込まないため、OWASP Top 10 の A08(Software or Data Integrity Failures)は、仕様の通り「該当しない」のままとする。依存物とコード生成の道具は、ビルドの時点で、版を固定して取得する(WS-32)。
- 推移的な依存物を含め、導入する版のライセンスは、導入の時点で確かめる。
