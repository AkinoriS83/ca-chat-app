# ADR-003 通信の形式の定義

- ステータス: active
- 作成日: 2026-11-19
- 対象: ウォーキングスケルトン([仕様](../specs/walking-skeleton.md)「技術要素の決定」)

## Context

サーバーは Go、クライアントは TypeScript で実装し、両者はソースコードを共有しません([ADR-001](ADR-001-language-and-libraries.md))。クライアントからの操作は HTTP で、サーバーからの配信は WebSocket で行います([ADR-002](ADR-002-realtime-communication.md))。

このため、通信の形式(HTTP の要求と応答、WebSocket で届けるメッセージ)を、2つの言語で持つことになります。それぞれを手で書くと、一方だけを変更したときに、食い違いが生じます。食い違いは、サーバーのテストでも、クライアントのテストでも検出できず、両者をつないで初めて現れます。

本ADRは、仕様が挙げた決定する事項のうち、「実装言語と主要なライブラリ」に伴って必要になった判断を、1つのADRとして記録するものです。すべての選定に共通する条件(仕様「技術要素の決定」)を満たすことを、選定の条件とします。

## Decision

- 通信の形式は、OpenAPI の文書1つで定義する。文書は、サーバーとクライアントのどちらにも属さない場所(`api/`)に置く。
- 文書には、HTTP の操作(要求、応答、拒否の応答)を記述する。WebSocket で届けるメッセージの形式も、同じ文書のスキーマとして記述する。
- サーバーの型と、HTTP の操作を受けるインターフェイスは、文書から oapi-codegen で生成する。クライアントの型は、文書から openapi-typescript で生成する。通信の形式を、手で書いた型で二重に持たない。
- 要求の本文(JSON)は、HTTP の操作を受ける adapter が復号する。生成したコードに任せるのは、型と、操作の振り分けまでとする。メッセージの本文の項目を、置き換えなしに復号するためである(下記 Consequences)。
- 生成したコードは、リポジトリに含める。文書から生成し直した結果が、リポジトリの内容と一致することを、機械的に検査する。
- 生成した型は、通信の形式を扱う層だけで使い、内側の層へ渡さない([ADR-005](ADR-005-layer-structure.md))。生成したサーバーのコードは、どの adapter にも属さないパッケージに置く。HTTP の操作を受ける adapter と、WebSocket を扱う adapter が、同じ型を使うためである。
- 拒否の応答は、共通の形式とし、拒否の種類を示す値を含める。クライアントは、この値によって、拒否の理由を利用者に示す(WS-40)。拒否の応答に、内部の構造が分かる情報を含めない(WS-30)。同じ応答で拒否すると仕様が定めた場合(R-2)は、応答の種類と内容を、同じにする。
- OpenAPI の版は、3.0 とする。2つの生成の道具が、ともに対応する版である。3.1 は、本ADRの時点で、oapi-codegen の対応が初期の段階にあるため、採らない。生成の道具の版は、リポジトリに記録して固定する(WS-32)。

### 選定の条件の確認

| 条件 | 確認 |
|---|---|
| 後続フェーズで目標水準を満たす妨げにならない | フェーズ1以降で加わる操作を、同じ文書に加えていける。認証の方式(SEC-1〜3)は、文書に記述できる。分割しての取得(PERF-2)の形式も、記述できる |
| ライセンスが、MITライセンスでの公開と両立する | oapi-codegen(Apache-2.0)、openapi-typescript(MIT)。どちらも、開発の時点で実行する道具である。oapi-codegen が生成するサーバーのコードは、パラメータの復号のために、oapi-codegen/runtime(Apache-2.0)を import することがある。その場合、これは、サーバーの実行時の依存物になる |
| 個人データとメッセージを、外部のサービスへ送信しない(PRV-3) | 生成は、開発者の端末の上で行う。外部のサービスを使わない |
| 検証にかける費用を、小さく抑えられる | すべて無償で使える |

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| サーバーとクライアントで、それぞれ型を手で書く | 道具が要らない。採らなかったのは、食い違いを、両者をつないだテスト(E2Eテスト)と動作検証でしか検出できないためである。操作は、フェーズ1以降で増え続ける。最初のスライスで、定義を1つにする流れを通しておく |
| Protocol Buffers(Connect など)で定義する | 1つの定義から、両方の言語のコードを生成できる。採らなかったのは、ブラウザで一般的な HTTP と JSON の形から離れ、要求と応答を、ブラウザの開発者向けの機能でそのまま読めなくなるためである。gRPC を使う予定はない |
| GraphQL | クライアントが、取得する項目を選べる。要求の形が自由になる分、認可と、1回の取得量(PERF-2)を確かめる範囲が広がる |
| WebSocket で届けるメッセージを、別の文書(AsyncAPI など)で定義する | 配信の経路を、専用の形式で記述できる。本スライスで届けるメッセージの種類は少なく、文書と道具を増やす利点が小さい。種類が増えた時点で、改めて判断する |
| 生成したコードを、リポジトリに含めない(ビルドのたびに生成する) | 生成物と定義がずれない。採らなかったのは、検査、テスト、AIによる参照の前に、常に生成の手順が要るようになるためである。ずれは、生成し直した結果との一致の検査で防ぐ |

## Consequences

- 通信の形式を変えるときは、文書を変えてから、コードを生成し直す手順になる。手順は、ローカルの開発環境の手順に含める([ADR-007](ADR-007-local-development-environment.md))。
- サーバーの、HTTP の操作を受ける部分の形(関数の単位と引数)は、生成したインターフェイスに従う。この影響は、通信の形式を扱う層に留まる。
- 文書に記述するのは、形式(項目とその型)までとする。値の検証(本文の規則〈WS-D3〉、送信の識別子の形式〈[ADR-009](ADR-009-send-identifier.md)〉)は、内側の層で行う。本文と送信の識別子は、文書の上では、制約のない文字列とする。復号の段階で値を拒否すると、仕様が定めた拒否の順序(仕様「メッセージを送る」の拒否の表)を保てないためである。
- 「文字列として正しい」(WS-D3)も、本文の他の規則と同じく、domain が判定し、本文が正しくないことを示す応答で拒否する。Go の encoding/json は、正しくない UTF-8 と、対にならないサロゲートを、U+FFFD に置き換えて復号するため([ADR-001](ADR-001-language-and-libraries.md))、そのまま使うと、内側で判定できなくなる。adapter は、メッセージの本文の項目を、置き換えずに復号し、正しくない並びのまま、ユースケースの入力に渡す。adapter は、検出するだけで、拒否しない。
- 形式に合わない要求(JSON として壊れている、項目の型が違うなど)は、復号の段階で拒否し、入力が正しくないことを示す共通の応答を返す(WS-30)。メッセージの本文の項目の中の、文字列として正しくない並びは、これに含めない(上記)。
- WebSocket で届けるメッセージは、OpenAPI の「操作」としては記述できず、スキーマとしてだけ記述する。どのメッセージが、いつ届くかは、文書の説明に書く。
