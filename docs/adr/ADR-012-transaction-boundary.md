# ADR-012 トランザクションの境界を握る層

- ステータス: active
- 作成日: 2026-11-20
- 対象: ウォーキングスケルトン([仕様](../specs/walking-skeleton.md)「メッセージを送る」、WS-D2)

## Context

メッセージの送信は、保管先への複数の操作を、一体として行います。

- 会話の成立と、最初のメッセージの保管は、1つのトランザクションで行う([ADR-004](ADR-004-data-store.md))。
- 連番は、メッセージを保管するトランザクションの中で、会話の単位で直列にして付ける。欠番を作らない([ADR-010](ADR-010-message-ordering.md))。
- 送信の識別子の一致は、保管先の一意性の制約によって判定する([ADR-009](ADR-009-send-identifier.md))。

一体とする範囲は、仕様が定める規則でもあります。

- 拒否した送信は、保管せず、配信せず、会話も成立させない(仕様「メッセージを送る」)。
- 完了の応答と配信は、保管が確定した後に行う(OPS-2、WS-31)。

[ADR-005](ADR-005-layer-structure.md) は、層と依存の規則を定めましたが、このトランザクションを、どの層が始め、確定し、取り消すのかを、定めていません。握る層によって、ポートの形と、規則の置き場所が変わります。

- 保管先を扱う adapter が握る場合、ポートは「メッセージを保管する」の1つになる。「会話がなければ成立させる」「識別子が一致したら、保管済みのメッセージを返す」という判断が、adapter の中の問い合わせに入る。
- usecase が握る場合、トランザクションを表すポートが要る。判断は、usecase に残る。

PostgreSQL には、本ADRに関わる性質が1つあります。制約に違反したトランザクションは、その場で続行できなくなり、取り消すことしかできません。「保管を試み、制約に当たった場合に、保管済みのメッセージを取得する」(ADR-009)は、同じトランザクションの中では、そのままの形では行えません。

## Decision

- 一体とする範囲は、usecase が決める。application/port に、トランザクションのポートを置く。usecase は、一体として行う操作を、1つの関数として、このポートに渡す。関数がエラーを返した場合、その中で行った操作は、すべて取り消される。エラーを返さなかった場合、確定する。
- トランザクションの中でだけ行える操作(会話を成立させる、会話への追記を直列にする、メッセージを追記する)は、上の関数に引数として渡されるインターフェイスにだけ置く。トランザクションの外からは、呼べない形にする。トランザクションを、呼び出しの文脈(Go の context)に隠して渡すことは、しない。
- ポートの操作は、ユースケースの用語で定義する(「追記を直列にする」「重複した送信である」)。行のロック、一意性の制約、連番の採番は、保管先を扱う adapter の中の、実現の手段とする。
- 送信の識別子が、保管済みのメッセージと一致した場合は、次の通りに扱う。
  1. メッセージを追記する操作が、重複した送信であることを示すエラーを返す。
  2. usecase は、そのエラーを関数から返し、トランザクションを取り消す。併せて行った会話の成立と、連番の割り当ても、取り消される。
  3. usecase は、取り消した後に、トランザクションの外で、保管済みのメッセージを取得する。指定した会話のものであれば、完了を示し、配信しない。別の会話のものであれば、拒否する(ADR-009)。
- 配信のポートは、トランザクションのポートから戻った後(保管が確定した後)に、usecase が呼ぶ。関数の中では、引数として渡された操作のほかに、ポートを呼ばない。
- 読み取りだけのユースケース(会話の履歴を読む)は、トランザクションのポートを使わない。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| 保管先を扱う adapter が握る(ポートは「メッセージを保管する」の1つ) | 境界要素が少なく、usecase は短くなる。会話の成立と、重複した送信の扱いの判断が、adapter の問い合わせに入り、「domain の規則は、adapter から呼ばない」(ADR-005)の趣旨と合わない。分岐を、application のテストで確かめられず、実際の PostgreSQL を使うテストだけに頼ることになる。送信のユースケースが、ポートを呼ぶだけに近づき、観察記録の計数([ADR-008](ADR-008-observation-records.md))が、飛ばし禁止の携行コストではなく、adapter へ押し出した量を表すようになる |
| トランザクションを、呼び出しの文脈(context)に載せて渡す | ポートの操作の形が、トランザクションの内と外で変わらず、記述は短い。トランザクションの外から追記の操作を呼ぶ誤りが、コンパイルでも、import の検査でも検出されず、一体性が黙って失われる |
| usecase が、開始、確定、取り消しを、別々の操作として呼ぶ | 関数を渡す形が要らない。取り消しの呼び忘れと、エラーの経路での確定の誤りを、usecase ごとに防ぐことになる |
| 制約に当たった後も、同じトランザクションの中で続ける(制約に当たっても失敗としない書き方や、途中まで巻き戻す仕組みを使う) | 取り消した後の読み取りが、1回減る。会話の成立と、連番の割り当てを、場合に応じて個別に取り消す処理が要り、その判断が adapter に入る。全体を取り消す形は、拒否の場合(別の会話のメッセージと一致した)と、同じ経路になる |

## Consequences

- 境界要素が2つ増える(トランザクションのポートと、その中で使う操作のインターフェイス)。メッセージを送るユースケースが、現に通過する境界である。観察記録の計数の対象とする(ADR-008)。
- ADR-009 の「制約に当たった場合」と、ADR-010 の「欠番を作らない」は、本ADRの取り消しによって、両立する。未成立の会話への送信で、識別子が別の会話のメッセージと一致した場合も、会話は成立しない。
- 重複した送信は、取り消されるトランザクション1回と、読み取り1回を要する。送り直しは、送信を完了できなかった場合に限られ、頻度は小さい。
- 制約への違反は、一致する相手のメッセージが確定している場合にだけ起こる。取り消した後の読み取りで、保管済みのメッセージは、必ず見つかる(本スライスは、メッセージを削除する操作を持たない。フェーズ2の削除〈PRV-5〉で、この前提を見直す)。
- テスト用のポートの実装は、取り消しを再現しない。一体性と、同時の送信(WS-05、WS-18)は、実際の PostgreSQL を使うサーバーのテストで確かめる。application のテストは、分岐(完了、重複した送信、別の会話との一致)を確かめる([ADR-006](ADR-006-automated-testing.md))。
- 「関数の中では、引数として渡された操作のほかに、ポートを呼ばない」は、import の検査では検出できない。規約とし、レビューで確かめる。
- 一体性は、保管先のトランザクションで保つため、サーバーが複数になっても成り立つ(PERF-3)。
- フェーズ1以降の、複数の保管にまたがるユースケースも、同じトランザクションのポートを使える。そのための操作は、先行して作らない。
