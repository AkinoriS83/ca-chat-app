# 開発方針

ポピュラーなチャットアプリの主要機能を備え、公開して利用されても問題のない品質を持つチャットアプリを、Clean Architectureを実践して開発します。副次的に、本プロジェクトを docs/hypothesis.md の仮説(AI駆動開発におけるClean ArchitectureとYAGNI原則の両立)の検証台とします。

## 目的

1. **実サービスへ拡張できるチャットアプリの雛形を作る**
   - 機能面: テキスト・音声によるやり取り、グループチャットを中心に、ポピュラーなチャットアプリの機能を一通り網羅する。拡張としてファイル共有、画面共有、ビデオ会議を備える。
   - 非機能面: セキュリティ、アクセスコントロール等を、公開して利活用されても問題のない水準で技術選定・設計する。パフォーマンス・スケーラビリティは、想定規模と開発体制に見合った範囲で考慮する(「非機能要件」参照)。
2. **Clean Architectureの実践**
   - Robert C.Martin (著)日本語訳の「Clean Architecture 達人に学ぶソフトウェアの構造と設計」に基づく層構造・依存規則を、雛形の土台として実践する。構造(レイヤー分割・依存規則・strict layering)は開発の初期から採用する(その理由は docs/hypothesis.md)。
   - 副次的に、本プロジェクトを docs/hypothesis.md の仮説の検証台とし、構造の効果と携行コストの検証記録(計測結果・振り返り)を残す。

### 到達目標(雛形の定義)

当面の到達目標は、実サービスとして利用できる形に拡張できる雛形とすることです。ここでの「雛形」は以下を満たす状態を指します。対象とするフェーズの範囲と具体的な完了条件は、企画書の成功基準で定めます。

- 想定規模(「非機能要件」参照)において、公開環境で第三者が利用したとしても、非機能要件で定めた水準を満たす設計・実装になっている(本プロジェクト自身は公開・運営しない。「雛形の公開範囲」参照)。
- 機能の追加や、想定規模を超える利用規模の拡大(実サービス化)に対し、Clean Architectureの層構造を保ったまま拡張できる。

### 雛形の公開範囲

雛形の公開範囲は、GitHubでのソースコードの公開と、Zennでの記事の公開とします。AWS上のサーバーは検証用に限り、第三者が利用できるサービスとしては公開(運営)しません。

この方針は、以下の2点を目的とします。

- **法令上の義務の回避**: 第三者が利用できるチャットサービスを運営すると、他人の通信を媒介する者として法令上の義務(例: 電気通信事業法上の届出や通信の秘密の保護、個人情報の取扱いに係る義務)が生じうる。サービスを運営しないことで、これらの義務が生じない形とする。
- **企画書以降の規模を開発体制に合わせる**: サービスの運営を前提にすると、運営に伴う要件(利用規約・プライバシーポリシーの整備、問い合わせ・違反行為への対応、常時稼働の運用等)が企画書以降の成果物に加わり、開発者1名の体制(「開発体制」参照)を超える。運営しないことで、企画書以降の対象を雛形そのものに限定する。

本文書でいう「公開して利活用されても問題のない水準」は、雛形を利用する者が自らの責任で公開・運営した場合に満たせる、設計・実装上の水準を指します。本プロジェクト自身が公開・運営することを意味せず、水準の確認は自身の検証環境(「開発体制」参照)で行います。

## 開発フェーズと機能

開発はフェーズに分けて進めます。フェーズ1をMVP(Minimum Viable Product)とし、フェーズ2以降はMVP完了後に段階的に拡張します。

### フェーズ1(MVP)
1. ユーザー登録/編集
2. 認証(ログイン/ログアウト)
3. テキストによる1on1でのリアルタイムチャット機能(通信相手の特定〈ユーザー一覧・検索等〉を含む)
4. メッセージ履歴の永続化と取得(ページング)
5. オンライン/オフラインのプレゼンス表示

### フェーズ2(MVP完了後)
1. テキストによる複数人でのリアルタイムチャット機能(グループチャット)
2. ユーザー削除(削除ユーザーのメッセージの扱い〈カスケード削除/匿名化〉の設計を含む)
3. 新着の把握(会話画面を開いていない相手にメッセージが届いたことを、アプリ内で把握できる。1on1/グループ共通)
4. 既読管理(誰がどこまで読んだかが分かる)

グループチャットは、hypothesis.md の検証方法が「フェーズ2(グループチャット追加)時」を、既存の層構造に機能追加が閉じるかを観察するチェックポイントとしているため、MVPに含めずフェーズ2に置きます。

### フェーズ3(MVP完了後)
1. 音声による1on1でのリアルタイムチャット機能
2. 音声による複数人でのリアルタイムチャット機能

音声チャットはテキストチャットとは技術領域が大きく異なる為、テキストチャットの完成後に取り組むフェーズとして分離します。

### フェーズ4(拡張)
1. ファイル共有
2. 画面共有
3. ビデオ会議(1on1/複数人)

画面共有・ビデオ会議はフェーズ3のリアルタイムメディア通信の上に積み上げます。ファイル共有はメディア通信とは独立した領域(ファイルの保管・配信・アクセス制御)のため、フェーズ4内の着手順は企画以降で判断します。

### 上記以外の機能
上記以外のポピュラーなチャットアプリの機能(例: メッセージの編集・削除、リアクション、アプリ外への通知、メッセージ検索)を網羅の対象に含めるか、含める場合にどのフェーズに置くかは、企画で判断します。

## 非機能要件

公開して利活用されても問題のない水準を、技術選定と設計の前提とします。ただし、非機能要件の水準は「開発体制」に合わせて定めます。検証に規模を要するもの(パフォーマンス・スケーラビリティ等)は技術選定・設計で考慮するに留め、検証はテストコードで確認できる範囲とします。

雛形の想定規模は、利用者数十人程度とします。各領域の目標水準は、この想定規模に基づき、かつ「開発体制」の検証環境で確認できる範囲で企画書に定めます。技術選定はその水準を満たせることを条件とします。

- **セキュリティ**: 認証情報の安全な保管、通信経路の暗号化、一般的な脆弱性(OWASP Top 10 相当)への対策、濫用(大量送信・総当たり等)の抑止。E2E暗号化の採否は企画で判断する。
- **アクセスコントロール**: 会話・メッセージ・ファイル・通話等の資源への操作を、利用者の参加関係と権限に基づいて認可する。認可されない操作は、存在の有無を含めて漏らさない。
- **パフォーマンス・スケーラビリティ**: 数値目標は定めず、想定規模で支障なく利用できることを技術選定・設計で考慮する。想定規模では単一サーバー構成を許容する。ただし、実サービス化に伴うスケールアウト(複数サーバー構成)を妨げる技術選定・設計は採らない(スケールアウトの仕組み自体は先行実装しない)。
- **可用性・運用**: デプロイ、ログ・監視、データのバックアップの水準を、開発者1名で運用できる範囲で企画で定める。これは雛形として備える仕組みの水準であり、第三者向けサービスとしての運営(常時稼働等)は対象外とする(「雛形の公開範囲」参照)。
- **プライバシー**: 個人データの扱いと、退会時のデータの扱いを定める(フェーズ2のユーザー削除と整合させる)。

### 非機能要件とYAGNI原則の関係
非機能要件は本プロジェクトの目的から現に求められている要件であり、投機的な実装ではありません。ただし hypothesis.md の「適用範囲の限定」に従い、YAGNI原則の適用除外は構造に限ります。非機能要件についても以下を守ります。

- 実装する仕組みは、企画書で定めた目標水準を満たす範囲に留める。目標水準を超える仕組み(例: 想定規模に対して過大な分散構成・冗長化)は作らない。
- 各機能スライスは、そのスライスの機能に必要な非機能要件を満たす。後続フェーズの機能のための非機能の仕組みを先回りして作らない。
- 技術選定では、後続フェーズで目標水準を満たす妨げにならないことを確認する(選定の確認であり、仕組みの先行実装ではない)。

## 開発体制

- 開発者は1名(本人)で、AI(Claude)を使用して開発を進める。
- 検証はローカル環境を中心に行う。検証に数台の端末が必要な場合(例: 複数の利用者間での通話・画面共有)は、仮想環境、またはAWS上に配置した小規模なノードで行う。AWS上の環境は自身の検証用とし、第三者には公開しない(「雛形の公開範囲」参照)。
- 検証にかける費用は小さく抑える。

## 開発の流れ

開発は、Clean Architectureを採用した形で、以下の流れで行います。(レビューは、逐次挟む。)

なお、Clean Architectureの構造的採用(レイヤー分割・依存規則・呼び出し経路のstrict layering)は docs/hypothesis.md の仮説に基づき先行確定済みとします。それ以外の技術要素の決定(通信方式、実装言語・使用ライブラリ、インフラ構成、型参照の範囲〈hypothesis.md 参照〉等)は、仕様以降のフェーズに遅延させます。企画・ユースケースの成果物には特定の技術要素を記述しません(非機能要件の目標水準は、技術要素に依存しない形で企画書に記述する)。

企画 → ユースケース → 仕様 → 設計 → 実装 ↔ テスト → 動作検証

ただし、全機能を一括で各フェーズに通すのではなく、機能単位でこの流れを回します。まずテキスト1on1チャットを企画から動作検証まで薄く貫通させ(ウォーキングスケルトン)、Clean Architectureの層構造を早期に検証した上で、以降の機能を縦に積み上げていきます。

なお、企画とユースケースはプロジェクト全体を対象に一度だけ実施し、仕様以降のフェーズを機能単位で回します。ウォーキングスケルトンの対象はテキスト1on1チャットとし、前提となるユーザー登録・認証は貫通時点では固定ユーザー等の仮実装で代替し、スケルトンの層構造検証後に正式実装します。仮実装はMVP完了までにすべて正式実装に置き換え、MVP完了時点で非機能要件の目標水準(MVPの機能に関わるもの)を満たすものとします。

各フェーズの成果物は次の通りです。

- 企画 = 企画書(目的、対象ユーザーと利用シナリオ、機能スコープ、非機能要件の目標水準、成功基準、リスク)
- ユースケース = ユースケース記述
- 仕様 = 機能仕様(非機能要件を受け入れ基準に含める)と技術要素の決定
- 設計 = ADRおよび使い捨て詳細設計(「設計フェーズの進め方」参照)

非機能要件は機能横断の関心事として、企画で目標水準を定め、各機能スライスの仕様で当該スライスの受け入れ基準に落とし込み、テストと動作検証で確認します。クライアントはブラウザを第一想定とします。

## 設計フェーズの進め方
設計は2段階(ADR+使い捨て詳細設計)に分けて実施します(この分割を採用した背景は後述)。ドキュメントは寿命に応じて以下の3種類に役割分担します。

1. **ADR(Architecture Decision Record)= なぜその構造にするか**
   - アーキテクチャや設計の採用判断を記録する。主戦場は設計フェーズだが、仕様フェーズ以降にアーキテクチャ上重要な判断が発生した時点で随時起こす(例: リアルタイム通信方式の選定、認証方式の選定)。
   - 1つのADRには1つの判断のみを記載し、ADR-001形式の連番を付与する。定型は「Context / Decision / 検討した代替案 / Consequences」とする。
   - ステータスは active(作成時から実装完了まで)/ frozen(実装完了後)の2つ。frozenのADRは編集せず、時系列で設計判断を追跡できる状態を保つ。
   - 過去の判断を部分的に打ち消す・修正する場合は、新しいADRにその設計判断を記載する(supersededのような状態は管理の煩雑化を避けるため設けない)。
2. **実装方法に具体的に言及した使い捨ての詳細設計 = これからどう実装するか**
   - 設計フェーズの終盤〜実装直前に、機能スライス単位で作成する(AI開発ツールの実装計画機能〈CursorやClaude CodeのPlanモード〉で作成する計画文書に相当)。実装完了後は使い捨てる。
3. **アーキテクチャ概要 = 今どうなっているか**
   - リポジトリ全体の現在の姿(層構成、ディレクトリ構造、依存の向き、実行環境の構成)を説明する軽量な文書を1枚だけ持ち、メンテし続ける。ADR(なぜ)と使い捨て詳細設計(これから)がカバーしない「現在」を担う。

なお、アーキテクチャ上の新たな判断を伴わない機能スライスでは、ADRを起こさず使い捨て詳細設計のみでよいものとします。

仮説の検証記録(計測結果・振り返り)は、上記3種類とは別の長寿命文書として時系列に残します。指標の定義と計測タイミングは、hypothesis.md の検証方法に基づき、ウォーキングスケルトンの設計フェーズでADRとして定めます。

### 設計を2段階に分けた背景
直近で参画したプロジェクトでは、Cursorを用いて、設計判断と実装方法の仔細を1つの設計書に纏めて開発を進めていた。その結果、リファクタリングや機能追加・修正のたびに設計書のメンテナンスコストが高くつき、実装と冗長な部分も大きかった。かといってメンテナンスを放棄すると設計書が陳腐化する問題があり、両立が難しかった。そこで設計を2段階に分け、実装方法の仔細はAI開発ツールの実装計画機能(CursorのPlanモード)に記述して実装後に使い捨て、設計判断はADRとしてactive/frozenのステータス管理で残す形を採り、後から時系列に設計判断を追跡できるようにした。
