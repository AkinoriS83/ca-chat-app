# 企画書

本書は、[開発方針](development-policy.md)が定める開発の流れのうち、企画フェーズの成果物です。プロジェクト全体(フェーズ1〜4)を対象に、目的、対象ユーザーと利用シナリオ、機能スコープ、非機能要件の目標水準、成功基準、リスクを定めます。

本書の前提は次の通りです。

- 開発方針が「企画で判断する」「企画書に定める」とした事項は、本書で判断し、理由とともに記載する。
- 特定の技術要素(通信方式、実装言語・使用ライブラリ、インフラ構成等)は記述しない。技術要素は仕様以降のフェーズで決定する。運用の前提をAWSとする点は、開発方針「開発体制」に由来する制約であり、本書での技術選定ではない。
- 背景と用語は開発方針および[仮説](hypothesis.md)に従い、本書では繰り返さない。

## 目的

実サービスへ拡張できるチャットアプリの雛形を、Clean Architectureを実践して開発します。雛形は次の2点を満たすものとします(開発方針「到達目標」)。

- 想定規模(利用者数十人程度)において、公開環境で第三者が利用したとしても、本書の非機能要件の目標水準を満たす。
- 機能の追加や利用規模の拡大に対し、Clean Architectureの層構造を保ったまま拡張できる。

副次的に、仮説(AI駆動開発におけるClean ArchitectureとYAGNI原則の両立)を実践し、振り返り・観察記録を残します。仮説の採否は判定しません。

成果物の公開範囲は、GitHubでのソースコードとZennでの記事です。ソースコードは、雛形の利用者が改変・再利用できるよう、MITライセンスで公開します。第三者が利用できるサービスとしては公開・運営しません。

## 対象ユーザーと利用シナリオ

### 対象ユーザー

本プロジェクトはサービスを運営しないため、成果物の直接の受け手は雛形の利用者です。エンドユーザーと運営者は、雛形が満たすべき水準を定めるために想定する利用者像であり、本プロジェクトでは開発者自身が検証環境でその役割を担います。

| 区分 | 想定する人 | 雛形に求めること |
|---|---|---|
| 雛形の利用者 | 雛形を基に自らのチャットサービスを開発・公開したい開発者。Clean Architectureの実践例を参照したい開発者 | 自分の環境で動かせる。層構造を保ったまま機能を追加できる。公開するときに自分で対応すべき範囲が分かる |
| エンドユーザー | 雛形から作られたサービスで会話する人。数十人程度のコミュニティ(チーム、サークル、友人同士等)の一員で、ブラウザから利用する | 相手やグループとテキスト・音声でやり取りできる。自分の会話と個人データを、関係のない人に見られない |
| 運営者 | 雛形から作られたサービスを設置・運用する人(多くの場合、雛形の利用者自身) | 1名で設置・更新・バックアップ・障害調査ができる |

エンドユーザーについて、次を前提とします。

- 1つの設置環境(雛形を構築して動かしている1つの環境)を、1つの場として利用する。複数の組織・コミュニティを1つの設置環境に同居させ、互いを見えなくする利用形態は対象外とする。
- 登録は、招待を要さず、誰でも行える。登録時に連絡先(メールアドレス)を登録し、本人がその連絡先を受け取れることを確認する。
- 登録済みの利用者は、相手を特定して会話を始められる。誰でも登録できるため、全利用者を列挙できる一覧は提供しない。相手を特定する手段と、利用者情報を見せる範囲は、ユースケースで定める(AC-7)。
- 会話と通話は、アプリを開いてその場に居る利用者同士で行う。通話は会話の中で開始し、アプリを開いている参加者に知らせて、参加してもらう。アプリを開いていない利用者を呼び出す手段は持たない。不在の間に届いたメッセージは、次にアプリを開いたときに把握する。

### 開発方針に挙がっていない機能の採否

次のいずれかに当たる機能を採用し、それ以外は対象外とします。

- (a) 欠けると、非機能要件の目標水準(プライバシー、濫用の抑止)を損なう。
- (b) 開発方針が判断の候補として例示した機能であり、新たな技術領域や外部サービスへの依存を伴わない。

(b)で候補を開発方針の例示に限るのは、開発者1名の規模に収めるためです。例示にない機能は、(a)に当たるものだけを採用します。

採用する機能はすべてテキストチャットに属するため、フェーズ2に置きます(音声チャットはテキストチャットの完成後に取り組む、という開発方針に合わせる)。

| 機能 | 判断 | 理由 |
|---|---|---|
| メッセージの編集・削除 | 採用(フェーズ2) | (a)(b)。誤って送った内容を本人が取り消せることは、プライバシーの水準に関わる。フェーズ2のユーザー削除で設計する「メッセージの扱い」と同じ領域にある |
| リアクション | 採用(フェーズ2) | (b)。既存のメッセージに付随する機能で、新たな技術領域を要しない |
| メッセージ検索 | 採用(フェーズ2) | (b)。想定規模では新たな技術領域を要しない |
| ブロック | 採用(フェーズ2) | (a)。誰でも登録でき、登録済みの利用者は相手を特定して話しかけられるため、望まない相手を利用者自身が遮断する手段が要る。運営者による対応(下記)を対象外とするので、これがアプリ内の唯一の手段になる |
| アプリ外への通知 | 対象外 | 会話と通話は、アプリを開いてその場に居る利用者同士で行う方針とする(「対象ユーザー」の前提)。アプリを開いている間の把握は「新着の把握」で満たす。メールの送信は連絡先の確認と再設定に限る(PRV-3)。通知に広げると、送信量の管理、濫用への対策、配信停止の扱いが新たに要る。ブラウザを閉じている利用者へ届ける通知は、外部の配信の仕組みへの依存を伴う。この帰結として、新着の知らせと通話の開始の知らせは、アプリを開いている利用者にのみ届く(メッセージ自体は保管され、次にアプリを開いたときに読める) |
| 返信(引用)・スレッド、メンション、入力中の表示、ピン留め、転送、リンクのプレビュー | 対象外 | 開発方針の例示になく、(a)にも当たらない。雛形の到達後に、層構造の上へ追加できる機能である |
| 運営者向けの管理機能(通報の受付、利用停止、投稿の監視) | 対象外 | サービスの運営に伴う要件であり、開発方針「雛形の公開範囲」により対象としない |

このほか、次を対象外とします。

- サービスの運営に伴う成果物(利用規約、プライバシーポリシー、問い合わせ窓口)。
- ブラウザ以外のクライアント(端末に導入する専用アプリ)。
- E2E暗号化(「セキュリティ」の「E2E暗号化の採否」参照)。

### 着手順

- **フェーズ1**: テキスト1on1チャットをウォーキングスケルトンとして先に貫通させ(ユーザー登録・認証は仮実装)、その後に残りの機能を正式実装する(開発方針「開発の流れ」)。
- **フェーズ2**: グループチャットを最初に着手する。理由は2つある。(1) 仮説のチェックポイント(グループチャット追加時の観察)を、他の機能追加が混ざる前のMVPの構造に対して行うため。(2) 新着の把握・既読管理・リアクション・検索は1on1とグループに共通する機能であり、グループチャットの後に作る方が手戻りが少ないため。
- **フェーズ4**: 着手順はフェーズ3の完了時に判断する(ファイル共有はメディア通信と独立しており、現時点で順序を固定する理由がない)。

## 非機能要件の目標水準

想定規模は、利用者数十人程度(同時に利用する人数も同程度)とします。

各水準にはIDを付けます。仕様フェーズでは、各機能スライスの受け入れ基準からこのIDを参照します。水準は、それが関わる機能を実装するスライスから適用し、後続フェーズのための仕組みを先回りして作りません(開発方針「非機能要件とYAGNI原則の関係」)。特定の機能に属さない水準を含め、各水準を最初に適用する時点は、本章末尾の「水準を最初に適用する時点」に定めます。確認は、自動テストと、検証環境での動作検証で行います。上限値などの具体的な値は、各スライスの仕様で定めます。

### セキュリティ

- **SEC-1 認証情報の保管**: 利用者の認証に用いる秘密は、保管データが漏えいしても元の値を現実的な計算量で復元できない形でのみ保管する。認証に用いる秘密、ログイン状態を示す資格、連絡先の確認・再設定のための一時的な資格は、ログやエラー応答に出力しない(出力が避けられない箇所では伏せる)。
- **SEC-2 通信経路の暗号化**: 利用者の端末とサーバーの間、および端末同士が直接通信する場合はその間の、すべての通信(認証、メッセージ、音声・映像、ファイル)を暗号化する。ローカルの開発環境を除き、暗号化されていない経路での利用を受け付けない。
- **SEC-3 ログイン状態の管理**: ログアウトすると、そのログインで得た資格では操作できなくなる。ログイン状態には有効期限を設ける。認証に用いる秘密を変更または再設定したとき、他の端末のログイン状態を無効にする。退会したとき、その利用者のすべてのログイン状態を無効にする。連絡先の確認・再設定のための一時的な資格は、有効期限を設け、一度だけ使えるものとする。
- **SEC-4 一般的な脆弱性への対策**: OWASP Top 10(各フェーズで最初の仕様に着手する時点の最新版)の各項目について、機能スライスごとに該当の有無を確認し、該当する項目への対策を受け入れ基準に含める。少なくとも次を満たす。
  - 入力の検証をサーバー側で行う。
  - 利用者が入力した内容が、他の利用者の画面でプログラムとして解釈・実行されない。
  - 利用者が意図しない操作を、第三者のサイトから実行させられない。
  - エラー応答に、内部の構造が分かる情報を含めない。
- **SEC-5 濫用の抑止**: 認証の連続した失敗に対して試行を制限する(総当たりの抑止)。登録、連絡先への送信(確認・再設定)、メッセージ送信、検索、通話の開始などの操作に、利用者ごと・送信元ごとの頻度の上限を設ける。連絡先への送信は、宛先ごとにも上限を設ける(他人の連絡先へ大量に送らせる濫用の抑止)。メッセージの長さやファイルの大きさに上限を設ける。上限を超えた要求は拒否する。
- **SEC-6 秘密情報の管理**: リポジトリを公開するため、鍵や接続情報などの秘密を、ソースコードとリポジトリの履歴に含めない。
- **SEC-7 依存物の脆弱性**: 各フェーズの完了時点で、既知の重大な脆弱性が報告されている版の依存物を残さない。機械的な検査で確認する。
- **SEC-8 保管データの保護**: 保管データ、そのバックアップ、ログに、サーバーと運営者以外が到達できない構成とする。
- **SEC-9 共有ファイルの取り扱い(フェーズ4)**: 共有されたファイルが、受け取った利用者のブラウザでプログラムとして実行されない。

#### E2E暗号化の採否

採用しません。理由は次の通りです。

- 履歴の永続化と別の端末からの取得、メッセージ検索、退会時のメッセージの扱いは、サーバーがメッセージを扱えることを前提とする。これらとE2E暗号化を両立させるには、鍵の管理(端末の紛失・追加、グループの参加者の変更)という独立した大きな領域の設計が必要になり、開発者1名の体制と、検証環境で水準を確認できる範囲を超える。
- 不完全な実装は、「守られている」という誤った期待を利用者に与える。

この判断の帰結として、運営者と、サーバーに侵入した者は、保管されたメッセージを読むことができます。メッセージの保護は SEC-2(経路)、SEC-8(保管データ)、アクセスコントロールで行います。この前提は雛形の文書に明記し、雛形の利用者が自らのプライバシーポリシーに反映できるようにします。

### アクセスコントロール

- **AC-1 認証と認可の強制**: 登録とログインを除くすべての操作を、認証済みの利用者に限る。認可はサーバー側で操作のたびに判定し、クライアントの表示制御に依存しない。
- **AC-2 参加関係による認可**: 会話(1on1/グループ)に属する資源(メッセージ、既読、リアクション、ファイル、通話)の読み書きは、その会話の参加者に限る。メッセージ検索の結果も、自分が参加する会話に限る。
- **AC-3 本人による操作**: プロフィールの編集、認証に用いる秘密の変更・再設定、退会、メッセージの編集・削除、ブロックの設定は、本人のみが行える。
- **AC-4 グループ内の権限**: メンバーの追加・除外やグループの設定変更など、グループ内の権限はユースケースで定義し、サーバー側で強制する。
- **AC-5 存在の秘匿**: 認可されない資源への操作に対する応答は、その資源が存在しない場合の応答と、内容から区別できない。
- **AC-6 リアルタイム配信への適用**: リアルタイムに配信する情報(メッセージ、新着、既読、リアクション、プレゼンス、通話の開始の知らせ)にも、AC-2、AC-7、AC-8と同じ認可を適用する。参加関係を失った利用者(グループからの退出・除外、退会)と、ブロックによって見えなくなった相手には、その時点から配信しない。
- **AC-7 利用者情報の公開範囲**: 利用者の情報(プロフィール、プレゼンス)は、認証済みの利用者にのみ見せる。誰でも登録できるため、全利用者を列挙できる一覧は提供しない。相手を特定する手段と、利用者の情報を見せる相手の範囲は、ユースケースで定め、会話を始めるのに必要な範囲に絞る。
- **AC-8 ブロックの効果**: 利用者Aが利用者Bをブロックしている間、次の通りとする。
  - Bからは、Aが存在しない場合と区別できない(相手の特定、プロフィール、プレゼンス)。Bは、Aとの1on1でメッセージの送信と通話の開始ができない。Bにブロックされたことを通知しない。
  - グループでは、グループの仕様を優先する。AとBが同じグループに参加している場合、そのグループの中では、互いの発言と参加を通常どおり見られる。グループの通話も同様とする。
  - Bは、Aを新たにグループへ追加できない(ブロックの迂回を防ぐ)。
  - 同じグループの中ではAが見えるため、BがブロックされたことをAの見え方の違いから推測しうる。これは許容する。
- **AC-9 未認証の操作における存在の秘匿**: 登録、ログイン、再設定の応答は、ある連絡先が登録済みかどうかを、内容から区別できない。ログインの失敗は、理由(アカウントがない、秘密が違う)を区別せずに応答する。利用者が自分で決める識別名を登録に用いる場合、その重複が登録時に分かることは許容し、SEC-5の頻度の上限で緩和する。

認可は、機能ごとに「権限のない利用者の操作が拒否され、資源の存在が漏れない」ことを自動テストで確認します。

### パフォーマンス・スケーラビリティ

数値目標は定めません。規模を要する検証(負荷試験)は、完了条件に含めません。余裕があれば、想定規模を上回る同時接続数(数十〜数百)での負荷試験を任意で行い、結果を記録します。

- **PERF-1 想定規模での利用**: 想定規模で、メッセージの送受信、履歴の閲覧、通話が支障なく行えることを、技術選定のADRと、設計・実装の確認で判断する。あわせて、数台の端末での動作検証で挙動を確かめる。通話について、動作検証で確かめた人数と仕様で定める上限が異なる場合は、その差を雛形の文書に記載する。
- **PERF-2 蓄積量への耐性**: 一覧・履歴・検索結果は分割して取得し、蓄積された件数が増えても1回の取得量が増えないようにする。
- **PERF-3 スケールアウトを妨げない**: 単一サーバー構成を前提にしてよいが、複数サーバー構成への移行を妨げる技術選定・設計を採らない。1つのサーバーの中だけで保持する状態(接続中の利用者、プレゼンス、リアルタイム配信の宛先など)は、内側の層が定義するインターフェイスの背後(外側の層)に置き、複数のサーバーで共有する仕組みへ差し替えられるようにする。これは、現に存在するユースケースが通過する層の境界であり、差し替えのためだけの拡張点を新たに設けるものではない。スケールアウトの仕組み自体は実装しない。妨げにならないことは、技術選定のADRで確認する。

### 可用性・運用

AWS上で個人が運用する程度(小規模な構成を、1名で設置・運用する)を想定します。AWS以外の環境への対応、冗長構成、無停止での更新、稼働率の目標、常時の監視体制は対象外です。利用するAWSのサービスと構成は、仕様以降で決定します。

- **OPS-1 デプロイ**: リポジトリの内容と手順書から、設置環境をまだ構築していないAWSアカウントに、設置環境を構築できる。保管データを保ったまま、新しい版へ更新できる。更新時の短時間の停止は許容する。
- **OPS-2 障害からの復帰**: サーバーが異常終了・再起動しても、送信が完了したと利用者に示したメッセージは失われない。クライアントは接続が切れたことを利用者に示し、再接続した後、切断中に届いたメッセージを取得できる。
- **OPS-3 ログ**: 障害と不正利用の調査に必要な出来事(エラー、認証の成功・失敗、認可の拒否、上限の超過)を、発生時刻とともに記録する。ログには保持期間を設け、期間を過ぎたものは削除する。保持期間は仕様で定める。
- **OPS-4 監視**: サーバーが稼働しているかを、外部から確認できる手段を備える。
- **OPS-5 バックアップ**: 保管データ(アカウント、会話、メッセージ、ファイル)をバックアップする手順と、復元する手順を備える。復元は検証環境で実際に行い、復元後に利用を再開できることを確認する。取得の頻度と保持期間は、仕様で定める。

### プライバシー

- **PRV-1 収集の最小化**: 機能に必要な個人データのみを取得する。取得する項目、用途、保管先を一覧にして文書化する(雛形の利用者が、自らのプライバシーポリシーを作る材料とする)。一覧には、ログに記録する項目(利用者の識別子、送信元の情報など)を含める。
- **PRV-2 他の利用者への公開範囲**: 他の利用者に見せる個人データは、表示用のプロフィールとプレゼンスに限る(見せる相手の範囲は AC-7、AC-8)。会話の参加者には、これに加えて、その会話の中での活動(メッセージ、既読、リアクション、通話への参加)を見せる。連絡先(メールアドレス)は、他の利用者には表示しない。
- **PRV-3 外部への送信**: 個人データとメッセージを、外部のサービスへ送信しない。例外は、連絡先の確認と再設定のためのメールの送信とする。この送信に含めるのは、宛先の連絡先と、手続きに必要な内容に限り、メッセージの本文や他の利用者の情報は含めない。これ以外に、機能の実現に外部のサービスが必要になった場合は、送信する内容をADRに記録する。
- **PRV-4 記録しない情報**: メッセージの本文、ファイルの内容をログに記録しない。通話の音声・映像は保存しない。
- **PRV-5 本人による編集・削除**: 本人が削除したメッセージ・ファイルは、内容が他の利用者から見えなくなり、保管データからも消える。本人が編集したメッセージは、編集前の本文が他の利用者から見えなくなり、保管データからも消える。編集・削除された事実(編集済みである、削除されたメッセージがあった)は、会話に表示して残す。
- **PRV-6 退会時の扱い**: 退会すると、次の通りとする。
  - アカウント、プロフィール、連絡先、認証に用いる秘密、本人の活動の記録(リアクション、既読の位置、ブロックの設定など)を削除する。すべてのログイン状態を無効にする(SEC-3)。
  - 他の利用者との会話に残るメッセージ(フェーズ4以降は共有したファイルを含む)を削除するかどうかは、退会する本人が退会時に選ぶ。削除しない場合、送信者を「削除済みユーザー」に当たる表示に置き換えて残す。この場合、本文に書かれた個人情報は残ることを、選ぶ時点で本人に示す。
  - 退会後は、他の利用者の画面と保管データから、退会者を識別できない(残すことを選んだメッセージの本文を除く)。
- **PRV-7 バックアップとログ内のデータ**: 削除したデータがバックアップに残るのは、バックアップの保持期間までとする。退会者の識別子など、ログに記録された個人データが残るのは、ログの保持期間までとする。それぞれの保持期間を文書に明示する。

ユーザー削除はフェーズ2の機能のため、MVP完了時点では PRV-6 を満たしません。フェーズ2の完了時点で満たします。

### 水準を最初に適用する時点

各水準は、次の時点から受け入れ基準に含めます。それ以降のマイルストーンでは、追加する機能に対して引き続き適用します。

| 最初に適用する時点 | 水準 |
|---|---|
| ウォーキングスケルトン | SEC-4、SEC-6、AC-2、AC-6、PERF-3、PRV-4(AC-2とAC-6は、仮実装の固定ユーザーの間で確認する) |
| フェーズ1(MVP) | SEC-1、SEC-2、SEC-3、SEC-5、SEC-7、SEC-8、AC-1、AC-3、AC-5、AC-7、AC-9、PERF-1、PERF-2、OPS-1〜5、PRV-1、PRV-2、PRV-3、PRV-7 |
| フェーズ2 | AC-4、AC-8、PRV-5、PRV-6 |
| フェーズ4 | SEC-9 |

特定の機能に属さない水準(SEC-2、SEC-6、SEC-8、PRV-1、PRV-7、PERF-3 など)は、上記の時点で最初に着手する機能スライスの受け入れ基準に含めます。SEC-7 は、フェーズ1以降の各フェーズの完了時点で確認します。

## 成功基準

### 対象とするフェーズの範囲

開発方針が当面の到達目標とする「雛形」は、**フェーズ1〜3の完了**をもって到達とします。開発方針が機能面の中心に挙げる、テキスト・音声によるやり取りとグループチャットが、フェーズ3で揃うためです。フェーズ4は到達した雛形に対する拡張と位置づけ、同じ完了条件を適用します。

到達目標のうち「層構造を保ったまま拡張できる」は、次の2点で確認します。機能の追加については、フェーズ2・3の機能を追加した後も、共通の完了条件3(構造の違反0件)を満たしていること。利用規模の拡大については、PERF-3 を技術選定のADRで確認していること。

マイルストーンは次の順です。

ウォーキングスケルトン → フェーズ1(MVP) → フェーズ2 → フェーズ3(雛形の到達) → フェーズ4(拡張)

### 各マイルストーンに共通の完了条件

1. **機能**: 対象の全機能について、ユースケース記述の各フローが仕様の受け入れ基準を満たすことを、自動テストと動作検証で確認している。
2. **非機能**: その時点までに適用を始める目標水準(「水準を最初に適用する時点」)が、対象の機能の受け入れ基準に含まれ、確認できている。
3. **構造**: 依存規則と飛ばし禁止(strict layering)への違反が、機械的な検査で0件である。
4. **文書**: アーキテクチャ概要が現状と一致している。実装を終えたADRが frozen になっている。
5. **観察記録**: 構造の先行実装が妨げになった箇所・助けになった箇所を、発生の都度記録している。

### マイルストーンごとの完了条件

| マイルストーン | 共通の完了条件に加えて満たすこと |
|---|---|
| ウォーキングスケルトン | 2人の利用者(仮実装の固定ユーザー等)が、別々のブラウザから1on1でテキストをリアルタイムにやり取りできる。企画から動作検証までを一度通している。観察記録の項目と記録タイミングを定めたADRがある。仮実装の箇所を一覧にしている(共通の完了条件2は、ウォーキングスケルトンに適用すると定めた水準のみを対象とする) |
| フェーズ1(MVP) | 仮実装がすべて正式実装に置き換わっている。OPS-1〜5を検証環境で確認している(構築、更新、バックアップからの復元を実際に行う)。仮説の「MVP完了時」のチェックポイント(一度も変更・参照されなかった境界要素の数、パススルーなユースケースメソッドの数、振り返り)を記録している |
| フェーズ2 | 仮説の「フェーズ2(グループチャット追加)時」のチェックポイント(変更したファイル数、レイヤー横断の漏れの有無、構造自体の変更の要否)を、グループチャットの完了時に記録している。PRV-6を満たしている |
| フェーズ3(雛形の到達) | 異なるネットワークにつながった端末の間で、1on1の音声通話が成立する。3人以上での音声通話が成立する。加えて、下記「雛形としての公開条件」を満たしている |
| フェーズ4(拡張) | ファイル共有、画面共有、ビデオ会議(1on1/複数人)が、複数の端末の間で成立する |

**雛形としての公開条件**(フェーズ3の完了時)

- ソースコードを、MITライセンスを明示してGitHubで公開している。依存物のライセンスが、この公開と両立している(技術選定の条件とする)。
- 雛形の利用者に向けた文書があり、次を記載している。
  - 設置環境の構築・更新・バックアップ・復元の手順。
  - 取得する個人データの一覧(PRV-1)。
  - 雛形が扱わず、公開・運営する者が自ら対応すべき事項(法令上の義務、利用規約・プライバシーポリシー、問い合わせ・違反行為への対応)。
  - 雛形の限界。次を含む。
    - E2E暗号化を採用していないこと。
    - 第三者によるセキュリティ診断を受けていないこと。
    - 想定規模と単一サーバー構成。負荷試験を行っていない場合はその旨、通話について動作検証で確かめた人数と仕様上の上限の差(PERF-1)。
    - AWS上での個人運用を前提とした運用水準。
    - 誰でも登録できること。運営者が利用者の利用を停止する機能をアプリ内に持たないこと。
    - アプリ外への通知を持たず、新着と通話の開始は、アプリを開いている利用者にのみ知らされること。
    - 同じグループの中では、ブロックした相手と互いに見えること(AC-8)。
- 雛形と観察記録を紹介する記事を、Zennで公開している。

### 成功基準に含めないもの

- 仮説の採否(判定しない。支持する所見と支持しない所見の両方を記録する)。
- 機能追加が構造の変更を要したかどうか(観察の対象であり、合否の条件ではない)。
- 利用者数や稼働の実績(サービスを運営しないため)。
- 性能の数値、負荷試験の実施(任意で行った場合は、結果を記録する)。
