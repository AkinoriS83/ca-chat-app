# 仮説: AI駆動開発によるClean ArchitectureとYAGNI原則の両立

## 仮説(一文で)
AI駆動開発においては、Clean Architectureの構造的価値(関心事・責務の分離、依存規則)を「YAGNI原則の適用除外となる必須要件」に昇格させた方が、総コストが下がり、以降のYAGNI原則の実践も容易になる。

## 背景・問題意識

### Clean Architecture側の問題
Clean Architectureは、Robert C. Martinの著書にもある通り、それを実現するためのインターフェイスやデータ構造の構築に高いコストを支払う必要があり、開発初期段階における早すぎる抽象化はYAGNI原則に違反するとされる。著書は「後から拡張しやすいように部分的な抽象化を採用する」等のアプローチを紹介しているが、どのアプローチも潜在的な問題を孕んでいるとしている。

### YAGNI原則側の問題
「You Aren't Gonna Need It(必要ないだろう)」は、裏を返せば「必要になったとき、適切に実装する必要がある」ということだが、実際にこれを行うのは難しい。

- **トリガー問題:** 直近のAI駆動開発でYAGNI原則を実践した経験では、ガイドラインに記載してAIに丸投げでは機能しなかった。「今が抽象化のタイミングだ」と判断してトリガーを引くのは開発者であり、AIと共同して実践する必要があった。
- **現場の力学:** 多くの現場では「優秀なエンジニアの工数を確保できているうちに、予測型の機能や抽象化を済ませてしまおう」という力学が働き、YAGNI原則の実践を一層困難にしている。

### 前提: YAGNIは経済的判断である
YAGNI原則は道徳律ではなく、構築コスト・携行(維持)コスト・遅延コストの比較に基づく経済的判断である。AI駆動開発は「定型的な冗長化の構築コストをほぼゼロにする」形でこのコスト構造を変えたため、損益分岐点の再計算 — すなわち本仮説を実地で試し、観察すること — には合理性がある。

## 仮説の本体
Clean Architectureの提供価値のうち、以下の**構造的価値**を、インターフェイスやデータ構造の冗長化を伴っても提供が必要なものと見なし、YAGNI原則に違反しない必須要件として設計する。

1. 関心事・責務の分離
2. 依存規則: ソースコードの依存は外側(詳細)から内側(上位方針)への一方向のみ
   - 加えて本プロジェクトでは、**呼び出し経路について**中間レイヤーを飛ばした依存を禁止する(例: ハンドラーはユースケースを経由せずリポジトリに到達できない)。これは書籍の依存規則そのものではなく、より厳格な追加ルール〈strict layering〉としての意図的な採用である。
   - この飛ばし禁止を採用する理由: (a) 「ハンドラーがユースケースを飛ばしてリポジトリを直接呼ぶ」はAIが最も取りやすいショートカットであり、その防波堤になる(根拠4の具体化)。(b) パッケージ間のimport制約としてlintで機械的に強制でき、施行コストが最も安い部類のルールである(AIに構造を守らせる本仮説の実行可能性を支える)。
   - なお、禁止するのは呼び出し経路の飛ばしのみであり、**型参照**(内側の型をどこまで外側に見せるか)は別の判断として仕様/設計フェーズで決める。型参照まで一律に禁止すると全境界でDTO変換が強制され、後述の「境界要素は必要な箇所のみに置く」最適化と矛盾するためである。

### 根拠
1. **生成コストの低下:** レイヤー境界のインターフェイスやデータ構造の冗長化は、AIにとって生成が容易でコストがかからない。
2. **AIパフォーマンスへの直接効果:** 関心事・責務の分離と依存関係が適切に設計されているか否かは、AIが読むべきコンテキストの量と精度に直結し、パフォーマンスとコストに大きな影響を与える。
3. **将来のYAGNI実践の局所化:** 予めレイヤーを適切に切っておくことで、「必要になったときの抽象化」がレイヤー内に閉じやすくなる。つまり構造への先行投資は、YAGNI原則の後段(必要時の適切な実装)を実行可能にするための投資である。
4. **負債の加速抑制:** AI駆動開発では、プロジェクトの拡大に伴い設計判断を違えると、技術的負債(および認知・理解負債)が加速度的に増大する。逐次適切な設計判断ができる構造を先に用意しておく。

## 適用範囲の限定(除外規定の拡大解釈を防ぐ)
YAGNI適用除外は**構造**に限る。以下の境界線を守る。

- **除外対象(必須要件として先行実装してよい):** レイヤー分割、依存の向きの強制、レイヤー境界のインターフェイスと境界を越えるためのデータ構造(DTO等)
- **除外対象外(引き続きYAGNIを全面適用する):** 機能レベルの投機的汎用化 — 未使用エンティティのための汎用リポジトリ、使う予定のない設定項目・プラグインポイント、予測型の機能実装、過剰なパラメータ化 等

境界インターフェイス・DTOも「当然必要なもののみとする」最適化は行う(現に存在するユースケースが通過する境界にのみ置く)。

## 想定される反論と応答

- **反論1: AIにとっても維持コストはゼロではない。** 冗長なインターフェイスやDTOはコンテキストウィンドウを消費し、1変更あたりの修正ファイル数(ショットガン・サージェリー)を増やす。
  → その通りであり、だからこそ除外対象を上記の構造に限定し、境界要素は必要な箇所のみに置く。本仮説は「生成が安いから何でも作ってよい」ではなく「構造に限れば携行コストを上回る便益がある」という主張である。
- **反論2: AIはリファクタリングも安くするので、必要になってから抽象化すればよく、YAGNIはむしろ強化される。**
  → AIが得意なのは局所的なリファクタリングであり、構造のないコードベースを横断する大規模リファクタリングは依然として苦手でリスクも高い。事前の層構造は、まさに将来のリファクタリングを「局所的で安い」領域に閉じ込めるための前提条件である(根拠3)。

## 観察方法
本プロジェクト(チャットアプリ)を、本仮説を実践する場とする。MVPを本仮説に従って構築し、以下のチェックポイントで振り返り・観察を行う。

### 位置づけ(検証ではなく振り返り・観察記録)
本仮説は「総コストが下がる」という比較の主張だが、本プロジェクトは比較対象(構造を先行させない開発)を置かない1件の事例である。また、採否を判定する基準を定める材料となる前例が、着手時点で見当たらない。そのため、本プロジェクトでは仮説の採否を判定せず、仮説に従って開発した結果の振り返り・観察記録を残すに留める。記録は、仮説を支持する所見と支持しない所見の両方を残す。

### チェックポイント
- **MVP完了時:** 構造の先行実装が開発の妨げになった箇所・助けになった箇所を振り返る。境界要素のうち一度も変更・参照されなかったもの(純粋な携行コスト)を数える。また、飛ばし禁止ルールの携行コストとして、リポジトリへ委譲するだけのパススルーなユースケースメソッドの数を数え、振り返りの結果コストが重いと判断すればフェーズ2以降に新しいADRでルールを緩めることを検討する。
- **フェーズ2(グループチャット追加)時:** 機能追加が既存レイヤー構造の中に閉じたか、構造自体の変更を要したかを観察する。変更されたファイル数・レイヤー横断の漏れの有無を目安とする。
- **雛形の到達後(フェーズ3の完了後)にブロックを追加する場合:** 既存の機能(相手の特定、1on1とグループの会話、プレゼンス、通話)にまたがる機能を追加したとき、既存の機能のコードを、どのレイヤーで、どれだけ変更したかを観察する。フェーズ2のチェックポイントが「機能追加が既存の構造に閉じるか」を見るのに対し、ここでは横断的な機能の追加を見る。レイヤーごとの変更されたファイル数、既存の機能のコードを変更した箇所、構造自体の変更の要否を目安とする。ブロックのための拡張点は、追加の時点まで先行して設けない(「適用範囲の限定」)。ただし、フェーズ1〜3は、ブロックを後から追加しうることを知ったうえで設計する。この知識が既存の設計に影響した可能性を、所見に併記する。ブロックを追加するかどうかは、フェーズ3の完了時に判断し、追加しない場合、このチェックポイントは実施しない。経緯は、企画書(docs/project-plan.md)の「ブロックを対象外とする判断」を参照。

チェックポイントで数えるものの数え方は、docs/adr/ADR-008-observation-records.md で定める。同ADRは、境界要素を「現に存在するユースケースが通過する境界にのみ置く」方針の下では、どこからも参照されない境界要素がほぼ生じないことから、MVP完了時の「一度も変更・参照されなかったもの」を、「導入したスライスの完了より後に変更されず、抽象としても働かなかったもの」と読み替えている。

妨げになった箇所・助けになった箇所は、後から遡って復元できないため、開発中に発生の都度記録する。

観察結果と振り返りの所見は、ADRまたは本メモの追記として記録する。
