### OBS-001

| 項目 | 内容 |
|---|---|
| 日付 | 2026-11-19 |
| スライスと工程 | ウォーキングスケルトン、設計 |
| 区分 | 妨げ |
| 出来事 | 型参照の範囲を決めようとした。仮説は、呼び出し経路の飛ばし禁止と、型参照を、別の判断としている。Go の import は、型の参照と、関数の呼び出しを区別しない。ユースケースを呼ぶ adapter に、domain の型の参照を許すと、domain の規則を直接呼ぶ経路も、import の検査で検出できなくなる。このため、ユースケースを呼ぶ境界に、専用の入力・出力のデータ構造と、拒否の種類の定義を置くことにした |
| 関わる構造 | ユースケースを呼ぶ境界(adapter → usecase)。飛ばし禁止。型参照の範囲 |
| 手がかり | [ADR-005](adr/ADR-005-layer-structure.md)「型参照の範囲」「検討した代替案」。[ADR-001](adr/ADR-001-language-and-libraries.md) の Consequences。コミット 717a9c5 |
| 所見 | 飛ばし禁止を、import の検査で安く強制できること(仮説「仮説の本体」の(b))と、型参照の範囲を別に決められることが、Go では両立しなかった。ユースケースの出力の詰め替えが、1回増える。型だけの import を区別できる言語(TypeScript)では、この制約は生じないため、構造そのものではなく、言語の選定との組み合わせによる。実装の前であり、コストの大きさは、まだ分からない。構造がなかった場合との差は、推測である |

### OBS-002

| 項目 | 内容 |
|---|---|
| 日付 | 2026-11-20 |
| スライスと工程 | ウォーキングスケルトン、設計(ADRのレビュー) |
| 区分 | 妨げ |
| 出来事 | WebSocket を、1つの adapter のパッケージで扱う構成にしていた。このパッケージは、ユースケースを呼び、かつ、配信のポートを実装するため、usecase、port、domain のすべての import を許す、規則の例外になっていた。レビューで、リアルタイムの経路でだけ、飛ばしを検出できないことに気付いた。パッケージを、接続の受け付けと、配信の2つに分け、接続を、ユースケースを経由して渡す形に改めた |
| 関わる構造 | adapter の層。依存規則と飛ばし禁止。境界要素(接続への書き込み口のインターフェイス、接続を登録するポート、登録を解くポート) |
| 手がかり | [ADR-005](adr/ADR-005-layer-structure.md)「WebSocket を扱う adapter の分割」 |
| 所見 | 外部の相手が双方向である場合、「ユースケースを呼ぶ adapter」と「ポートを実装する adapter」の二分に、そのままでは収まらなかった。規則を保つために、境界要素が3つと、ポートを呼ぶだけのユースケースが増えた。一方で、配信の adapter は、WebSocket のライブラリに依存しなくなった。実装の前であり、増えた要素が妨げになるかどうかは、まだ分からない。構造がなかった場合との差は、推測である |
