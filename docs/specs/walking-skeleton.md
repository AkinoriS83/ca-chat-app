# ウォーキングスケルトン仕様

本書は、[開発方針](../development-policy.md)が定める開発の流れのうち、仕様フェーズの成果物です。最初の機能スライスであるウォーキングスケルトン(テキスト1on1チャットを、企画から動作検証まで薄く貫通させるもの)を対象に、対象とするフローの範囲、機能仕様、受け入れ基準を定めます。

本書の前提は次の通りです。

- [ユースケース記述](../use-cases.md)が「ウォーキングスケルトンの仕様で定める」とした事項(対象とするフローの範囲、送り直しによるメッセージの重複の扱い)と、仕様を定める上で判断が必要だった事項は、本書で判断し、理由とともに記載する(「本書で判断した事項」)。
- 受け入れ基準からは、ユースケース記述のフローと、[企画書](../project-plan.md)の非機能要件の目標水準を、IDで参照する(企画書「各マイルストーンに共通の完了条件」1、2)。
- 技術要素(通信方式、実装言語・使用ライブラリ、保管先など)は、本書では選定しない。本書は、振る舞いを技術要素に依存しない形で定め、決定すべき技術要素と選定の条件を挙げる(「技術要素の決定」)。選定はADRに記録する。
- 画面の構成と操作の手段は、設計で定める。
- 背景と用語は、開発方針、[仮説](../hypothesis.md)、企画書、ユースケース記述に従う。

本書で付けるIDは、次の通りです。IDは、本書を改訂しても振り直さず、欠番を許します。

| ID | 対象 |
|---|---|
| WS-D1〜 | 本書で判断した事項 |
| WS-P1〜 | 仮実装 |
| WS-01〜 | 受け入れ基準 |

## 目的と完了の姿

ウォーキングスケルトンの目的は、Clean Architectureの層構造を早期に検証することと、企画から動作検証までの流れを一度通すことです(開発方針「開発の流れ」)。

完了の姿は、2人の利用者が、別々のブラウザから、1on1でテキストをリアルタイムにやり取りできることです(企画書「マイルストーンごとの完了条件」)。このために、本スライスは次の3つの経路を、画面から保管まで通します。

| 経路 | 内容 |
|---|---|
| 送信 | 本文の入力 → 検証と認可 → 保管 → 完了の応答 |
| 配信 | 保管したメッセージを、アプリを開いている参加者へ即時に届ける |
| 取得 | 会話を開いたときに、保管済みのメッセージを履歴として示す |

## 本書で判断した事項

### WS-D1 対象とするフローの範囲

対象は、UC-09(メッセージを送る)とUC-11(会話の履歴を読む)の、1on1会話に関わるフローのうち、次の表で「対象」としたものです。

| フロー | 扱い | 補足 |
|---|---|---|
| UC-09 基本フロー | 対象 | |
| UC-09 A1(1on1会話の最初のメッセージ) | 対象 | 会話の一覧に現れることは除く(UC-10が対象外のため) |
| UC-09 E1(本文が正しくない) | 対象 | 検証の規則は WS-D3 |
| UC-09 E2(頻度の上限) | 対象外 | SEC-5 とともに、フェーズ1で扱う |
| UC-09 E3(会話が見つからない) | 対象 | |
| UC-09 E4(相手が退会している) | 対象外 | フェーズ2 |
| UC-09 E6(送信を完了できなかった) | 対象 | 送り直しによる重複の扱いは WS-D2 |
| UC-11 基本フロー | 対象 | 分割しての取得(手順2の件数の区切り、手順3)は除く(WS-D4) |
| UC-11 A1(開いている間にメッセージが届いた) | 対象 | |
| UC-11 A2、A3 | 対象外 | フェーズ2 |
| UC-11 E1(会話が見つからない) | 対象 | |

共通の規則(ユースケース記述「共通の規則」)は、次の通り扱います。

| 規則 | 扱い |
|---|---|
| R-1 ログイン済みであること | 仮実装で代替する(WS-P2) |
| R-2 存在の秘匿 | 対象のフロー(UC-09 E3、UC-11 E1)に適用する |
| R-3 入力の検証と上限 | 形式と長さの検証を適用する。頻度の上限は対象外とする |
| R-4 リアルタイム配信の宛先 | 適用する |
| R-5 分割しての取得 | 対象外とする(WS-D4) |
| R-6 記録 | 対象外とする(OPS-3 とともに、フェーズ1で扱う)。メッセージの本文を記録しないこと(PRV-4)は適用する |

範囲は、次の基準で定めました。

- 完了の姿を満たすのに欠かせないフローと、ウォーキングスケルトンから適用する水準(企画書「水準を最初に適用する時点」)の確認に必要なフローを含める。
- 対象のフローから切り離せる仕組み(頻度の上限、分割しての取得、再接続)は、それを扱う水準を適用する時点まで送る(開発方針「非機能要件とYAGNI原則の関係」)。
- 保管は、仮実装としない。メッセージは、正式な保管先に保管する。送信から取得までが保管を通らなければ、層構造を外側の端まで検証できないためです。

この基準の帰結として、フェーズ1から適用する水準のうち2つを、対象のフローに限って先に満たします。どちらも、フローの定義そのものであり、後から加えると応答の内容が変わるためです。水準としての適用(他の操作への適用と、網羅の確認)は、企画書の通りフェーズ1から行います。

- UC-09 E1 の長さの上限(SEC-5 に属する)。本文の検証(SEC-4)の一部として定める(WS-D3)。
- UC-09 E3、UC-11 E1 の「同じ応答で拒否する」(AC-5 に属する)。

### WS-D2 送り直しによる重複の扱い(UC-09 E6)

送信には、クライアントが送信の操作ごとに作る「送信の識別子」を添えます。送り直しには、最初の送信と同じ識別子を使います。システムは、同じ送信者から、保管済みのメッセージと同じ識別子の送信を受けた場合、新しいメッセージを保管せず、保管済みのメッセージについて送信の完了を示します。

- 送信が保管されたが、完了の応答だけが届かなかった場合、送信者には、送信が届かなかった場合と区別が付きません。重複を許すと、送り直しによって、相手に同じメッセージが2通見えます。送信者には、これを避ける手段がありません。
- 本文の一致や送信時刻の近さで判定する方法は採りません。同じ本文を意図して続けて送る場合と、区別できないためです。
- 一致は、送信者ごとに判定します。他の利用者の識別子と一致しても、別の送信として扱います。送信者をまたいで判定すると、他の利用者の送信を妨げることや、他の利用者のメッセージについての応答を得ることができてしまうためです(AC-2)。
- 一致の判定に、本文は用いません。識別子が一致すれば、本文が異なっていても、最初に保管した内容を保ちます。
- 識別子は、メッセージとともに保管し、判定に期限を設けません。期限を設けると、期限の後の送り直しで重複が生じ、期限を管理する仕組みも要るためです。
- 識別子の形式は、設計で定めます。
- この帰結として、送信者に完了を示していないメッセージが、保管され、相手に届いていることがあります(UC-09 事後条件3)。送信者が送り直さなかった場合も、そのメッセージは会話に残り、送信者が次に会話を開いたときに、履歴に現れます。

### WS-D3 本文の検証の規則(UC-09 E1)

本文は、次のすべてを満たすものを正しいとします。

| 規則 | 内容 |
|---|---|
| 空でない | 空白文字(Unicodeの White_Space 特性を持つ文字)以外の文字を、1文字以上含む |
| 長さの上限 | 4,000文字以下。文字は、Unicodeのコードポイントで数える |
| 使える文字 | Unicodeの制御文字(一般カテゴリ Cc)を含まない。ただし、改行(U+000A)とタブ(U+0009)は使える |

- 上限の4,000文字は、想定する用途(コミュニティの中の会話)の1通として足りる長さであり、1通が保管と配信に与える負荷に上限を与えます。
- コードポイントで数えるのは、クライアントとサーバーが、それぞれの実装言語の文字列の表現に依らず、同じ数え方をできるようにするためです。
- 制御文字を拒否するのは、表示されない文字と、保管先や通信の途中で扱えない文字が、本文に混ざらないようにするためです。
- 正しい本文は、前後の空白を含め、入力された通りに保管します。

### WS-D4 履歴は、分割せずに取得する

ウォーキングスケルトンでは、会話を開いたときに、その会話のすべてのメッセージを取得して示します(WS-P4)。

- 分割しての取得(R-5、PERF-2)は、フェーズ1から適用する水準です。開発方針も、「メッセージ履歴の永続化と取得(ページング)」を、1on1のリアルタイムチャットとは別の機能として挙げています。
- この帰結として、メッセージが増えると、1回の取得量が増えます。固定ユーザーの間の検証で蓄積する量では、支障がないものとします。

### WS-D5 固定ユーザーは3人とする

仮実装の固定ユーザーは、3人とします(WS-P1)。

- やり取りの確認には2人で足りますが、AC-2とAC-6は「仮実装の固定ユーザーの間で確認する」と定められています(企画書「水準を最初に適用する時点」)。2人だけでは、すべての会話がその2人のものとなり、参加者でない利用者の操作が拒否されることを確認できません。

### WS-D6 動かす環境は、ローカルの開発環境に限る

ウォーキングスケルトンは、開発者の端末の上のローカルの開発環境でのみ動かします。AWS上の検証環境には構築しません。

- 仮のログイン(WS-P2)は、認証に用いる秘密を持たず、誰でも任意の固定ユーザーとして振る舞えます。ローカルの開発環境の外に置くと、到達できる人すべてが、すべての会話を読み書きできます(企画書「リスク」6)。
- 設置環境の構築(OPS-1)と、通信経路の暗号化(SEC-2。ローカルの開発環境を除く)は、フェーズ1から適用する水準です。
- この帰結として、動作検証の「別々のブラウザ」は、開発者の端末の上の、互いに状態を共有しない2つ以上のブラウザ(別のブラウザ、または別のプロファイル)とします。対応するブラウザの範囲は、フェーズ1の仕様で定めます(企画書「仕様以降で決める事項」)。

## 仮実装

本スライスで仮実装とするものです。MVPの完了までに、すべて正式実装に置き換えます(企画書「マイルストーンごとの完了条件」)。実装の中で仮実装となった箇所の一覧は、本表のIDと対応させて管理します(置き場所は設計で定める)。

| ID | 仮実装 | 代替している対象 | 正式実装との違い |
|---|---|---|---|
| WS-P1 | 固定ユーザー | UC-01、UC-05、UC-06 | 利用者は、あらかじめ定めた3人に限る。登録、プロフィールの編集、連絡先は持たない |
| WS-P2 | 仮のログイン | UC-02、UC-03、UC-04、UC-07、R-1 | 利用者は、固定ユーザーから自分として振る舞う1人を選ぶだけでログインした状態になる。認証に用いる秘密、有効期限、ログアウトを持たない。なりすましを防がない |
| WS-P3 | 相手の選択 | UC-08 | 相手を、識別名の入力ではなく、固定ユーザーの一覧から選ぶ。全利用者を列挙できる一覧を提供しないこと(AC-7)を満たさない |
| WS-P4 | 履歴の一括取得 | UC-11 基本フロー 2〜3、R-5 | 会話のすべてのメッセージを、一度に取得する(WS-D4) |

次は、仮実装ではなく、本スライスでは実装しないものです。

| 実装しないもの | 扱う時点 | 本スライスでの帰結 |
|---|---|---|
| 会話の一覧(UC-10) | フェーズ1 | 会話は、相手を選んで開く(WS-P3) |
| プレゼンス(UC-12) | フェーズ1 | 相手がアプリを開いているかどうかは、示さない |
| 切断からの復帰(UC-13) | フェーズ1 | 接続が切れた後に受信を再開するには、利用者がアプリを開き直す。切断中のメッセージは、開き直したときに履歴として読める |
| 頻度の上限(UC-09 E2、SEC-5) | フェーズ1 | 送信の頻度は制限しない |
| 出来事の記録(R-6、OPS-3) | フェーズ1 | 認証・認可・上限に関する出来事は、記録しない |
| 新着の把握(UC-20) | フェーズ2 | 開いていない会話に届いたメッセージは、その会話を開くまで分からない |

## 機能仕様

### 利用者(WS-P1、WS-P2)

固定ユーザーは、次の3人です。

| 識別名 | 表示名 |
|---|---|
| alice | Alice |
| bob | Bob |
| carol | Carol |

- 利用者は、アプリを開き、固定ユーザーの中から、自分として振る舞う1人を選ぶ。
- システムは、以後の操作とリアルタイムの接続を、選ばれた固定ユーザーによるものとして扱う。
- システムは、固定ユーザーのいずれでもない利用者としての操作と接続を、拒否する。
- 同じ固定ユーザーを、複数のブラウザで同時に選べる。

### 会話を開く(WS-P3)

- 利用者は、自分以外の固定ユーザーの中から相手を1人選び、その相手との1on1会話を開く。
- 同じ2人の間の1on1会話は、1つだけである。どちらが相手を選んでも、同じ会話を開く。
- 開いただけでは、会話は成立しない。相手には何も知らされない(D-3)。会話は、最初のメッセージの送信によって成立する(UC-09 A1)。
- 成立していない会話を開いた場合、システムは、メッセージがないことを示す。

### メッセージ

| 項目 | 内容 |
|---|---|
| 本文 | WS-D3 の規則を満たすテキスト |
| 送信者 | 送信した利用者。表示名で示す |
| 送信の日時 | システムがメッセージを保管した日時。クライアントの時計には依らない |
| 順序 | 会話の中で、システムがメッセージを保管した順 |

- 本文は、書式を持たないテキストとして扱う。改行を含め、入力された通りに表示する。本文を、表示のための書式や、プログラムとして解釈しない(SEC-4)。
- メッセージは、会話のすべての参加者に、履歴としても、リアルタイムの配信としても、同じ順序で見える。

### メッセージを送る(UC-09)

1. 送信者は、開いている会話で本文を入力し、送信する。クライアントは、送信の識別子を添える(WS-D2)。
2. システムは、送信者と会話を確かめ、本文を検証して、メッセージを保管する。成立していない会話への送信であれば、併せて、会話を成立させる。
3. システムは、送信が完了したことを送信者に示す。クライアントは、そのメッセージを、送信の日時とともに会話に示す。
4. システムは、メッセージを、リアルタイムに配信する(「リアルタイムの配信」)。

システムは、次の場合に送信を拒否します。拒否した送信は、保管せず、配信せず、会話も成立させません。

| 場合 | 応答 | フロー |
|---|---|---|
| 本文が WS-D3 の規則を満たさない | 本文が正しくないことを示す | UC-09 E1 |
| 送信の識別子の形式が正しくない | 入力が正しくないことを示す | R-3 |
| 相手として自分自身を指定した | 相手にできないことを示す | UC-09 A1、UC-08 E2 |
| 相手が固定ユーザーの中に居ない | 見つからないことを示す | UC-09 E3 |
| 送信者が参加者でない会話を指定した | 会話が存在しない場合と同じ応答で、見つからないことを示す | UC-09 E3、R-2 |

検証と認可は、サーバー側で、送信のたびに行います。クライアントでの検証は、利用者への早い通知のためのものであり、サーバー側の検証に代えません。

送信を完了できなかった場合(UC-09 E6)は、次の通りです。

- クライアントは、次のいずれかの場合に、送信できなかったことを送信者に示す。
  - 接続が切れている。
  - 送信から10秒以内に、完了の応答も、拒否の応答も得られない。
- 送信できなかった本文は、失われない。送信者は、入力し直さずに、同じ本文を送り直せる。
- 送り直しは、最初の送信と同じ送信の識別子で行う。保管済みであった場合、システムは、新しいメッセージを保管せず、再び配信もせず、完了を示す(WS-D2)。
- クライアントは、完了したメッセージと、送信できなかったメッセージを、送信者が見分けられるように示す。

10秒は、送信者が成否を待てる長さとして定めた値です。保管に失敗した場合など、システムが送信を完了できなかった場合は、完了を示さず、メッセージを配信しません。

### 会話の履歴を読む(UC-11)

1. 利用者は、会話を開く。
2. システムは、その会話のすべてのメッセージを、順序の通りに示す(WS-D4)。各メッセージには、送信者の表示名と、送信の日時を示す。
3. メッセージがない場合、システムは、ないことを示す。

- 利用者が参加者でない会話を指定した場合、システムは、会話が存在しない場合と同じ応答で拒否する(UC-11 E1、R-2)。
- 会話を開いている間に届いたメッセージは、即時に、履歴に続けて示す(UC-11 A1)。
- 会話を開いた時点までに保管されたメッセージは履歴として、それより後に保管されたメッセージはリアルタイムの配信として届く。クライアントは、その境目で、メッセージを欠かすことも、重複して示すこともない。
- アプリを開いていない間に届いたメッセージは、次に会話を開いたときに、履歴として読める(UC-09 基本フロー 4)。

### リアルタイムの配信

- 宛先は、そのメッセージの会話の参加者(送信者と相手)が、アプリを開いている端末のすべてとする。送信者が他の端末でアプリを開いている場合、その端末も宛先に含む(UC-09 基本フロー 3)。
- 宛先は、配信する時点で、サーバー側で判定する。参加者でない利用者の端末には、メッセージも、メッセージがあったことも、届けない(R-4、AC-6)。
- 「即時」は、受け取る側の利用者が操作(再読み込みなど)をしなくても、表示されることを指す。所要時間の数値目標は定めない(企画書「パフォーマンス・スケーラビリティ」)。
- 受け取る側の利用者が、別の会話を開いている場合、開いている会話の中には示さない。そのメッセージは、該当する会話を開いたときに、履歴として読める。
- 配信が端末に届かなかった場合も、保管と、送信者への完了の応答は取り消さない。届かなかったメッセージは、履歴として読める。

## 非機能要件の適用

ウォーキングスケルトンから適用する水準(企画書「水準を最初に適用する時点」)と、本スライスでの受け入れ基準の対応です。

| 水準 | 本スライスでの適用 | 受け入れ基準 |
|---|---|---|
| SEC-4 一般的な脆弱性への対策 | 下記「OWASP Top 10 の該当の確認」の通り | WS-09〜WS-13、WS-26〜WS-32 |
| SEC-6 秘密情報の管理 | 保管先への接続情報などの秘密を、リポジトリとその履歴に含めない | WS-34 |
| AC-2 参加関係による認可 | メッセージの読み書きを、その会話の参加者に限る。固定ユーザーの間で確認する | WS-19、WS-23、WS-24、WS-26 |
| AC-6 リアルタイム配信への適用 | 配信の宛先を、その会話の参加者に限る。固定ユーザーの間で確認する | WS-25、WS-26 |
| PERF-3 スケールアウトを妨げない | 接続中の端末と配信の宛先を保持する状態を、内側の層が定義するインターフェイスの背後に置く。技術選定のADRで、複数サーバー構成への移行を妨げないことを確認する | WS-35、WS-36 |
| PRV-4 記録しない情報 | メッセージの本文を、ログに記録しない | WS-33 |

### OWASP Top 10 の該当の確認(SEC-4)

SEC-4 は、OWASP Top 10 の各項目について、機能スライスごとに該当の有無を確認することを求めています。版は、フェーズ1で最初の仕様となる本書の着手時点(2026年11月)で最新の、OWASP Top 10:2025 とします。フェーズ1の後続のスライスも、この版を使います。

| 項目 | 該当 | 本スライスでの対策 | 受け入れ基準 |
|---|---|---|---|
| A01 Broken Access Control | 該当 | 認可を、サーバー側で操作のたびに判定する。配信の宛先を、参加者に限る。第三者のサイトから、利用者のブラウザを介した操作をさせない | WS-23〜WS-25、WS-29 |
| A02 Security Misconfiguration | 該当 | エラー応答に、内部の構造が分かる情報を含めない | WS-30 |
| A03 Software Supply Chain Failures | 該当 | 依存物の版を固定し、リポジトリに記録する。既知の脆弱性の検査(SEC-7)は、フェーズ1の完了時に行う | WS-32 |
| A04 Cryptographic Failures | 該当しない | 本スライスは、認証に用いる秘密を扱わず、ローカルの開発環境でのみ動かす(WS-D6)。SEC-1、SEC-2 は、フェーズ1から適用する | — |
| A05 Injection | 該当 | 本文を、保管先への問い合わせの一部としても、画面の構造やプログラムとしても解釈しない | WS-27、WS-28 |
| A06 Insecure Design | 該当 | 検証と認可を、クライアントに依存せず、サーバー側で行う | WS-12、WS-26 |
| A07 Authentication Failures | 該当しない | 認証は仮実装であり(WS-P2)、本スライスでは水準を満たさない。フェーズ1の認証のスライスで扱う | — |
| A08 Software or Data Integrity Failures | 該当しない | 本スライスは、外部から取得したコードやデータを実行・適用する仕組みと、更新の仕組みを持たない | — |
| A09 Security Logging and Alerting Failures | 該当しない | 出来事の記録(OPS-3)は、フェーズ1から適用する。本スライスでは、ログに本文を出力しないこと(PRV-4)だけを確認する | WS-33 |
| A10 Mishandling of Exceptional Conditions | 該当 | 保管に失敗した送信を、完了として扱わない。想定しない入力に対しても、内部の構造が分かる応答を返さない | WS-30、WS-31 |

## 動作検証

ローカルの開発環境で、互いに状態を共有しない3つのブラウザ(以下、ブラウザ1〜3)を使って行います(WS-D6)。

| # | 手順 | 期待する結果 | 基準 |
|---|---|---|---|
| 1 | ブラウザ1で alice を選び、相手に bob を選ぶ。ブラウザ2で bob を選び、相手に alice を選ぶ | どちらにも、メッセージがないことが示される | WS-21 |
| 2 | ブラウザ1から、メッセージを送信する | ブラウザ1に、完了したメッセージが示される。ブラウザ2に、操作なしに、同じメッセージが示される | WS-01、WS-02 |
| 3 | ブラウザ2から返信する。続けて、双方から数通ずつ送信する | 双方に、操作なしに示される。メッセージの順序が、双方で一致する | WS-02、WS-07 |
| 4 | ブラウザ3で alice を選び、相手に bob を選ぶ。ブラウザ1から送信する | ブラウザ3に、それまでの履歴が示される。ブラウザ1からのメッセージが、ブラウザ3にも操作なしに示される | WS-03、WS-20 |
| 5 | ブラウザ3で carol を選び直し、相手に alice を選ぶ。ブラウザ1(alice と bob の会話)から送信する | ブラウザ3には、alice と bob の会話のメッセージが、履歴としても、配信としても示されない | WS-25 |
| 6 | ブラウザ2を閉じる。ブラウザ1から送信する。ブラウザ2を開き直し、bob として alice との会話を開く | 閉じている間のメッセージが、履歴として示される | WS-04 |
| 7 | サーバーを再起動する。各ブラウザを開き直す | それまでのメッセージが、すべて履歴として示される | WS-08 |
| 8 | サーバーを停止した状態で、ブラウザ1から送信する。サーバーを起動し、ブラウザ1を開き直さずに送り直せる場合は送り直す。開き直しが必要な場合は、開き直して履歴を確かめる | 送信できなかったことが示され、本文は失われない。送り直した場合も、履歴には1通だけが示される | WS-17、WS-18 |
| 9 | 画面の構造やプログラムとして解釈されうる記述を含む本文を送信する | 双方の画面に、文字として示され、実行されない | WS-27 |

手順8について、再接続(UC-13)は本スライスの対象外です。サーバーを起動した後に、開き直さずに送り直せるかどうかは、選定する通信方式に依ります。動作検証の手順は、設計で具体化します。

## 技術要素の決定

仕様フェーズの成果物には、技術要素の決定が含まれます(開発方針「開発の流れ」)。本スライスで決定が要る事項と、選定の条件は、次の通りです。それぞれ、1つの判断を1つのADRに記録します(開発方針「設計フェーズの進め方」)。

| 決定する事項 | 選定で確認すること |
|---|---|
| 実装言語と主要なライブラリ(サーバー、クライアント) | 依存規則と飛ばし禁止を、機械的に検査できる。フェーズ1〜3の機能(認証、ブラウザでの音声通話)と、AWS上での個人による運用を妨げない |
| リアルタイムの通信方式 | サーバーからブラウザへ、操作なしに届けられる。接続ごとに利用者を特定し、宛先を絞れる(AC-6)。第三者のサイトからの接続を拒否できる(WS-29)。経路を暗号化できる(SEC-2)。複数サーバー構成へ移行できる(PERF-3) |
| 保管先 | 完了を示したメッセージが失われない(OPS-2)。分割しての取得(PERF-2)、バックアップと復元(OPS-5)、複数のサーバーからの共有(PERF-3)を妨げない |
| 層の構成、依存規則と飛ばし禁止を検査する手段、型参照の範囲 | 仮説「仮説の本体」の構造を満たす。境界要素は、現に存在するユースケースが通過する境界にのみ置く(仮説「適用範囲の限定」) |
| 自動テストの手段 | 本書の受け入れ基準のうち、確認方法を「自動テスト」としたものを確認できる。複数の利用者の接続にまたがる基準(WS-02、WS-25 など)を含む |
| ローカルの開発環境の構成 | 秘密をリポジトリに含めずに、手順に従って起動できる(SEC-6) |

すべての選定に共通して、次を確認します。

- 後続フェーズで目標水準を満たす妨げにならない(開発方針「非機能要件とYAGNI原則の関係」)。確認であり、後続フェーズのための仕組みは先行して作らない。
- 依存物のライセンスが、MITライセンスでの公開と両立する(企画書「雛形としての公開条件」)。
- 個人データとメッセージを、外部のサービスへ送信しない(PRV-3)。
- 検証にかける費用を、小さく抑えられる(開発方針「開発体制」)。

観察記録の項目と記録タイミングは、本スライスの設計フェーズで、ADRとして定めます(開発方針「設計フェーズの進め方」)。
